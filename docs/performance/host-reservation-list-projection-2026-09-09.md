# 호스트 예약 목록 조회 개선

## 판단 근거

대상은 `GET /api/v1/profile/host/reservations`다. 원격 main을 다시 가져와 확인했으며,
프론트 작업트리 `codex/editable-booking-review`에는 `origin/main`의 `f80bc095`가 이미 포함되어 있었다.

`reservationListViewModel.ts`와 `ProfileController.tsx`에서 확인한 주요 소비는 다음과 같다.

| 데이터 | 용도 |
| --- | --- |
| 예약 UID | 상세 화면 이동과 목록 행 구분 |
| 예약 코드·상태·인원·예약 금액 | 목록 표시 |
| 체크인·체크아웃 날짜 | 날짜 표시 및 현재 불러온 목록의 체크인순 정렬 |
| 생성 시각 | 예약일 표시 및 서버 커서 |
| 게스트 닉네임·숙소 이름 | 목록 표시 |
| 예약 내부 ID | 생성 시각 동률 처리와 서버 커서 생성; 응답에는 노출하지 않음 |

기존 조회는 예약·숙소·게스트 엔티티 전체를 읽었다. 각 숙소·게스트 조인은 PK 한 건을 참조하므로
현재 한 번의 조인은 적절하다. 응답 생성과 커서에 필요한 17개 컬럼만 읽는 projection으로 변경했다.
기존 응답의 통화·예약 시간대·게스트 및 숙소 기본 정보도 보존했다.
주소·결제·취소 이력을 추가로 조회하거나 목록에 합칠 필요는 없다.

## 보존한 동작

- 조회 소유권은 `accommodation.member.id = hostId`로 제한한다.
- `PAYMENT_PENDING`, `PAYMENT_PROCESSING` 예약은 호스트 목록에서 제외한다.
- `UPCOMING`과 `PAST`는 확정·취소 처리 중·취소 실패 예약을 대상으로 체크아웃 시각을 구분한다.
  정확한 체크아웃 시각은 `PAST`에 속한다. `CANCELLED`는 취소·만료 예약을 포함한다.
- 서버 정렬은 `createdAt DESC, id DESC`다. 프론트의 체크인순 정렬은 불러온 목록 안에서만 수행한다.
- 한 페이지보다 한 건 더 조회해 다음 페이지 여부를 판단한다.
  커서는 **실제 반환한 마지막 행**의 ID와 생성 시각으로 만든다.
- 생성 시각의 마이크로초 정밀도, 예약 당시 날짜·시간대, 최종 페이지의 null 커서,
  빈 페이지의 `current_size: 0`을 유지한다.
- 현재 비공개인 숙소나 주소·이미지가 없는 숙소의 기존 예약도 누락하지 않는다.
- 목록 금액은 기존 `reservation.totalPrice`를 사용한다. 결제나 취소 잔액으로 바꾸지 않는다.

## 선택 필터의 오류 수정

컨트롤러는 `filterType`을 선택 파라미터로 선언했지만, 저장소는 null을 switch에 전달해
`NullPointerException`이 발생했다. 이를 실제 서비스·MySQL 통합 테스트로 재현했다.

필터 생략 시 날짜·상태 필터를 추가하지 않도록 수정했다. 호스트 소유권과 결제 대기·진행 중
예약 제외 조건은 항상 적용한다. 프론트가 지정하는 기존 세 필터의 결과는 바뀌지 않는다.

## 측정 결과

MySQL 8.4.11 Testcontainers에서 직전 구현 `e921af7c`와 동일한 테스트 데이터를 사용했다.
서비스 호출 전에 영속성 컨텍스트와 Hibernate 통계를 초기화했다.

| 항목 | 이전 | 이후 |
| --- | ---: | ---: |
| 페이지당 SQL 수 | 1 | 1 |
| SELECT 컬럼 수 | 55 | 17 |
| 엔티티 적재 — 두 건 반환하는 첫 페이지 fixture | 7 | 0 |
| 주소·결제·거래 원장 추가 조회 | 0 | 0 |

첫 페이지 fixture는 다음 페이지 확인용 예약까지 3건, 숙소 2건, 게스트 2건을 적재하던 경우다.
엔티티 수는 페이지 데이터에 따라 달라지며, 개선 후에는 projection만 생성한다.
HTTP 인증 SQL은 포함하지 않았고 운영 응답 시간·처리량의 개선 비율은 아직 측정하지 않았다.

## 검증

- 백엔드 67개 통과: 호스트 목록 통합 테스트 7개, 예약 상세 결제 조회 14개,
  예약 DTO 7개, 예약 저장소·트랜잭션 테스트 39개.
- 세 필터의 생성 시각 동률 페이지, 소유권, 마지막·빈 페이지, 결제 대기·진행 중 제외를 검증했다.
- 커서 기준 행 삭제와 더 최신 예약 삽입 후에도 남은 페이지가 누락·중복 없이 이어지는지 확인했다.
- 필터 생략 시 조회 범위와 권한·결제 상태 제한을 검증했다.
- 실제 DB에서 만든 전체 응답을 `contracts/host-reservation-list.json`과 비교한다.
  동일 fixture를 프론트 wire mapper와 목록 표시 테스트에서 사용한다.
- 프론트 예약·프로필 관련 테스트 292개, 브라우저 테스트 3개, 타입 검사와 strict lint 통과.
  브라우저에서는 추가 페이지 로딩 후 체크인순 재정렬과 행 보존을 확인했다.
  브라우저 검사는 응답 fixture를 사용하며 실행 중인 백엔드와 연결한 E2E는 아니다.

인덱스·DB 스키마·쓰기 경로·ES 검색은 이번 변경 범위가 아니다.
게스트 목록을 비롯한 다른 조회의 projection 필요성과 실행계획·운영 지연 시간은 별도 검토 대상이다.
