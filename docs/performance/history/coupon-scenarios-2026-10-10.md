# 쿠폰 한계 탐색과 추가 시나리오의 로컬 근거

원본 계측 파일·설정·검증 기록: [측정 당시 보관본](https://github.com/eeoos/airbob/tree/a10b89a1bfdc173f3f327ed4657a1df2db14d2cd/docs/performance/results/coupon-scenarios-2026-10-10).

[보고서](coupon-local-results.md)의 2026-10-10 추가 측정 자료다.
2026-10-09의 고정 500 RPS 실험과 다른 실행 묶음이며 통계를 합치지 않는다.
커넥션 풀 선정 실험은 보류한 상태로, 앱 1개·Hikari 최대/최소 유휴 10개를 고정했다.
기존 JAR을 그대로 사용했고 AWS 자원이나 기존 개발용 컨테이너는 변경하지 않았다.

| 파일 | 범위 |
|---|---|
| `capacity-coarse.json` | 큰 부하 단계 44회와 추가 300 RPS 1회, 워밍업·실행 설정·정리·원본 해시 |
| `capacity-coarse-raw.ndjson.gz` | 위 실행의 클라이언트·SQL 카운터·재고·잠금·풀·자원 원본, 중단된 부분 실행 포함 |
| `capacity-refinement.json` | 경계 이분 탐색 20회, 워밍업·앞 실행의 경계 입력·원본 해시 |
| `capacity-refinement-raw.ndjson.gz` | 경계 탐색의 클라이언트·관측·상태 원본 |
| `scenario-suite.json` | 7개 시나리오 × 5개 방식 × 2라운드의 본 측정 70회와 워밍업 70회 |
| `scenario-suite-raw.ndjson.gz` | 위 시나리오의 클라이언트·관측 전후 카운터·표본·상태·준비 이벤트 원본 |
| `harness-sources.ndjson.gz` | 세 실행에서 보존한 스크립트·설정 예제·문서 사본 79개와 원본 해시 |
| `validation.json` | 수정된 측정 도구의 Python/k6 테스트 56개 통과와 범위·로그 해시 |
| `SHA256SUMS` | 이 묶음의 파일별 SHA-256 (`SHA256SUMS` 자신은 제외) |

시나리오 70회 중 63회 유효·56회 통과했다. 실제 요청은 861,356건으로,
성공 712,366건·품절 99,990건·중복 거절 49,000건이었다. 모든 완료 회차의 재고와 회원별 고유 발급 수가 맞았고,
CP012·예상 밖 응답·InnoDB 교착 상태는 관측되지 않았다. 성능 실패와 데이터 정합성 실패를 구분한다.

## 실행 구분

- `local-20261010-004725-3294`: 각 회차 20초, 초기 재고 20,001개, 2라운드.
  큰 단계가 끝난 뒤 도구의 경계 계산 문제를 발견하여 종료했다. 전체 실행 상태는 `incomplete`다.
  완료 회차의 정합성·실패·무효 판정은 보존하며, 한 번만 수행한 추가 300 RPS를 반복 통과 경계로 쓰지 않는다.
- `local-20261010-013103-3a96`: 같은 JAR·재고·측정 시간·반복·VU·SLO를 검사한 뒤 경계부터 재개했다.
  새 앱과 일회성 DB에서 수행했으므로 하나의 연속 실행으로 표현하지 않는다.
  중간값으로 구간을 이분하고 남은 폭이 100 RPS 이하일 때 멈췄다.
- `local-20261010-015411-009f`: C 결과에서 정한 400/650 RPS 지속 부하와 급증·회복, 재고 1,000개·1개,
  중복 요청, 다른 캠페인 준비를 순서대로 완료했다. 정확한 조건은 `metadata.workloadPlan`에 있다.
  이전 fixture는 비활성화하되 발급 이력과 잔여 unit은 같은 실행의 DB에 남는다. DB 버퍼 풀 128MiB와
  실행 중 테이블 크기 추정치를 `notes.mysql-runtime-context.json`에 보존했다.

각 본 측정 직전에 별도 쿠폰으로 100 RPS·10초 워밍업을 했다. 회원 인증과 측정 대상 쿠폰의 재고 준비는
측정 밖이며, 다른 캠페인 준비를 병행하는 마지막 시나리오만 그 별도 준비 작업을 측정 구간에 포함한다.
원본 스크립트는 실행 디렉터리의 `source/k6/`에 고정했으며 JSON에 파일별 SHA-256이 있다.
`harness-sources.ndjson.gz`의 각 줄에는 `runId`, `path`, `sha256`, `text`가 있다. 런타임 비공개 파일을 만들기
전에 복사한 저장소 소스이며, 설정 예제의 자리표시자는 실제 실행 자격 증명이 아니다.
첫 실행의 세션 재작성 과정에서 이전 비공개 입력 파일을 별도 보존한 조치와 경계 재시작 사유도 `notes`에 남겼다.

## 원본 형식과 해석

압축 파일은 한 줄에 하나의 JSON 레코드다. `path`는 실행 디렉터리 기준 상대 경로이고,
`completedTrial`은 그 회차의 `result.json` 존재 여부다. `data`는 JSON 문서 또는 관측 표본 배열이다.
완료되지 않은 회차도 남기되, 완료 회차의 요청 합계·성능 통계에 포함하지 않는다.

요약 JSON의 `runs`에는 모든 완료 본 측정과 워밍업이 있다. `metadata`, `notes`,
`sourceArtifactSha256`은 실행 조건·정리 결과·인증 갱신 시점·원본 무결성을 확인하기 위한 자료다.
애플리케이션 로그, 이메일, 로그인 세션, 비밀번호, 토큰, 비공개 fixture 파일은 포함하지 않는다.
소스 사본에는 테스트용 예제 문자열과 필드 이름이 포함될 수 있으며, 실제 회원 manifest와 구분한다.

시나리오 실행 사본의 구간별 `droppedIterations`는 사용자 정의 태그로 잘못 분리되어 실제 누락이 있어도
0이 될 수 있다. 해당 필드를 구간별 누락 없음의 증거로 쓰지 않는다. 전체 `droppedIterations`,
실제 구간별 HTTP 수, 지연·응답·정합성은 유지되며 무효 판정도 전체 누락·실제 요청 수로 잡혔다.
원본은 고치지 않았다. 제한과 이후 `scenario` 태그 수정·회귀 검증은 `notes.segment-drop-observation.json`에 있다.
수정된 현재 스크립트와 측정 당시 사본을 구분한다.

`notes.harness-validation-window.json`은 테스트의 시작·종료 시각과 현재 코드 해시를 보존한다.
세션 갱신 중 수행한 테스트가 완료된 140개 HTTP 회차와 겹치지 않음을 검사했다.
짧은 본 측정의 워밍업 세션 수 가드를 보완한 뒤에는 실험 정리 후 같은 56개를 다시 통과했다.
최종 코드 해시·시간·로그 해시는 `notes.post-run-validation-window.json`에 있으며, 테스트 수를 112개로 합산하지 않는다.
`notes.final-verification.json`은 140회 정합성, 준비 캠페인 20개, 실행 코드 검증과 리소스 정리를 기록한다.
실험용 앱 포트는 닫혔고 두 컨테이너는 삭제됐으며, 기존 개발 컨테이너 11개는 모두 실행 중이었다.

격리 수준 설정·복원 명령의 관찰과 사용 라이브러리 확인은 `notes.session-control-observation.json`,
`notes.session-control-implementation.json`에 있다. 여러 비교군·준비·워밍업이 섞인 누적 관찰이며,
회차별 성능 비용이나 RC 결과의 원인을 정량적으로 분리한 실험은 아니다.

요청 누락·관측 누락·호스트 자원 기준 미달은 무효다. 지연 기준만 넘은 유효한 회차도 실패로 남긴다.
무효나 실패 회차를 지우고 개선율을 만들지 않는다. 부하 발생기·앱·DB가 공유하는 호스트의 결과이므로,
여기서 관측한 구간을 운영 최대 처리량이나 DB 자체의 한계로 표현하지 않는다.

풀 대기만으로 풀 크기 부족을 확정하지 않는다. 행 잠금 대상·대기 시간·커넥션 사용 시간·
호스트 자원과 함께 해석한다. 풀 증설의 효과와 스케일아웃 시 총 연결 예산은 이번 실험 범위 밖이다.

무결성은 이 디렉터리에서 `shasum -a 256 -c SHA256SUMS`로 확인할 수 있다.
