# 위시리스트 이름·찜 상태 반복 조회 제거

대상은 위시리스트 상세 제목과 저장 변경 후 찜 상태 확인이다. 프론트는
`codex/editable-booking-review` 작업트리에 적용했다.

## 상세 이름은 기존 상세 응답에서 반환

프론트는 상세 제목을 찾으려고 일반 위시리스트 목록을 조회하고, 해당 이름이
없으면 다음 페이지들을 순회했다. 백엔드 상세 서비스는 이미 위시리스트 소유권을
검사하면서 이름이 포함된 행을 읽고 있었다.

`GET /api/v1/members/wishlists/accommodations/{wishlistId}` 응답에
`wishlist_name`을 추가하고 그 값을 재사용한다. 빈 위시리스트에도 이름을 반환한다.
프론트 상세 화면은 첫 상세 페이지의 이름을 사용하며, 제목을 위한 목록 조회와
목록 다음 페이지 탐색을 제거했다. 상세 조회 실패 시에도 상세 요청만 재시도한다.

상세 서비스의 소유권 조회와 항목 페이지 조회는 두 SELECT로 유지한다.
소유권 검사에는 타인 접근과 삭제·미존재 구분이 필요하고, 항목 조회에는 공개 숙소
필터와 커서 페이지 경계가 필요하다. 항목 조회 결과가 없어도 이름을 보여야 하므로
단순한 항목 JOIN 하나로 대체하지 않았다. 이름 추가에 따른 SQL 증가는 없다.

## 찜 여부는 작은 상태 응답으로 조회

기존 저장 흐름은 숙소 ID를 붙인 일반 위시리스트 목록을 마지막 페이지까지 읽고
`id`와 `is_contained`만 사용했다. 이 과정에서 이름·썸네일·개수도 함께 조회했다.

`GET /api/v1/members/wishlists/membership?accommodationId=31`을 추가했다.
선택적으로 `wishlistId`를 주면 재시도 대상 위시리스트도 확인한다.

| 필드 | 의미 |
| --- | --- |
| `is_in_any_wishlist` | 본인 활성 위시리스트 중 하나 이상에 저장되어 있는가 |
| `target_wishlist_found` | 지정한 대상이 본인 활성 위시리스트인가 |
| `target_wishlist_contains` | 해당 대상에 저장되어 있는가. 대상 생략·미존재·타인 소유·삭제 시 null |

한 SELECT의 세 EXISTS 식으로 응답을 만들며 엔티티를 로딩하지 않는다. 같은 SQL
스냅샷에서 전체 저장 여부와 대상 상태를 확인한다. 회원 ID는 세션에서 가져오며,
요청 파라미터로 다른 회원을 지정할 수 없다.

찜 상태는 저장 관계를 뜻한다. 상세 카드 조회의 공개 숙소 필터를 여기에는 붙이지
않았다. 비공개 숙소라도 본인 활성 위시리스트에 저장된 관계는 기존 목록 API와
동일하게 반영한다. 삭제된 위시리스트의 잔여 관계와 타인의 관계는 제외한다.

프론트는 저장·해제 후 상태 확인을 이 조회 한 번으로 대체했다. 생성 성공 후 숙소
추가 응답을 놓쳤을 때는 대상 위시리스트의 실제 저장 여부를 확인해 중복 추가를
피한다. 다른 목록의 찜 여부를 대상의 추가 성공으로 오인하지 않는다. 대상이
삭제되었다면 기존 재시도 흐름대로 다시 생성한다. 계정 전환·요청 취소·늦은 응답
차단과 숙소별 변경 직렬화는 유지한다.

일반 목록과 저장 대상 선택 모달은 이름·개수·썸네일·삭제용 연결 ID를 실제로 쓴다.
이 화면들의 커서 페이지 조회와 화면 갱신은 유지한다. 이번 변경은 그 목록을
찜 상태 확인용으로 추가 순회하던 부분만 제거한다.

## 측정과 검증

MySQL Testcontainers 통합 테스트에서 Hibernate 통계를 초기화하고 서비스의
SELECT 수를 비교했다. 본인 활성 위시리스트 46개 중 45개에 같은 숙소를 저장하고
대표 숙소로 지정했으며, 페이지 크기는 20이다.

| 조회 | 기존 | 변경 후 |
| --- | --- | --- |
| 찜 상태 확인 | 일반 목록 3페이지, SELECT 9회 | 상태 응답 1회, SELECT 1회, 엔티티 로딩 0건 |
| 상세 조회 자체 | 소유권 + 항목 SELECT 2회 | 이름 포함 후에도 SELECT 2회 |
| 상세 직접 진입의 프론트 요청 | 상세 + 제목을 찾는 일반 목록 페이지들 | 상세 1회, 일반 목록 0회 |

9→1은 위 데이터와 페이지 조건에서 측정한 SQL 수다. 일반 목록의 페이지 수와
대표 숙소 유무에 따라 기존 SQL 수는 달라진다. 전체 클릭의 요청 수에는 선택 모달
갱신도 포함되므로, 모든 요청이 한 번으로 줄었다는 의미는 아니다. 대규모 지연 시간,
처리량, 실행계획이나 인덱스 효과는 이번 측정으로 주장하지 않는다.

- 백엔드: `./gradlew test --tests '*WishlistMembershipApiTest' --tests '*WishlistDetailQueryIntegrationTest'`
  — 실제 MySQL 조회 12개와 세션·HTTP 계약 3개. 타인·삭제·빈 목록, 비공개 숙소,
  마지막 찜 해제, 커서 경계와 JSON 계약을 검증한다.
- 프론트: `npm run test:ci -- src/features/wishlist src/screens/wishlist src/workflows/wishlist-membership`
  — 20개 파일, 132개 통과. 응답 검증, 부분 성공 재시도, 중복 방지, 늦은 응답,
  캐시 갱신, 상세 제목과 재시도를 포함한다.
- 브라우저: `npm run test:e2e:characterization -- wishlist-characterization.spec.ts auth-session-characterization.spec.ts`
  — 17개 통과. 검색 화면의 찜 흐름, 계정 전환, 직접 상세 진입과 빈 목록, 브라우저
  이동을 포함한다. 실제 서버 연결 대신 모의 HTTP 응답을 사용한다.
- 운영·테스트·E2E TypeScript, 운영·E2E ESLint와 변경 파일 Prettier 검사를 통과했다.
- 상세와 찜 상태 JSON fixture는 백엔드와 프론트에서 동일한 내용을 사용한다.

프론트는 새 조회 경로와 이름 필드를 사용하므로 백엔드를 먼저 배포해야 한다.
이 단계는 F16의 반복 조회 개선이며, 전체 비-ES 조회 및 인덱스 튜닝 완료를 뜻하지 않는다.
