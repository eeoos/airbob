# 게스트 예약 상세 조회 개선

## 프론트 소비와 변경 판단

대상은 `GET /api/v1/profile/guest/reservations/{uid}`다. 프론트 작업트리
`codex/editable-booking-review`에서 원격 main을 가져왔고, `origin/main`의 `f80bc095`는
이미 작업트리에 포함되어 있었다.

`reservationReadMappers.ts`, `reservationDetailViewModel.ts`, `GuestReservationDetailScreen.tsx`,
`ReservationConfirmRoute.tsx`와 결제 복구 코드를 대조했다.

| 데이터 | 실제 사용과 결정 |
| --- | --- |
| 예약 UID·코드·인원·현지 날짜 및 시각 | 상세 표시, 숙소·후기 화면 이동, 예약 식별에 사용하므로 유지 |
| 예약 상태·결제 가능 여부·hold 만료 시각·서버 시각 | 상세 응답 검증 및 `acknowledgeReservationStatusDrift`의 복구 판단에 사용하므로 유지 |
| 후기 작성 가능 여부 | 상세 버튼과 후기 작성 진입에서 서버 판정을 사용하므로 유지 |
| 숙소 이름·이미지·주소·좌표·호스트 이름 및 이미지 | 상세 표시와 지도에 사용하므로 유지 |
| 결제수단·최초 결제금액·결제 상태·승인 시각 | 결제 정보 영역이 사용하는 네 필드이므로 유지 |
| 결제 주문번호·잔액·요청 시각·취소 이력 | 프론트 mapper와 모델에만 남아 있고 화면·복구에서 읽지 않아 게스트 상세의 결제 DTO에서 제거 |
| 결제 키 | 프론트 상세 mapper가 이미 버리고 있었다. 게스트 상세에서 제거 |

결제 복구의 order ID와 payment key는 attempt·callback·operation 계약에서 가져온다.
이 변경은 그 계약이나 결제 명령을 수정하지 않는다.

`PaymentResponse.GuestPaymentInfo`를 분리해 게스트 상세만 축소했다.
독립된 `/payments/{paymentKey}`, `/payments/orders/{orderId}`의 `PaymentInfo`는
소유권 검증과 전체 취소 내역을 계속 제공한다. DB의 취소·실패·과거 발급 원장도 유지한다.
본 응답에서 사용하지 않는 내역 때문에 원장을 읽을 필요가 없다는 판단이다.

`request_message`는 현재 상세 mapper가 버리고, `created_at`, `address.postal_code`, `host.id`는
모델에 보존되지만 상세 화면에서 직접 표시하지 않는다. 이 단계에서는 비결제 응답 구조를
유지하고 반복 조회와 전체 엔티티 적재 제거에 범위를 두었다. 모든 응답 필드가 화면 표시용이라는 뜻은 아니다.

프론트에서 `PARTIAL_CANCELED`가 코드 그대로 표시되던 부분도 “부분 취소”로 정렬했다.
표시 금액은 기존과 같이 최초 결제금액이며 잔액이나 환불액으로 바꾸지 않았다.

## 단건 조회 통합과 분리 유지

예약·숙소·주소·호스트·결제를 `GuestReservationDetailProjection`으로 함께 읽는다.
`payment.reservation_id`의 UNIQUE 제약으로 예약에 결제를 조인해도 행이 늘어나지 않는다.
결제와 주소는 없을 수 있으므로 LEFT JOIN을 유지한다. 결제 존재 여부는 payment ID로 구분하여
0원 결제와 결제 없음이 같아지지 않도록 했다.

후기 존재 확인은 다음 조건을 모두 만족할 때만 별도로 실행한다.

- 현재 숙소가 `PUBLISHED`다.
- 저장 예약 상태가 `CONFIRMED` 또는 `CANCELLATION_FAILED`다.
- 예약의 저장된 체크아웃 시각이 서버 시각 이하이다.

그때만 해당 숙소에 본인이 게시한 후기가 있는지 확인한다. 여러 건일 수 있는 후기를
상세 JOIN에 붙이지 않고 기존 존재 확인을 유지한다. 숨김·삭제 후기와 다른 회원의 후기는
본인의 새 후기 작성을 막지 않는다.

32개 SELECT 컬럼에는 직접 응답하지 않는 예약 금액·만료 시각·숙소 상태·payment ID도 포함된다.
결제 가능 여부, 실제 만료 상태, 후기 권한, 결제 존재 여부를 계산하는 데 필요하다.
기존 `Reservation.effectiveStatus`와 공유한 `isPaymentAllowedAt` 계산을 사용한다.

## 측정

MySQL 8.4.11 Testcontainers에서 변경 전 `f203c0b9` 기준 구현과 같은 데이터를 사용했다.
각 서비스 호출 전에 영속성 컨텍스트와 Hibernate 통계를 초기화했다.

| 조건 | 이전 SQL 수 | 이후 SQL 수 |
| --- | ---: | ---: |
| 결제 없음, 후기 확인 불필요 | 2 | 1 |
| 결제 있음, 후기 확인 불필요 | 3 | 1 |
| 결제 없음, 후기 존재 확인 필요 | 3 | 2 |

후기 존재 확인이 필요한 경우에는 결제 유무와 관계없이 개선 후 총 2회다.

| 상세 결제 fixture 측정 | 이전 | 이후 |
| --- | --- | --- |
| SELECT 컬럼 | 예약 등 68개 + 결제 14개 + 취소 원장 24개 | 통합 32개 |
| 엔티티 적재 | 6개 | 0개 |
| 취소 원장 조회 | 1회 | 0회 |

위 fixture는 주소·호스트·결제·부분 취소 1건이 있는 예약이다.
이전 엔티티 수는 데이터에 따라 달라진다. 인증 필터의 Redis 접근은 이 SQL 측정에 포함하지 않았다.
운영 데이터의 지연 시간·처리량 개선 비율은 측정하지 않았다.

## 보존한 동작과 검증

- 백엔드 147개 통과: 상세 조회 통합 44개, 호스트·게스트 목록 15개,
  예약 서비스·DTO·엔티티·체크인 제한·독립 결제 조회 등 88개.
- DB에서 본인·다른 회원·호스트의 소유권, 미존재 예약, 비공개 숙소, 주소·결제 없음,
  다른 예약의 결제가 섞이지 않음과 0원 결제를 검증했다.
- 만료 시각 직전·정각·직후를 마이크로초 단위로 확인했다. 응답만 만료로 계산하고
  저장 상태를 갱신하지 않으며, 결제 진행 등 다른 상태를 만료로 바꾸지 않는다.
- 실제 MySQL 후기 존재 확인으로 체크아웃 경계, 숙소 공개 여부, 예약 상태,
  본인/타인 후기 및 후기 게시·숨김·삭제 상태를 확인했다.
- DST가 끝나는 뉴욕 숙박과 숙소의 현재 시간대가 달라도 예약의 저장된 시간대로 응답한다.
- 별도 결제 조회의 전체/부분 취소 순서·금액·잔액과 원장 보존을 확인했다.
- 백엔드 직렬화와 프론트 mapper·표시 검증은 같은
  `contracts/guest-reservation-detail-payment.json` fixture를 사용한다.
- 프론트 예약·상세·결제 복구 관련 365개 통과. 부분 취소 표시 변경 후 관련 13개를 다시 확인했다.
- 브라우저 3개 통과: 축소 응답의 금액·호스트·현지 날짜·후기 버튼, 결제 승인과 해제의 탭 간 복구,
  모바일·데스크톱 상세 화면의 기존 스크린샷 비교. 제품/E2E 타입 검사와 strict/E2E lint 통과.

브라우저는 합성 API 응답을 사용하며 실행 중인 백엔드나 실제 결제사와 연결한 E2E가 아니다.
이번 변경에는 인덱스·DB 스키마·재고 및 결제 쓰기 경로·ES 검색 변경이 없다.
남은 다른 조회 검토와 운영 실행계획·지연 시간 측정은 별도다.
