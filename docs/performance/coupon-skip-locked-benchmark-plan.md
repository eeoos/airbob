# 쿠폰 발급 SKIP LOCKED 전환과 반복 성능 비교 계획

작성일: 2026-10-09

출발 코드: main `97b021bf5132124b156f32b52d987897dbbd1ff3`. 쿠폰 기준선·실험 도구 선행 커밋을 이식한 기준은 `6cef28f1`이다.

기존 조건부 UPDATE 발급과 MySQL SKIP LOCKED 발급을 로컬과 AWS에서 각각 같은 애플리케이션 이미지와 조건으로 비교한다.
공용 수량 행의 잠금 경쟁, 재고 인덱스 구조, 트랜잭션 격리 수준을 차례로 검증하고,
반복 측정으로 확인된 결과를 최종 구현 선택과 이력서 작성의 근거로 남긴다.

진행 순서는 구현과 로컬 정합성 검증, 로컬 반복 측정, AWS 반복 측정, 결과 검토와 운영 전환이다.

실험 중에는 기존 `issued_quantity`와 조건부 UPDATE 구현을 보존한다.
SKIP LOCKED 경로는 이 카운터를 재고 판단이나 갱신에 사용하지 않는다.
Redis Lua 발급 구현은 새 구현으로 교체하면서 제거한다.
대리 키를 기본 후보로 두고 같은 키에서 RR과 RC를 비교한다.
2026-10-09 추가 요청을 반영해 복합 키 RR·RC도 로컬·AWS 본 비교군에 포함한다.
키 구조 사전 비교는 보존하며, 최종 키 선택은 전체 결과로 판단한다.

## 목표와 완료 기준

- 같은 발급 계약에서 조건부 UPDATE와 SKIP LOCKED의 성공 처리량, 지연, DB 자원 사용을 비교한다.
- 초과 발급, 중복 발급, 실패한 요청의 재고 유실, 경합을 품절로 오인하는 문제를 방지한다.
- 키 구조와 격리 수준의 영향을 별도로 설명할 수 있도록 비교군을 유지한다.
- 원본 계측 자료, 실행 설정, 코드 커밋, 이미지 digest, 데이터·스키마 정보를 보존한다.
- 유효한 반복 실행과 동일한 판정 기준으로 최종 구현을 선택하고, 관측된 효과만 성능 개선으로 기술한다.

이 계획의 구현·측정 범위는 쿠폰 기능과 격리된 쿠폰 실험 환경이다.
AWS 측정 결과를 검토한 뒤 최종 운영 방식과 실험용 카운터·비교군의 정리 범위를 결정한다.
Lua 구현 제거와 준비 시각 컬럼 변경은 그때까지 미루지 않고 새 구현 도입에 포함한다.

## 확정한 정책

| 항목 | 정책 |
|---|---|
| 총수량 | 유한 수량만 지원한다. 새 쿠폰의 `total_quantity`는 필수이며 NULL을 무제한으로 해석하지 않는다. |
| 값 검증 | 총수량은 1 이상이어야 하며 수량과 기간의 유효성은 애플리케이션에서 검증한다. |
| 시작 전 증량·감량 | 모두 허용한다. 재고가 준비됐다면 증가분 unit 추가 또는 감소분 unit 삭제와 총수량 변경을 같은 트랜잭션에 반영한다. |
| 시작 후 변경 | 첫 발급 여부와 무관하게 증량·감량을 모두 금지한다. 진행 중인 캠페인을 교체하는 기능도 범위에 넣지 않는다. |
| 캠페인 폐기 | 시작 전에만 허용하며, 발급 내역이 없는지 함께 확인한다. |
| 회수와 재입고 | 완료된 발급을 회수해 unit을 다시 넣는 기능은 구현하지 않는다. |
| 사용자 수량 표시 | 사용자 응답에서 발급 건수 `issuedQuantity`를 제거하는 방향으로 정리한다. 관리자 수량은 발급 내역에서 집계한다. |
| DB 제약 | 새 CHECK 제약은 추가하지 않는다. PK, UNIQUE, FK는 유지한다. |
| 발급 완료 | 회원 쿠폰이 MySQL에 커밋된 뒤 성공을 응답한다. |
| 중복 | 1인 1매를 유지한다. 기존의 이미 발급됨 응답을 사용하며 성공 재응답으로 자동 변경하지 않는다. |
| 기존 Lua 구현 | 발급·준비·보상·조회와 실험 도구의 Lua 전용 경로를 제거한다. 조건부 UPDATE 기준선은 보존한다. |
| 기본 키 후보 | 대리 키를 우선 구현한다. 복합 키의 이점이 검증 범위에서 확인되지 않으면 대리 키를 유지한다. |
| 격리 수준 | RR을 기본 구현으로 두고 RC를 비교군으로 제공한다. |

무제한 쿠폰 생성·발급과 유한·무제한 유형 전환은 새 모델의 구현 범위에서 제외한다.
무제한은 unit 없이 회원 쿠폰만 생성하는 별도 경로로 구현할 수 있지만, 이번 목표에서는 그 분기를 유지하지 않는다.
새 수량 변경 계약은 목표 총수량을 필수로 받고 NULL·0·음수를 거부한다.
기존 nullable 컬럼과 과거 무제한 데이터의 처리는 아래 실험 스키마 보존·운영 전환 절차로 구분한다.

## 비교군과 검증 가설

| 비교군 | 실험 식별자 | 구현 | 격리 수준 | 역할 |
|---|---|---|---|---|
| A | `db` | 기존 조건부 UPDATE와 `issued_quantity` 증가 | RR | 필수 기준선 |
| B | `skip_surrogate_rr` | 대리 PK를 사용하는 unit 발급 | RR | 기본 SKIP LOCKED 후보 |
| D | `skip_surrogate_rc` | B와 같은 키·발급 흐름 | RC | 기본 격리 수준 비교군 |
| C | `skip_composite_rr` | 복합 PK를 사용하는 unit 발급 | RR | 키 구조의 본 비교군 |
| E | `skip_composite_rc` | C와 같은 키·발급 흐름 | RC | 복합 키의 격리 수준 비교군 |

- A는 컬럼 이름 변경을 반영하되 조건부 UPDATE의 의미와 실행 순서를 보존한다. 첫 DB 연산은 조건부 UPDATE이다.
- 모든 SKIP LOCKED 비교군은 검증, 재시도, 시간 기준, 응답 처리, 로깅과 계측을 동일하게 유지한다.
- D와 E는 발급 트랜잭션만 RC로 실행한다. 서버나 커넥션 풀의 전역 격리 수준을 변경하지 않는다.
- 실제 세션의 격리 수준을 확인해 실행 결과에 기록한다. 기본 설정을 RR이라고 가정한 채 측정하지 않는다.
- 같은 이미지에 해당 실험의 비교군을 모두 포함하되 부하는 한 비교군씩 준다.
- 각 실험 쿠폰은 생성 시 비교군을 고정한다. 다른 구현으로 같은 쿠폰을 발급하거나 중간에 전략을 바꾸는 요청은 거부한다.
- Lua 비교군은 제거한다. 기존 코드와 결과는 Git 이력·원본 결과로 남긴다.

실험 비교군 확인을 위한 공통 처리는 A의 업무 트랜잭션 밖에서 수행하여 첫 조건부 UPDATE 순서를 유지한다.
공통 진입 검증이나 계측 비용이 추가되면 모든 비교군에 같은 조건으로 적용하고 SQL 차이를 기록한다.

A에서 최종 선택한 방식으로의 변화는 전체 발급 모델의 개선으로 평가한다.
B와 C의 차이는 PK뿐 아니라 클러스터링, 보조 인덱스 크기와 접근 비용을 포함하므로,
처리량 변화의 원인을 잠금 개수 하나로 단정하지 않는다.

본 비교군은 A·B·D·C·E로 고정한다. B와 C의 사전 비교에서 인덱스별 잠금과 작은 반복 부하를 확인하고,
다섯 방식 모두를 같은 조건으로 반복 측정한다. 복합 키에서 잠금 항목이 줄어도 지연·DB 비용의
재현 가능한 이점이 없으면 대리 키를 유지한다. B·C로 키 구조, B·D와 C·E로 격리 수준을 각각 비교한다.
로컬 자원 한계로 판단하기 어려운 차이는 AWS에서 같은 다섯 비교군으로 재확인한다.
각 본 반복 측정의 비교군 목록을 미리 고정하고, 실험 축소 사유와 사전 비교 결과도 보존한다.
사전 비교에서 차이가 없었다는 관찰을 모든 환경에서 차이가 없다는 결론으로 확대하지 않는다.

## 실험 단계의 스키마

### coupon

할인 정책, 발급·사용 기간, 활성 상태와 기존 감사 컬럼을 유지한다.

| 컬럼 | 실험 단계 처리 |
|---|---|
| `id` | 기존 BIGINT PK 유지 |
| `total_quantity` | 실험 중 기존 INT NULL 보존. 새 생성·수량 변경과 모든 fixture는 1 이상의 필수 수량을 사용. 운영 전환 시 기존 NULL 데이터를 정리한 뒤 INT NOT NULL로 변경 |
| `issued_quantity` | 기존 컬럼과 A의 증가 쿼리를 보존. 모든 SKIP LOCKED 경로는 재고 판단·증가·집계 기준으로 사용하지 않음 |
| `stock_prepared_at` | 기존 `redis_stock_prepared_at`을 이 이름으로 변경. DATETIME(6) NULL 유지. 새 모델에서는 최초 MySQL unit 준비 완료를 나타냄 |
| `issue_strategy` | 생성 시 확정하는 불변 전략. 기본 SKIP_SURROGATE_RR, 실험 fixture에서만 다른 전략 선택. 요청 variant와 일치 검증 |
| 기간·활성·할인·감사 컬럼 | 기존 구조 유지 |

새 SKIP LOCKED 경로는 양의 총수량과 준비 완료 표시를 발급의 필수 조건으로 요구한다.
준비 완료 표시와 unit 생성은 함께 커밋되어야 한다.
기존 Redis 준비 시각 값을 그대로 MySQL unit 준비 완료로 간주하지 않는다.

Java 필드도 `redisStockPreparedAt`에서 `stockPreparedAt`으로 변경하고 준비 상태 메서드·JPQL·DTO·테스트를 함께 맞춘다.
A의 기존 `redis_stock_prepared_at IS NULL` 조건은 `stock_prepared_at IS NULL`로 바꾼다.
A의 쿠폰은 unit 준비를 하지 않아 NULL을 유지하고, SKIP LOCKED 쿠폰은 준비 완료 후 값을 갖는다.
전략 혼용 차단은 별도의 비교군 검증으로도 보장하며 준비 시각만으로 전략을 추론하지 않는다.

이름 변경만으로 기존 Redis 준비 이력이 MySQL 준비 이력으로 바뀌지는 않는다.
실험용 새 쿠폰은 NULL에서 시작해 unit 생성과 준비 시각을 같은 트랜잭션에 기록한다.
기존 Redis 준비 행이 있는 DB는 별도 전환 절차가 끝나기 전 새 발급 경로를 열지 않는다.
기존 값은 전환 기록으로 보존하고, 대상 캠페인의 이관·종료 여부를 확인한 뒤 새 마커를 정리한다.
진행 중인 캠페인을 이름 변경만으로 준비 완료 처리하거나 새 unit을 다시 채우지 않는다.

실험 중 총수량 컬럼의 nullable 속성을 보존하는 것은 기존 기준선과 과거 데이터의 호환성을 위한 과도기 처리이다.
새 모델에서 무제한을 지원한다는 뜻은 아니며, NULL 수량의 기존 쿠폰을 SKIP LOCKED 경로로 발급하지 않는다.
최종 NOT NULL 전환 전에 기존 NULL 행과 발급 내역을 확인하고 이관·보존 방식을 확정한다.
임의의 총수량으로 일괄 치환하거나 기존 발급 내역을 삭제하지 않는다. 양수 검증용 CHECK는 추가하지 않는다.

### 재고 테이블

B와 D에는 기본 테이블을 사용한다.

```sql
CREATE TABLE coupon_issue_unit (
    id BIGINT NOT NULL AUTO_INCREMENT,
    coupon_id BIGINT NOT NULL,
    unit_no INT NOT NULL,
    PRIMARY KEY (id),
    UNIQUE KEY uk_coupon_issue_unit_coupon_unit (coupon_id, unit_no),
    CONSTRAINT fk_coupon_issue_unit_coupon
        FOREIGN KEY (coupon_id) REFERENCES coupon (id)
) ENGINE = InnoDB;
```

C와 E의 비교에는 별도 테이블을 사용한다.

```sql
CREATE TABLE coupon_issue_unit_composite (
    coupon_id BIGINT NOT NULL,
    unit_no INT NOT NULL,
    PRIMARY KEY (coupon_id, unit_no),
    CONSTRAINT fk_coupon_issue_unit_composite_coupon
        FOREIGN KEY (coupon_id) REFERENCES coupon (id)
) ENGINE = InnoDB;
```

두 방식 모두 `coupon_id` 조건과 `unit_no` 정렬을 지원하는 인덱스를 갖춘다.
대리 키 버전의 필요한 인덱스를 생략한 비교는 하지 않는다.
FK 조건도 동일하게 유지한다. 각 테이블의 기존 인덱스가 `coupon_id`를 선두 컬럼으로 가지므로 FK용 별도 인덱스를 중복 생성하지 않는다.
[MySQL FK 인덱스 요건](https://dev.mysql.com/doc/refman/8.0/en/create-table-foreign-keys.html)

unit은 미발급 재고 한 장을 뜻한다. 발급되면 해당 행을 삭제한다.
소유 회원, 사용 상태, 개별 unit의 감사 컬럼은 추가하지 않으며 `BaseEntity`도 상속하지 않는다.
수량 N을 준비할 때 번호 1부터 N까지 생성한다.

### member_coupon

기존 `id`, `member_id`, `coupon_id`, `used`, `used_at`, `reservation_id`와 감사 컬럼을 유지한다.
`UNIQUE(member_id, coupon_id)`, `INDEX(coupon_id)`와 기존 회원·쿠폰 FK도 유지한다.

소비한 `unit_no`를 회원 쿠폰에 저장하거나 삭제되는 unit을 참조하는 FK를 추가하지 않는다.
재고 삭제와 회원 쿠폰 생성의 원자성으로 발급 수량을 보장한다.
예약 취소로 회원 쿠폰의 사용 상태를 복원하는 기존 기능은 unit을 재입고하지 않는다.

새 테이블 도입과 준비 컬럼 이름 변경은 V28 이후의 추가 마이그레이션으로 적용한다.
기존 V1부터 V28까지의 마이그레이션을 수정하지 않는다.

## Redis Lua 제거와 전환

새 발급·준비 경로가 연결되고 대응 테스트가 통과하는 구현 단계에서 쿠폰 Lua 경로를 제거한다.
AWS 비교를 위해 보존할 대상은 조건부 UPDATE와 `issued_quantity`이다.

| 영역 | 변경 범위 |
|---|---|
| 발급·보상 | CouponLuaIssueService, CouponRedisStockManager, Redis 전용 결과 타입, Lua 승인 후 영속화·카운터 증가 경로 제거 |
| 스크립트 | `coupon_prepare.lua`, `coupon_issue.lua`, `coupon_compensate.lua` 제거 |
| 준비·관리·조회 | MySQL unit 준비·수량 변경과 준비 시각 조회로 변경. 캠페인 조회의 Redis 시각 의존도 제거하고 시간대 계약 유지 |
| 사용자 API | CouponController를 새 발급 서비스로 연결. 기본 후보는 대리 키 RR이며 최종 방식은 실험 결과로 결정 |
| 전환 가드 | Lua-only 배포용 CouponLegacyIssuanceRolloutGuard와 전용 쿼리 제거. 실제 기존 데이터의 전환 완료 확인으로 대체 |
| 실험·계측 | fixture·variant 허용 목록·k6·준비 스크립트·Lua 전용 지표와 대시보드·문서에서 Lua 의존 제거 |
| 테스트 | Lua 전용 테스트를 정리하고 기존 발급 계약·롤백 보장은 MySQL 테스트로 유지 |

쿠폰 재고용 Redis 의존만 제거하며 세션·캐시 등 다른 Redis 용도는 유지한다.
구현에 맞춰 AGENTS.md의 쿠폰 재고 설명과 배포 문서도 수정한다.
코드 교체와 기존 데이터가 있는 환경의 배포는 구분한다. 기존 Lua writer와 진행 중인 발급·보상 처리를 종료한 뒤 컬럼을 변경한다.
기존 Redis 준비값·회원 쿠폰·캠페인 상태를 확인해 전환을 마치고 새 writer를 시작한다.
사용 중인 기존 캠페인은 자동 재준비하거나 카운터와 unit을 동시에 재고 원장으로 사용하지 않는다.

## 관리 기능

아래 unit 관리 절차는 모든 SKIP LOCKED 비교군과 최종 발급 경로에 적용한다.
A는 unit을 생성하지 않고 기존 카운터 기반 발급 조건을 사용한다.

### 최초 재고 준비

1. 쿠폰 행을 FOR UPDATE로 잠근다.
2. 잠금 획득 후 시작 전·활성·미준비·발급 내역 없음과 양의 총수량을 검증한다.
3. 총수량만큼 해당 비교군의 unit을 생성한다.
4. `stock_prepared_at`을 기록하고 함께 커밋한다.
5. 준비 실패는 전체 롤백한다. 준비 완료 후 재호출로 소비된 unit을 재생성하지 않는다.

실험용 초기 데이터 생성도 준비 완료 전에 발급 가능 상태를 노출하지 않는다.

### 시작 전 수량 변경과 폐기

증량·감량은 증감할 장수 대신 목표 총수량을 입력받는 방식으로 설계한다.
쿠폰 행을 FOR UPDATE로 잠근 뒤 저장된 시작 시각과 DB 시각으로 허용 여부를 판단한다.
목표 M은 1 이상이어야 하며 발급 내역이 없어야 한다.

| 상태 | 현재 N에서 목표 M으로 변경 |
|---|---|
| 재고 미준비 | 증량·감량 모두 총수량만 변경하고 이후 1부터 M까지 준비 |
| 준비 완료, M > N | N+1부터 M까지 unit 추가와 총수량 변경을 함께 커밋 |
| 준비 완료, M < N | 해당 쿠폰의 `unit_no > M`인 unit 삭제와 총수량 변경을 함께 커밋 |
| 같은 목표 수량, M = N | unit 변경 없이 처리 |
| 발급 시작 후 | 발급자가 없어도 증량·감량 모두 거절 |

감량 시 임의의 unit을 지우지 않고 번호가 큰 구간을 삭제해 남은 번호를 1부터 M까지 유지한다.
준비된 재고를 N장에서 M장으로 줄였다면 삭제 건수는 N-M이어야 한다.
예를 들어 100장에서 70장으로 줄이면 71~100번을 삭제하고, 다시 90장으로 늘리면 71~90번을 추가한다.
쿠폰 조건으로 삭제 범위를 한정하고, 기대한 변경 건수와 다르거나 수량 변경·unit 추가·삭제 중 하나라도 실패하면 모두 롤백한다.
이미 준비된 재고를 감량하더라도 `stock_prepared_at`은 유지한다.
시작한 캠페인의 시작 시각을 뒤로 옮겨 제한을 우회하지 못하도록 관리 규칙을 일관되게 적용한다.

폐기는 같은 쿠폰 행을 먼저 잠근 뒤 시작 전이며 발급 내역이 없는지 검증한다.
캠페인을 폐기하고 미발급 unit을 정리한다.
준비·증량·감량·폐기는 모두 쿠폰 행을 먼저 잠그도록 순서를 맞춘다.
같은 쿠폰의 발급은 이 행의 공유 잠금을 먼저 획득하므로 관리 변경과 동시에 재고를 소비하지 않는다.

## 발급 트랜잭션

### 재고 소비와 회원 쿠폰 생성

모든 SKIP LOCKED 비교군은 아래 순서로 처리한다.

1. 쿠폰 설정을 FOR SHARE NOWAIT로 읽고 준비·활성·발급 기간을 검증한다.
2. 회원의 기존 발급 내역을 일반 조회한다. 있으면 이미 발급됨으로 처리한다.
3. FOR UPDATE SKIP LOCKED로 잠기지 않은 unit 한 개를 확보한다.
4. 확보한 unit을 PK로 삭제한다.
5. `member_coupon`을 INSERT한다.
6. 같은 트랜잭션으로 커밋하고 성공을 응답한다.

B와 D의 재고 확보 쿼리는 다음과 같다.

```sql
SELECT id, unit_no
FROM coupon_issue_unit
WHERE coupon_id = :couponId
ORDER BY unit_no
LIMIT 1
FOR UPDATE SKIP LOCKED;
```

B와 D는 확보한 `id`로 삭제한다.
C와 E는 `coupon_issue_unit_composite`에서 같은 조건·정렬로 `unit_no`를 확보한 뒤 `(coupon_id, unit_no)`로 삭제한다.
재고 SQL과 회원 쿠폰 저장이 동일한 DataSource와 트랜잭션에 참여하는지 롤백 테스트로 확인한다.
JPA의 SQL 실행 시점까지 확인하여 의도한 잠금 순서가 실제 실행에서도 유지되게 한다.

쿠폰의 공유 잠금은 발급 요청끼리 함께 획득할 수 있다.
관리 작업과의 경계를 보호하되 발급 경로에서는 쿠폰 행을 배타 잠금으로 전환하는 카운터 갱신을 하지 않는다.
A에는 이 공유 잠금 단계를 공통 전처리로 추가하지 않는다.

### 빈 조회와 재시도

SKIP LOCKED의 빈 결과는 잠금 경합으로도 발생하므로 즉시 품절로 바꾸지 않는다.
발급 트랜잭션을 끝내고, 쓰기 서버의 새 스냅샷에서 상태를 다시 확인한다.

| 재확인 결과 | 처리 |
|---|---|
| 해당 회원의 발급 내역 존재 | 이미 발급됨 |
| 캠페인 미준비·폐기·기간 종료 등 | 해당 비즈니스 거절 |
| 유효한 유한 캠페인의 미발급 unit이 없음 | 품절 |
| 미발급 unit이 남아 있음 | 제한적 재시도 |
| 재시도 종료 후에도 미발급 unit이 남아 있음 | 재시도 가능한 일시적 실패 |

진행 중인 유한 캠페인에서는 커밋된 unit 수가 감소만 하므로 새 스냅샷의 재고 없음으로 품절을 판정할 수 있다.
미커밋 DELETE는 일반 조회에 아직 커밋된 삭제로 보이지 않는다.
RR의 일반 조회는 기존 스냅샷을 반복해서 볼 수 있으므로 재확인 트랜잭션을 새로 시작한다.
[MySQL 일관 읽기](https://dev.mysql.com/doc/refman/8.0/en/innodb-consistent-read.html)

재시도 조정 서비스에는 전체 요청을 감싸는 트랜잭션을 두지 않는다.
각 시도는 별도 서비스의 트랜잭션 경계나 TransactionTemplate으로 새로 시작한다.
대기는 커넥션과 잠금을 반납한 뒤 수행한다.
초기 구현안은 최초 시도 포함 최대 3회와 전체 시간 예산을 함께 둔다.
시간·간격은 로컬 검증과 탐색에서 정하고, 로컬 반복 측정 및 AWS 반복 측정에서는 각각 고정한 설정으로 모든 비교군을 실행한다.

### 중복과 실패

- 사전 중복 조회는 빠른 거절을 위한 것이다. 최종 보장은 `uk_member_coupon`이 담당한다.
- 유니크 충돌, 데드락, 잠금 실패 등으로 시도가 실패하면 unit 삭제를 포함해 해당 시도를 전체 롤백한다.
- 중복 키 이외의 무결성 오류를 전부 이미 발급됨으로 바꾸지 않는다.
- 데드락은 새 트랜잭션에서 제한적으로 재시도한다. 알 수 없는 모든 예외를 자동 재시도하지 않는다.
- 커밋 결과가 불명확하거나 HTTP 응답이 유실됐을 때는 기존 발급을 확인한다. 별도 INSERT로 unit을 보상하지 않는다.
- 시작 시간, 사용 시간은 기존 Asia/Seoul DATETIME 데이터와 DB 시각의 변환 계약을 확인한다. DB 서버 기본 시간대에 의존하지 않는다.

## 잠금 구조와 사전 관찰

기본 잠금 순서는 쿠폰 설정, 재고 unit, 회원 쿠폰이다.
unit의 배타 잠금은 DELETE가 아닌 SELECT FOR UPDATE 시점에 획득된다.
다른 회원의 발급 요청은 각기 다른 unit을 선택하도록 하되, FK와 유니크 인덱스 잠금도 함께 관찰한다.

InnoDB는 보조 인덱스를 통한 배타 잠금 검색에서 대응하는 클러스터드 인덱스 레코드에도 잠금을 설정한다.
따라서 B와 C에서는 재고 확보 구간의 실행 계획·잠금과 전체 트랜잭션의 잠금을 구분해 확인한다.
[MySQL SQL별 잠금](https://dev.mysql.com/doc/refman/8.0/en/innodb-locks-set.html)

대리 키에서는 `(coupon_id, unit_no)` 보조 인덱스와 PK 접근을, 복합 키에서는 PK 범위 접근을 확인한다.
SELECT 직후·DELETE 직후·회원 쿠폰 INSERT 직후를 나누어 `data_locks`의 테이블·인덱스·모드·대기 상태를 기록한다.
테이블 의도 잠금, 인덱스 레코드 잠금, gap·supremum 잠금, `SHOW ENGINE INNODB STATUS`의 lock structs 수를 구분한다.
전체 잠금 엔트리 수를 그대로 논리적 행당 잠금 수로 해석하거나, 모든 실행에서 반드시 2개에서 1개로 준다고 전제하지 않는다.
[MySQL data_locks](https://dev.mysql.com/doc/refman/8.0/en/performance-schema-data-locks-table.html)

RR에서는 복합 PK의 일부인 `coupon_id`로 검색해도 범위 잠금이 발생할 수 있다.
발급 중 재입고는 없지만 다른 캠페인 준비 INSERT와 인덱스 경계에서 충돌할 가능성은 테스트한다.
RC가 반드시 처리량을 높이거나 모든 교착 상태를 없앤다고 가정하지 않는다.
이 검증은 대리 키의 보조 인덱스 범위 검색에도 적용하고, 기본 B·D 비교에서 실제 대기·재시도 차이를 확인한다.

대화 중 MySQL 8.4.11의 축소 SQL 모델에서 확인한 내용은 다음과 같다.

| 조건 | 관찰 |
|---|---|
| 복합 PK의 쿠폰별 재고 조회 | RR에서 next-key 잠금, RC에서 REC_NOT_GAP 레코드 잠금 관찰 |
| 마지막 unit의 미커밋 삭제 | SKIP LOCKED는 빈 결과, 일반 조회에는 삭제 이전의 커밋된 재고가 보임 |
| 같은 회원의 세 INSERT 중 첫 요청 롤백 | RR과 RC 모두 ERROR 1213 데드락 재현 |
| 위 데드락의 실패 시도 롤백 후 | 재고 3장 중 회원 쿠폰 1개와 남은 unit 2개 유지 |

이 관찰은 애플리케이션 전체나 AWS 환경의 성능 결과가 아니다.
아래 통합 테스트로 재현 절차와 결과를 코드에 남기고, 실제 측정 DB 버전에서도 확인한다.

### 교착 상태 발견과 개선 기록

초기 구현은 위의 짧은 발급 흐름으로 시작하고, 동시성·실패 테스트에서 실제 SQL과 잠금 획득 순서를 관찰한다.
추가 잠금이나 직렬화 장치는 재현된 문제에 필요한 경우에 도입한다.
알고 있는 순서를 일부러 뒤집어 실패를 만들거나, 발생 전에 해결 사례를 확정하지 않는다.

1. 데드락이 발생하면 SQL 순서, 트랜잭션 경계, 대상 인덱스, 보유·대기 잠금과 DB 버전을 기록한다.
2. `SHOW ENGINE INNODB STATUS`와 `data_locks`·`data_lock_waits`로 순환 대기의 참여 경로를 확인하고 최소 재현 테스트를 만든다.
3. 서로 다른 경로의 잠금 순서 역전이 원인일 때 공통 순서로 통일한다. JPA 호출 순서뿐 아니라 실제 flush와 SQL 실행 순서도 확인한다.
4. 키 구조·격리 수준·부하를 고정하고 수정 전후의 데드락·재시도·최종 실패율·지연과 재고 정합성을 비교한다.
5. 재현 테스트와 반복 결과를 남기고, 확인한 경로에서 해당 순환 대기를 제거했다는 범위로 설명한다.

MySQL은 일관된 작업 순서와 짧은 트랜잭션을 권장하며 데드락 발생 시 트랜잭션 재시도도 요구한다.
[MySQL 데드락 대응](https://dev.mysql.com/doc/refman/8.0/en/innodb-deadlocks-handling.html)

같은 회원의 중복 INSERT 대기 후 선행 트랜잭션 롤백으로 생기는 데드락은 별도의 잠금 전환 문제일 수 있다.
모든 발급 요청의 테이블 접근 순서가 같아도 발생할 수 있으므로 순서 통일만으로 해결됐다고 기록하지 않는다.
이 경우에도 시도 전체 롤백과 제한적 재시도, 회원 쿠폰 중복 확인을 검증한다.
[MySQL 중복 INSERT 잠금 사례](https://dev.mysql.com/doc/refman/8.0/en/innodb-locks-set.html)

자연스러운 구현과 검증에서 순서 역전 문제가 발견되지 않으면 그 개선 항목은 생략한다.
학습을 위한 별도 오류 재현은 프로토타입 실험으로 표시하고 실제 서비스에서 발견한 장애와 구분한다.

잠금과 트랜잭션 동작은 실제 MySQL 기반 통합 테스트로 검증한다.
기존 test 프로필의 Kafka·스케줄링 격리는 유지한다.

| 시험 | 기대 결과 |
|---|---|
| N장에 서로 다른 회원의 동시 요청 | 초과 발급 없음. 종료 후 유효한 캠페인의 발급 수와 남은 unit 합이 N |
| 같은 회원의 동시 요청 | 회원 쿠폰 최대 1개. 실패 요청이 확보한 unit은 전체 롤백 |
| 마지막 unit을 잡은 요청의 지연·커밋·롤백 | 경합과 품절 구분. 롤백된 재고 재발급 가능 |
| 동일 회원 세 요청과 선행 INSERT 롤백 | 데드락이 나도 재시도 경계와 재고 정합성 유지 |
| unit 삭제 후 회원 쿠폰 저장 실패 | unit 유실과 회원 쿠폰 잔존 없음 |
| 성공 커밋 후 응답 유실과 재요청 | 추가 unit 소비와 중복 발급 없음 |
| 준비 중 실패와 준비 재호출 | 부분 준비 노출과 소진 unit 재생성 없음 |
| 준비 컬럼 변경과 과거 Redis 준비 이력 | 이름 변경만으로 새 재고를 준비 완료 처리하지 않음. A의 NULL 가드와 새 경로의 준비 검증 유지 |
| 쿠폰 Lua 제거 후 발급·관리·조회·실험 초기화 | 쿠폰 재고를 Redis에 읽고 쓰지 않으며 MySQL 경로와 기존 응답 계약 유지 |
| 시작 전 미준비 수량 변경 | 증량·감량 모두 총수량만 변경, 이후 목표 수량만큼 준비 |
| 시작 전 준비된 재고의 증량·감량·재증량 | 총수량과 unit 수 일치, 번호 1부터 목표 수량까지 유지 |
| 동시 증량·감량과 같은 목표 재요청 | 쿠폰 잠금으로 직렬화, 각 요청은 직전 커밋 수량에서 목표로 변경, 중복 추가·삭제 없음 |
| 수량 변경 도중 실패 또는 변경 건수 불일치 | 총수량과 unit 변경 모두 롤백 |
| 시작 경계의 증량·감량·폐기·발급 | 쿠폰 잠금으로 순서 보장, 시작 후 변경 거절 |
| 신규 생성·수량 변경의 NULL·0·음수 입력 | 애플리케이션에서 거절, unit과 쿠폰에 변경 없음 |
| 과거 NULL 수량 쿠폰의 새 발급 경로 진입 | 설정 검증에서 거절, 무제한 발급으로 우회하지 않음 |
| 다른 캠페인 발급 중 신규 재고 준비 | RR·RC의 대기와 실패를 관찰하고 처리 정책 검증 |
| 다른 비교군으로 실험 쿠폰 발급 | 요청 거부, 카운터와 unit에 커밋된 변경 없음 |

재고 수와 회원 쿠폰 수는 진행 중인 요청을 모두 종료한 뒤 일관된 스냅샷에서 검증한다.
의도적 중복·장애 테스트와 성능 측정의 고유 회원 워크로드를 분리한다.

## 계측과 결과 판정

### 지표

|---|---|
| API | 전체·성공·품절·일시적 실패 응답 수와 지연, 성공 p95와 p99 |

| 재시도 | 요청당 시도 수, 내부 재시도 사유, 최종 경합 실패와 데드락 수 |
| DB | SQL 수, 잠금 대기, CPU, 연결 상태, 관련 인덱스와 실행 계획 |
| 커넥션 풀 | 획득 대기, 사용 중·대기 중 연결 수, 점유 시간 |

상세 잠금 진단은 작은 재현 실험에서 수행한다.
처리량 측정 중 과도한 진단 조회로 특정 비교군에 추가 부하를 주지 않는다.
계측 실패가 커밋된 비즈니스 결과를 뒤집지 않도록 기존 fail-safe 계측 방식을 유지한다.

### 공통 발급 건수

현재 실험 판정은 모든 구현에서 `issued_quantity`를 기준으로 사용한다.
이를 실제 `member_coupon` 건수를 나타내는 공통 발급 건수로 변경한다.

- 고유 회원의 정상 성능 실행에서는 회원 쿠폰 수, 고유 회원 수, 성공 응답 수가 일치해야 한다.
- A에서는 추가로 `issued_quantity`와 회원 쿠폰 수가 일치해야 한다.
- 모든 SKIP LOCKED 비교군에서는 남은 unit 수와 회원 쿠폰 수의 합이 최초 재고와 같아야 한다.
- SKIP LOCKED 결과를 기존 판정에 맞추기 위해 공용 카운터를 갱신하지 않는다.
- 필요하면 결과 필드에 `legacyIssuedQuantity`와 `remainingUnitCount`를 분리한다. 적용되지 않는 값은 0으로 가장하지 않는다.

응답 유실·타임아웃은 성공으로 집계하지 않는다.
부하 생성 실패나 관측 누락과 서버의 성능 실패를 구분하고, 불리한 라운드를 제외해 개선율을 계산하지 않는다.
일시적 경합 실패를 품절로 집계하지 않는다.
초기 통과 기준은 최종 일시적 실패 0건으로 둔다.
오류 허용치를 바꾸려면 해당 환경의 본 반복 측정 전에 확정하고 모든 비교군에 동일하게 적용한다.

## 측정 시나리오와 통제 조건

### 2026-10-10 추가 실행 순서

첫 시나리오 확장에서는 커넥션 풀 크기 선정을 보류했다. 아래 실험은 앱 1대, Hikari maximumPoolSize/minimumIdle 10으로 고정하고,
실제 계측값도 10인지 검사한다. 풀 획득 대기·사용 시간·active/idle/pending, DB 잠금·CPU·I/O를 함께 기록한다.
결과는 이 구성에서의 처리 경계이며, 풀을 늘려도 개선되지 않는 한계나 DB 엔진 자체의 최대 성능으로 해석하지 않는다.

1. **C: 충분한 재고의 한계 탐색.** 다섯 구현에서 100/250/500/750/1,000 RPS를 20초씩 2회 탐색한다.
   본 측정의 초기 재고는 모든 단계에서 20,001개다. 반복 실패·불안정·부하 생성 누락을 구분하고 경계를 100 RPS 이내로 좁힌다.
   마지막 시험 단계만 통과한 경우 상한 미확인으로 남긴다. 이 2회 탐색은 최종 성능 개선율 산출용 반복 실험이 아니다.
2. **B: 관측한 경계 부근의 지속 검증.** C 결과를 바탕으로 공통 요청량을 정하고, 새 쿠폰에서 더 긴 구간을 반복한다.
   각 구현에 같은 요청량·초기 재고를 적용한다. 로컬의 계정 수 한도와 세션 TTL을 지키며 실제 시간·반복 수를 실행 입력에 남긴다.
3. **A: 급증과 회복.** 같은 쿠폰에 평상시 → 급증 → 회복 초기 → 회복 후기 부하를 연속 적용한다.
   전체 요청을 감당할 재고와 구간별로 겹치지 않는 회원을 미리 준비한다. 요청 시작 구간에 따라 결과를 집계한다.
   급증 시 실패와 회복 시 통과를 별도로 남기며, 정해진 회복 구간의 통과를 정확한 회복 소요 시간으로 표현하지 않는다.
4. **재고 소진·중복·다른 캠페인 준비.** 재고 1개와 여러 개의 소진, 같은 회원의 연속 중복 요청,
   발급 중 별도 캠페인 생성·unit 준비를 비교한다. 다른 캠페인 준비는 발급과 실제로 겹쳤는지 확인한다.
   재고 1개의 성공 지연은 표본 1개이므로 성능 백분위 비교에 사용하지 않는다.

로컬 결과로 원인 가설과 실행 절차를 검증한 뒤 AWS에서 환경에 맞는 부하 구간을 다시 탐색한다.
기본 before/after 비교는 같은 풀 크기를 유지한다. 풀 증설 효과는 별도 변수로 분리한다.
면접에서는 풀 크기, 인스턴스 수, 부하 유형·지속 시간과 실제 병목 관측을 명시하고, 로컬 관측과
운영 최대 처리량을 구분한다. 후속으로 승인된 풀 10/20/30 비교는 아래 별도 실행 결과에 기록한다.

2026-10-09의 `local-20261009-204436-57ad`는 사용자의 다른 작업을 위해 중단했다.
100 RPS 조건부 UPDATE 본 측정 1회만 완료됐고 실행 상태는 incomplete다. 새 반복 자료에 합치지 않는다.
재개 실행은 시작 시 측정 스크립트 사본과 해시를 보존한다. 진행 중 스크립트 변경이 k6 실행에 반영되지 않도록 사본을 사용한다.
실행 중 30분을 넘긴 세션은 측정 밖에서 다시 로그인하고 관리자 세션도 갱신한다.
추가 로컬 탐색의 2라운드는 아래 회전 순서의 앞 두 라운드를 사용한다. 다섯 실행 위치가 모두 균형화된
최종 반복 실험으로 표현하지 않는다. 각 실행의 입력·순서·실패·무효 결과를 모두 보존한다.

| 시나리오 | 부하와 재고 | 판단 |
|---|---|---|
| capacity | 쿠폰 하나에 서로 다른 회원, 재고는 전체 발급 시도 수보다 충분히 많음 | 성공 지연과 지속 가능한 성공 처리량 |
| scarcity | 쿠폰 하나에 서로 다른 회원, 재고보다 많은 발급 시도 | 마지막 재고 경합, 실제 품절, DB 비용과 거절 응답 |

모든 비교군은 유한 수량을 사용한다.
정상 발급·재고 소진 시나리오에서는 계정을 한 실행 안에서 순환 재사용하지 않는다.
중복 요청 시나리오에만 정해 둔 회원 수와 연속 요청 횟수로 재사용을 허용한다.
세션 생성, 재고 준비, 데이터 검증과 워밍업은 본 측정 밖에서 수행한다.

현재 예제의 p95 500ms·p99 1000ms와 180초 측정은 초기 검토값으로 사용한다.
RPS, 재고, 측정 시간, 워밍업, 재시도 예산과 판정 기준은 탐색 실행과 본 반복 측정을 구분해 고정한다.
로컬에서 탐색한 RPS를 AWS의 처리 한계로 간주하지 않는다. AWS에서도 본 측정 전에 해당 자원에 맞는 부하 구간을 정한다.
CloudWatch CPU는 실제 측정 구간의 완전한 버킷으로 비교하고, 짧은 실행의 누락 값을 0으로 채우지 않는다.

반복 순서의 편향을 줄이기 위해 각 RPS에서 비교군 순서를 균형 있게 바꾼다.
A·B·D·C·E의 다섯 라운드 순서는 다음과 같다. 실행 전 반복 횟수와 순서를 확정한다.

| 라운드 | 실행 순서 |
|---|---|
| 1 | A → B → D → C → E |
| 2 | B → D → C → E → A |
| 3 | D → C → E → A → B |
| 4 | C → E → A → B → D |
| 5 | E → A → B → D → C |

5라운드에서 각 비교군이 모든 실행 위치에 한 번씩 오도록 맞춘다. 앞서 수행한 A·B·D 6라운드 결과도
보존하되 새 다섯 비교군 실험과 표본을 합치지 않는다. 최종 채택 여부와 무관하게 B·C 비교 자료를 남긴다.

- 각 실행은 새 쿠폰과 정해진 초기 재고를 사용하고, 이전 실행의 요청을 모두 종료한 뒤 다음 실행을 시작한다.
- 같은 RPS에서 앱·DB·Redis 사양, 앱 수, Hikari 크기, 회원 조건, 재고, 시간과 관측 수준을 맞춘다.
- 모든 SKIP LOCKED 비교군의 SQL 조건·정렬·재시도 정책과 FK 설정을 동일하게 유지한다.
- 성공 지연과 품절 지연을 분리한다. 빠른 품절 응답으로 성공 성능이 좋아 보이지 않게 한다.
- CPU와 SQL 감소율은 같은 요청량·발급량에서 비교한다. 서로 다른 최대 RPS의 CPU를 직접 비교하지 않는다.
- 단계적으로 부하를 높여 통과·실패 경계를 좁힌다. 시험한 최고 단계만 통과했으면 최대치로 확정하지 않는다.
- 중앙값과 라운드별 변동을 함께 제시한다. 변동 범위 안의 작은 차이를 유의미한 개선으로 단정하지 않는다.
- 세션 TTL과 lab 수명에 맞춰 실행을 나누고 필요한 재인증은 측정 밖에서 수행한다.

## 로컬 검증과 반복 측정

로컬 단계는 정합성 검증과 반복 성능 측정을 별도로 수행한다.

| 단계 | 목적 | 수행 범위와 완료 기준 |
|---|---|---|
| 로컬 검증 | 발급·관리 규칙과 실험 도구의 정확성 확인 | 실제 MySQL 정합성·잠금 테스트, 기본 비교군과 복합 키 후보의 소규모 실행, 응답·지표·재고 판정 확인 |
| 로컬 탐색 | 반복 측정에 사용할 부하 구간 선정 | 단계적으로 RPS를 높여 처리 경계와 부하 생성기·호스트의 한계를 확인하고 로컬 실행 설정 고정 |
| 로컬 반복 측정 | 동일 조건에서 재현성과 변동 확인 | capacity·scarcity를 A·B·D·C·E로 반복하고 각 실행의 지연·성공 처리량·DB·풀 지표·정합성을 보존 |

로컬 반복 측정도 확정한 비교군에 맞는 균형 있는 순서를 사용한다.
한 번의 빠른 실행으로 결론을 내리지 않으며, 각 RPS·시나리오의 비교군마다 같은 수의 라운드를 수행한다.
같은 실행기와 판정 규칙을 AWS에서도 사용해 환경 차이 외에 비교 절차가 달라지지 않게 한다.

- 애플리케이션·DB 버전, 앱 수, JVM·Hikari 설정, 컨테이너 자원 한도와 관측 수준을 고정한다.
- 매 실행에 새 쿠폰과 초기 재고를 준비한다. 준비·워밍업·본 측정에 사용한 쿠폰을 구분하고 측정 시작 재고를 검증한다.
- 로컬에서는 호스트·앱·DB·부하 생성기 CPU와 메모리, 연결 대기, k6의 요청 생성 누락을 확인한다.
- 한 장비에서 DB·앱·부하 생성기가 자원을 공유하면 그 구성을 기록한다. 로컬 CPU 지표를 CloudWatch 지표로 가장하지 않는다.
- 부하 생성 실패·관측 누락은 무효로, 서버가 지연·오류 기준을 넘긴 실행은 성능 실패로 기록한다. 두 경우를 섞거나 제외해 개선율을 만들지 않는다.
- 실행 설정과 원본·집계 결과에 `local` 환경을 명시하고 AWS 결과와 별도 보관한다.

정합성과 계측에 문제가 있으면 수정 후 영향받은 로컬 반복 측정을 다시 수행한다.
AWS 진행 기준은 정확한 결과 분류, 누락 없는 관측, 동일 조건의 반복 자료와 재현 가능한 실행 절차를 확보하는 것이다.
로컬에서 SKIP LOCKED의 성능 우위가 나오는 것을 AWS 진행 조건으로 삼지 않는다.
로컬 수치는 실행 도구 점검과 병목 가설에 활용하고, AWS 결과의 예상 개선율이나 운영 실적으로 제시하지 않는다.

## AWS 실험 준비

기존 쿠폰 실험은 V28 스키마를 검증하며 시작 시 자동 마이그레이션하지 않는다.
재고 테이블 도입과 준비 컬럼 이름 변경을 위해 실험 DB에 추가 마이그레이션을 명시적으로 적용하고,
프로필의 예상 버전, 스키마 검증, 데이터 manifest와 준비 절차를 함께 갱신한다.
V28 고정 검증을 단순히 끄는 방식으로 통과시키지 않는다.

- 기존에 봉인된 데이터·이미지·manifest를 덮어쓰지 않고 새 실험의 스키마와 원본 데이터 관계를 기록한다.
- 동일한 실험 DB 스키마에서 선택한 비교군을 실행한다. 복합 키를 비교하면 별도 테이블을 미리 준비하며 라운드 사이에 PK를 바꾸는 DDL을 실행하지 않는다.
- 기존 GitHub OIDC 발행 경로와 digest 고정을 사용한다.
- 스케줄러, Kafka 소비, 외부 쓰기와 다른 실험 부하의 격리를 유지한다.
- 실제 DB 엔진 버전, 격리 수준, 인스턴스·스토리지 사양, 앱 수, 풀 설정과 백그라운드 상태를 기록한다.
- 버스터블 자원을 사용하면 크레딧 상태도 기록해 실행 간 자원 상태 차이를 식별한다.
- 부하 생성기는 기존 격리 실험 환경을 사용한다. 공개 OCI 트래픽이나 DNS를 전환하지 않는다.
- 자격증명과 세션 값은 저장소, 보고서, 배포 번들에 넣지 않는다.
- 자원 생성·배포·이미지 발행·스키마 준비는 계측 실행기와 분리된 단계로 유지한다.
- 실험 종료와 실패 시 기존 lab의 수명·정리 절차를 따른다.

전환 전 fixture는 발급 시작 시각을 과거로 생성했다.
구현한 fixture는 준비를 완료한 뒤 DB 현재 시각보다 2초 뒤에 발급을 열고, 실행기가 시작 시각까지 기다린다.
준비가 늦었다고 시작 후 재고 추가를 허용하는 예외를 만들지 않는다.
기간이 맞지 않는 fixture는 실행하지 않고 새로 준비한다.

P0부터 P8까지는 A의 `issued_quantity`와 조건부 UPDATE 기준선을 보존한다.
Lua 경로는 P2의 새 경로 연결과 함께 제거하고, 준비 시각 컬럼도 P1에서 이름을 변경한다.
실제 운영 배포에서는 기존 writer 중단·데이터 전환 확인과 새 바이너리·스키마 적용을 하나의 전환 절차로 다룬다.
최종 키와 격리 수준은 결과 검토 후 선택하며, 그 뒤 실험 전용 비교군·카운터를 정리한다.
발급 요청을 차단·정리하지 않은 채 진행 중인 캠페인의 재고 권한을 두 구현에 동시에 맡기지 않는다.
진행 중인 기존 캠페인과 과거 무제한 쿠폰 데이터는 전환 대상 현황에 맞춰 이관·보존 방식을 확정한다.
과거 데이터 처리가 완료된 뒤 `total_quantity`를 NOT NULL로 전환한다.

## 결과 정리와 이력서 활용

주 결과는 A와 최종 선택한 구현을 같은 조건에서 비교한다.
보조 비교는 B·C의 키 구조, B·D와 C·E의 격리 수준이다. 실제 수행한 범위와 확인된 효과만 제시한다.

- 조건부 UPDATE의 잠금 대기가 실제 병목인지 확인한 근거를 남긴다.
- 복합 키는 실행 계획과 실제 잠금·인덱스 크기를 근거로 설명한다.
- 복합 키에서 실질적인 이점이 확인되지 않아 대리 키를 유지했다면 그 선택과 검증 범위를 기록한다.
- RC 효과가 없거나 작으면 RR 유지 또는 RC 미채택의 이유를 기록한다.
- 교착 상태는 실제 재현된 원인과 수정 전후 검증을 근거로 설명한다. 순서 역전이 확인되지 않았다면 잠금 순서 통일로 해결했다는 사례를 만들지 않는다.
- 처리량과 지연 개선율은 동일한 판정 조건과 명확한 기준값으로 계산한다.
- 데이터 정합성, 최종 실패율과 준비 비용을 함께 제시한다.
- 축소 SQL 재현, 로컬 부하 테스트, AWS 부하 테스트와 운영 경험을 구분한다.
- 아직 측정하지 않은 수치나 Shopify의 결과를 우리 서비스의 개선 실적으로 사용하지 않는다.

이력서에는 AWS에서 반복 확인된 가장 중요한 결과를 중심으로 쓰고,
키 구조와 격리 수준 비교는 설계 판단을 설명하는 자료로 연결한다.
세 단계 모두에서 성능 개선이 나와야 프로젝트가 완료되는 것은 아니다.

결과 묶음에는 실행 설정, 코드·이미지·스키마 식별 정보, 요청 결과,
DB·커넥션 풀 지표, 정합성 검증, 무효·실패 라운드와 채택 결론을 함께 보관한다.

## 구현 기록 (2026-10-09)

- main 97b021bf에서 refactor/coupon 작업트리를 생성했다. main에 없던 쿠폰 기준선·fixture·k6·AWS 준비의
  선행 커밋 7ffbad65, 2592c831, 0dbfd444, 7e8e68ab만 이식했다. 캐시 변경은 가져오지 않았다.
- V29는 과거 Redis 준비 이력에 대해 fail-closed로 중단한다. 명시적 이관/종료 뒤에만 새 준비를 허용한다.
- 운영 폐기는 발급 전·발급 이력 없음 확인 후 coupon과 unit을 삭제한다. 실험 종료는 이력을 남기는 비활성화다.
- 재시도는 최대 3회, 시작 후 250ms를 넘으면 추가 시도하지 않는다. 각 트랜잭션 timeout은 1초이며
  풀 획득·DB 호출을 포함한 HTTP 전체 지연의 절대 250ms 상한을 보장한다는 뜻은 아니다.
- 초기 동시성 검증에서 전략 조회 연결을 보유한 채 REQUIRES_NEW가 두 번째 연결을 요구하는 풀 고갈을 발견했다.
  전략 조회도 독립된 짧은 트랜잭션으로 끝낸 후 시도하도록 수정했다. 이는 InnoDB 교착 상태 해결 사례가 아니다.
- OSIV가 활성화된 요청의 1차 캐시에 이미 적재된 Coupon이 있으면 새 트랜잭션의 잠금 조회도 오래된 객체를 재사용하는 문제를 재현했다. 각 시도·재확인 시작 시 해당 영속성 컨텍스트를 비워 최신 정책을 읽도록 수정하고 회귀 테스트를 추가했다.
