### **트래픽 급증 대응 - ALB·ASG 자동 확장**

인기 아티스트의 전국 공연 일정이 공개될 때마다 공연장 주변 숙소를 비교하는 사용자가 급증하는 상황을 가정했습니다. 트래픽 증가 시 앱 수를 늘려 응답 품질을 유지하고, 유입 감소 시 불필요한 인스턴스 운영을 줄이고자 했습니다.

- ALB로 요청을 분산하고, CPU 목표 50% 기반 ASG 정책으로 앱 1~4대 자동 확장·축소
- 증설 직후 응답 지연을 관측해 신규 앱의 요청 비중을 점진적으로 늘리는 ALB slow start 120초 적용

**→ 6,000 RPS를 목표로 15분간 테스트한 결과, 앱 1대 고정 대비 자동 확장(2대 → 4대) 구성에서 p95 803ms → 7ms**

**→ 같은 부하에서 실제 처리량 5,727 → 6,000 RPS, 이후 유입 감소에 따라 1대로 자동 축소**

---

측정 근거: [실험 보고서](README.md). 각 구성 1회 실행 결과입니다. 비교한 15분 구간에서 고정 구성은 계속 1대였고, 자동 확장 구성은 2대로 시작해 약 4분 후 4대가 정상 상태로 관측됐습니다. 따라서 p95 7ms는 4대 고정 실행의 수치가 아니라 증설 과정을 포함한 해당 15분 전체의 수치입니다. 처리량도 동일 구간의 평균 완료 RPS입니다.

전체 자동 확장 실행은 앱 1대에서 시작했으며, 1,000 RPS 복귀 후 약 13분 10초에 다시 1대로 돌아왔습니다. 60분 실행의 HTTP·본문 실패와 k6 `dropped_iterations`는 모두 0건입니다. 마지막 206초의 ASG 관측 공백으로 앱 수의 전체 누적 시간은 비교에서 제외했으며, 요청 지표와 앞선 확장·축소 관측은 검증했습니다. 30초씩 나눈 각 구간의 p95 중 최댓값은 상세 보고서에만 남겼습니다.
