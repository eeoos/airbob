# 쿠폰 발급 AWS 측정: 실행 조건과 해석

실제 종료 범위는 지속 부하 15개와 추가 시나리오 12개다. 원래 계획과 변경 근거를 함께
남기며, 최종 수치와 선택은 README.md와 comparison.json을 기준으로 한다.

## 사용자가 조정한 최종 실행 범위

2026-10-12 한국 시간, 사용자는 실험 목적에 비해 남은 반복이 과도하다는 점을 논의한 뒤
지속 부하를 방식별 3회까지 완료하고 추가 시나리오는 대리 키 RR·RC에서 각각 1회씩만 수행하도록
선택했다. 지속 부하 본 측정 15개와 추가 시나리오 12개가 조정된 종료 범위다.

원래 계획과 이미 수행한 성공·실패 결과는 보존한다. 4·5회차, 추가 시나리오의 DB·복합 키 후보 및
두 번째 반복은 실행하지 않는다. 축소는 미실행 항목에만 적용하며, 시행한 부하·예열·SLO는 바꾸지
않는다. 범위 변경은 `user-scoped-final-plan.json`에, 후속 실행은
`focused-additional-round-1.json`에 기록한다. 아래의 5회 반복 및 5쌍 개선 기준은 원래 계획이다.
최종 결과는 실제 3회 관측으로 표현하며, 원래 5회 확인 기준이나 5쌍 개선 기준을 완료했다고
주장하지 않는다. 추가 시나리오의 1회 결과는 해당 실행의 동작과 지연 관측으로 한정한다.

## 환경

기존 캐시 실험의 AWS 자원을 재사용했다. 파생 DB를 만들지 않고 기존 MySQL을 V28에서 V30으로
올렸으며, 마이그레이션 전후 서버 UUID와 기존 28개 Flyway 이력이 같은지 검증했다.
기존 쿠폰 120개와 회원 쿠폰 1,184,867개는 보존했다. V30에서 쿠폰 업무 시간만 서울 기준 값에서
UTC로 변환했고 감사 시간은 변경하지 않았다. 기존 스냅샷과 과거 데이터셋 manifest는 수정하지 않았다.

| 항목 | 고정 조건 |
|---|---|
| 앱 | c6i.large 1대, 2 vCPU, 4 GiB |
| 앱 컨테이너 | CPU 2개, 메모리 3 GiB, G1GC, Xms/Xmx 1,536 MiB |
| 소스 | main `43edf992227af2ae628ac0d83815c56722cf34b8` |
| 이미지 | `sha256:bd5a786c730a8a86109d359df4928a68c56e7967c32811d566e55e8b681bea4d` |
| DB | 기존 RDS db.t3.small, MySQL 8.4.11, 단일 AZ, gp3 100 GiB / 3,000 IOPS |
| InnoDB | 버퍼 풀 512 MiB, `innodb_flush_log_at_trx_commit=1`, `sync_binlog=1` |
| Hikari | maximumPoolSize/minimumIdle 모두 10 |
| 발급 격리 수준 | 조건부 UPDATE는 RR, SKIP LOCKED는 후보별 RR/RC |
| 풀 기본 격리 수준 | 후보에 맞춰 RR/RC로 설정하고 실제 연결 10개를 DB에서 확인 |
| 부하 발생기 | 별도 c6i.xlarge, k6 1.5.0 |
| HTTP 경로 | 실제 로그인 세션 → HTTPS ALB → 단일 앱 → RDS |
| 인증 fixture | 합성 회원 120,001명과 관리자 1명, BCrypt cost 4는 실험 계정에만 적용 |

대량 로그인과 재고 준비는 본 측정 밖에서 실행했다. 로그인은 앱 재시작 전에 끝내고, 이미 생성한
실제 세션을 사용했다. 쿠폰 전용 프로필로 예약 재고 초기화, 스케줄러, Kafka 리스너, 검색 및 캐시
작업을 중지했다. 운영 V1 API 전체의 성능을 측정한 것이 아니라 고정 전략의 보호된 V2 비교 API다.
보호된 비교 API에서도 세션 인증, 쿠폰 검증, 트랜잭션, 실제 MySQL 저장을 수행한다.

각 후보마다 앱을 재시작한다. RC 후보의 정상 발급에서는 RR 기본 풀을 RC로 바꾸었다 되돌리는 비용을
피한다. 품절 여부 확인용 새 RR 트랜잭션은 그대로 유지하므로, RC의 품절 경로에는 격리 수준 변경과
복구가 남을 수 있다. 발급 코드는 SKIP LOCKED 경로의 TransactionTemplate과 조건부 UPDATE의
명시적 RR 트랜잭션으로 구성되어 있다.

## 원래 측정 계획과 기준

기능 확인 → 충분한 재고의 단계별 탐색 C → 경계의 지속 확인 B → 급증·회복 A와
재고 소진·중복·다른 캠페인 준비를 순서대로 실행한다. 풀 크기, 인스턴스 수, 코드, DB 설정은
후보 사이에서 바꾸지 않는다. 실험 중 이전 fixture의 이력과 남은 unit은 보존하고 캠페인만 닫는다.
따라서 누적 이력과 버퍼 상태의 영향을 완전히 제거한 실험은 아니다. 후보 순서는 회차별로 회전한다.

본 측정 기준은 성공 요청 p95 ≤ 500 ms, p99 ≤ 1,000 ms다. 충분한 재고 시나리오에서는 모든 실제
요청이 HTTP 201이어야 하고, 목표 부하 누락이 없어야 하며, 실제 HTTP 창의 성공 처리율이 목표의
99% 이상이어야 한다. 빠른 품절·중복 응답을 성공 발급 RPS에 더하지 않는다. 보내지 못한 부하,
자원 관측 누락, 부하 발생기 압력은 별도 무효 사유로 남긴다. 성능 실패와 정합성 실패를 구분한다.

남은 unit + 실제 회원 쿠폰 = 총수량, 실제 회원 쿠폰 = 고유 회원 수 = 성공 응답 수를 검증한다.
조건부 UPDATE는 카운터와 실제 회원 쿠폰 수도 비교한다. SKIP LOCKED 경로가 공유 쿠폰 카운터를
증가시키지 않았는지도 확인한다. 재고 검증과 fixture 종료가 실패한 회차는 정상 실험으로 진행하지 않는다.

지속 확인은 새 JVM마다 100 RPS 60초 워밍업 → 목표 부하 120초 워밍업 → 100 RPS 10초 워밍업
→ 목표 부하 120초 본 측정으로 구성한다. 단계 사이에는 별도 쿠폰을 사용한다. DB 기준은 125 RPS,
최종 다섯 회 반복의 네 unit 후보는 500 RPS다. 목표는 앞선 탐색과 별도로 보존한 600 RPS 지속
확인 결과를 보고, 첫 500 RPS 지속 측정을 시작하기 전에 고른 값이다. 물리적 최대치로 표현하지 않는다.
5회 모두 유효하고 기준을 통과한 경우에만 해당 부하 수준을 반복 확인했다고 표현한다.
낮은 부하 예열로 수행한 초기 C의 경계와 목표 부하 예열 후 B의 경계는 같은 절차가 아니다.
125와 500을 나누어 "최대 처리량 4배 개선"이라고 표현하지 않는다. 반복 확인한 목표 부하와
공유 행 잠금 대기의 변화가 이 실험에서 직접 뒷받침하는 결과다.

최종 키·격리 수준 비교는 같은 500 RPS와 60,001개 재고에서 수행한다. 비교하는 양쪽 모두
다섯 회 유효·통과한 결과가 있고, p95가 20% 및 5 ms 이상 낮은 쌍이 5쌍 중 4쌍 이상이며
각 쌍의 p99와 정합성이 악화되지 않은 경우에만 사전에 정한 보수적 개선 기준을 통과한다.
조건부 UPDATE와 unit의 지속 확인 부하는 서로 다르므로 절대 CPU나 전체 SQL 시간을 단순한
절감률로 비교하지 않는다.

## 워밍업 절차를 변경한 이유

처음에는 100 RPS의 낮은 부하로만 예열했다. 이때 네 unit 후보의 첫 600 RPS·120초 실행에서
초반 지연과 요청 누락을 관측했다. 한 번의 새 JVM에서 같은 대리 키 RR 실험을 두 번 연속 수행하니,
첫 실행은 p95 1,828.37 ms와 누락 876건으로 실패했지만 두 번째는 72,000건을 모두 발급했고
p95 178.90 ms, p99 356.55 ms로 통과했다.

초기 앱 CPU와 누적 컴파일 시간 증가도 관측했다. 이는 충분한 예열의 영향을 뒷받침하지만 JIT가
유일한 원인이라는 실험은 아니다. 이후 모든 후보에 같은 목표 부하 예열 절차를 추가하고 새로
5회 반복 계획을 기록했다. 기존 실패 결과와 워밍업 실패는 보존한다. 서로 다른 예열 절차의 결과를
합치지 않으며, 예열된 앱의 성능과 앱 시작 직후 성능을 같은 결과로 설명하지 않는다.

목표 부하 예열을 적용한 600 RPS 비교는 다섯 후보의 첫 회차를 모두 완료하고 보존했다.
대리 키 RC는 실제 요청 72,000건을 누락 없이 발급했지만 p95 539.28 ms로 500 ms 기준을
넘었다. 나머지 후보의 통과 결과도 함께 남겼다. 이때 네 후보가 앞선 세부 탐색에서 공통으로
통과한 더 낮은 구간인 500 RPS를 최종 반복 부하로 선택했다. 600 RPS 결과는 500 RPS 결과에
합산하지 않는다. 최종 500 RPS 다섯 회는 지연 기준 실패가 나와도 보존하며 완료하고,
유리한 결과가 나올 때까지 더 낮은 부하로 반복하는 세 번째 확인 시리즈는 자동 실행하지 않는다.

## 비교가 답하는 범위

조건부 UPDATE와 SKIP LOCKED 사이의 공용 행 잠금 대기, 주어진 풀에서의 지속 부하 처리,
unit 키·격리 수준의 차이를 관찰하는 실험이다. Redis Lua 비교군은 실행하지 않았다.
과거 Lua 코드에도 있던 공용 카운터를 제거한 Lua 구현보다 빠르다고 주장할 수 없다.
비동기 발급의 접수 RPS와 현재 동기 DB 커밋 완료 RPS도 같은 지표로 비교하지 않는다.
풀 크기 조정은 이번 고정 조건 비교가 끝난 뒤 별도 결정하며, 현재 결과로 최적 풀 크기를 정하지 않는다.

## 실행 관리 중단과 복구

최종 500 RPS 1회차 대리 키 RC의 원격 명령은 정상 종료했으나, 로컬 실행기와 실행 잠금
갱신 프로세스가 사라져 결과 다운로드와 다음 후보 진행이 중단됐다. 종료 원인은 확인되지 않았다.
원격 명령의 Success·종료 코드 0과 완료 결과를 확인하고 기존 실행 잠금을 해제한 뒤,
새 잠금 아래 결과를 회수했다. 이미 수행한 세 후보는 재실행하지 않았고 원래 계획의 남은
복합 키 RR·RC부터 이어갔다. 복구 실행기는 별도 세션으로 실행하며 원래 측정 계획·드라이버·
앱·SLO를 변경하지 않았다. 중단 및 복구 기록은 controller-exit-recovery.json과
final-suite-recovered-controller.json에 남겼다.

범위 축소 후 RR 추가 시나리오 실행 중에는 로컬 실행기가 AWS SSM 관리 API에 연결하지 못했다.
AWS의 원격 명령은 여섯 시나리오를 모두 완료하고 성공으로 종료했다. 소유한 이전 실행 잠금을
확인·해제한 뒤 결과를 회수했으며, 미실행 RC만 이어갔다. 이미 실행한 RR을 다시 측정하지 않았다.
원격 종료 근거와 복구 기록은 공개 관측 묶음의 focused-controller-network-recovery.json에 남겼다.

## 관측 범위

성공 RPS와 지연은 k6의 실제 HTTP 창을 기준으로 한다. Grafana의 쿠폰 지표는 발급 서비스 호출
범위이며 15초 간격으로 수집한다. 인증·네트워크까지 포함한 정확한 클라이언트 통계와 구분한다.
대시보드 전체 시간 범위에는 준비·워밍업·본 측정이 섞이므로 전략의 전체 시간 평균으로 우열을 정하지 않는다.

DB 관측기는 별도 읽기용 연결 1개로 2초마다 잠금 대기와 누적 카운터를, 10초마다 SQL digest와
파일 I/O를 기록한다. 본 측정 HTTP 창 안에 완전히 들어온 표본만 진단에 사용하고 경계 여백과
관측 간격을 함께 남긴다. COMMIT 서버 시간은 네트워크 시간이 아니며 그 시간만으로 fsync 등
특정 내부 대기 원인을 단정하지 않는다. 잠금 대기 0건은 잠금 획득 비용 0을 뜻하지 않는다.
요청별 SQL 수는 발급 API 경로에 기록된 Hibernate 문장 수다. JDBC 드라이버의 격리 수준 조회·변경,
준비용 JDBC batch와 같은 전체 DB 작업 수와 다르다. DB digest는 같은 DB의 누적 값이므로
다른 캠페인 준비가 겹치는 시나리오에서는 그 준비 작업도 포함될 수 있다.

RDS CPU는 실제 HTTP 창에 완전히 포함된 1분 CloudWatch 버킷만 회차별 수치로 사용한다.
20초 탐색에 온전한 1분 버킷이 없으면 회차별 RDS CPU를 산출하지 않는다. 각 후보 시작 전 RDS
크레딧과 surplus를 확인한다. 부하 발생기는 HTTP 창의 CPU 90% 미만, 가용 메모리 15% 이상을 요구한다.

결과 원본에는 실패·무효 회차도 포함한다. 비밀번호, 세션, 토큰, 실제 로그인 입력, 앱 환경 파일은
공개 결과 묶음에서 제외한다. 앱과 DB 자원을 추가하거나 커밋 내구성 설정을 낮추어 만든 수치가 아니다.

## 추가 시나리오의 원래 계획과 실제 실행

급증·회복, 1,000개 소진, 마지막 1개, 중복 요청, 품절 중 다른 캠페인 준비, 발급 중 다른 캠페인 준비를
각 후보에서 2회 수행하는 원래 계획에서, 대리 키 RR·RC에서 각각 1회 수행하는 것으로 범위를 줄였다. 이 단계는 100 RPS 60초의 후보별 예열과 각 사례 직전 100 RPS 10초
예열을 사용하며, 지속 확인의 목표 부하 예열은 적용하지 않는다. 예열 절차가 다른 시나리오의
지연 차이를 부하 모양의 효과만으로 설명하지 않는다. 같은 시나리오 안에서 후보를 비교한다.
