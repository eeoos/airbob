# 쿠폰 발급 AWS 성능 비교 결과

[현재 발급 구조와 전환 절차](../operations/coupon-issuance-operations.md) · [로컬 후보 검증](history/coupon-local-results.md) · [측정 스크립트](../../load-test/k6/coupon/MEASUREMENT.md)

원본 계측 파일·설정·검증 기록: [측정 당시 보관본](https://github.com/eeoos/airbob/tree/a10b89a1bfdc173f3f327ed4657a1df2db14d2cd/docs/performance/results/coupon-aws-2026-10-11).

현재 요구사항에서는 **대리 키와 REPEATABLE_READ를 유지한다.** 공용 카운터를 갱신하는 조건부
UPDATE의 행 잠금 병목은 SKIP LOCKED로 해소됐지만, 복합 키나 READ_COMMITTED로 바꿀 만큼
일관된 성능 이점은 관측되지 않았다. 소진·중복·다른 캠페인 준비에서도 대리 키 RR과 RC는 모두
정합성과 지연 기준을 통과했다.

측정은 2026년 10월 11~12일 한국 시간에 기존 AWS 실험 자원에서 수행했다. 앱 1대와 Hikari 풀
10개를 유지했다. 여기서 RPS는 실제 HTTPS 요청과 MySQL 커밋을 거친 발급 완료를 기준으로 한다.
품절·중복 응답은 성공 발급 RPS에 포함하지 않는다.

## 지속 부하 결과

각 후보를 120초씩 3회 측정했다. 모든 회차가 성공 요청 p95 500ms 이하, p99 1,000ms 이하,
요청 누락 0건, 실제 성공 처리율 목표의 99% 이상이라는 기준을 통과했다. 전체 본 측정에서
765,000건이 발급됐고, 재고 보존식과 회원별 중복 방지 검증도 통과했다.

| 방식 | 목표 RPS | 통과 | 성공 p95 중앙값과 범위 ms | 성공 p99 중앙값과 범위 ms |
|---|---:|---:|---:|---:|
| 조건부 UPDATE RR | 125 | 3/3 | 57.6 · 56.7~87.3 | 188.1 · 164.3~747.5 |
| 대리 키 RR | 500 | 3/3 | 56.9 · 52.2~66.7 | 161.8 · 139.9~186.4 |
| 대리 키 RC | 500 | 3/3 | 53.5 · 45.8~80.1 | 158.9 · 156.6~329.9 |
| 복합 키 RR | 500 | 3/3 | 57.3 · 53.7~63.0 | 211.5 · 210.1~214.1 |
| 복합 키 RC | 500 | 3/3 | 77.2 · 39.4~101.5 | 298.5 · 108.7~425.5 |

중앙값과 범위는 회차별 백분위 세 개를 요약한 값이다. 전체 요청을 합친 백분위가 아니다.
대리 키 RR의 실제 성공 처리율은 500.00~500.03 RPS였다.

조건부 UPDATE는 측정 내부 구간에서 회차별 행 잠금 대기 2,752건, 2,398건, 2,892건을 기록했다.
네 SKIP LOCKED 후보의 지속 측정에서는 해당 대기 증가가 모두 0이었다. 교착 상태도 관측되지
않았다. 이 수치는 2초 간격 관측의 내부 구간에 대한 누적 카운터 증분이며, 잠금 획득 자체의
비용이 없다는 뜻은 아니다.

확인한 것은 **같은 환경에서 기준 구현 125 RPS와 개선 구현 500 RPS의 반복 통과**다. 서로 다른
목표 부하를 나눠 물리적 최대 처리량이 정확히 4배라고 주장하지 않는다. 복합 키가 이론적으로
줄이는 인덱스 잠금 수와 실제 발급 경로의 성능 개선도 구분한다. 현재 데이터는 그 키 변경을
성능 개선 사례로 제시할 근거가 부족하다.

## 급증과 재고 경계

대리 키 RR과 RC에서 아래 여섯 시나리오를 각각 한 번 수행했다. 다음 p95는 성공·품절·중복을
포함한 **전체 응답** 기준이다. 재고 경계의 성공 RPS는 수량에 의해 제한되므로 용량 비교에 쓰지
않는다.

| 시나리오 | RR 응답 p95 ms | RC 응답 p95 ms | 결과 |
|---|---:|---:|---|
| 재고 1,000개 · 250 RPS · 20초 | 19.7 | 60.8 | 양쪽 모두 발급 1,000건, 품절 4,000건 |
| 마지막 1개 · 100 RPS · 20초 | 12.7 | 13.4 | 양쪽 모두 발급 1건, 품절 1,999건 |
| 100명 중복 요청 · 250 RPS · 20초 | 12.3 | 10.7 | 양쪽 모두 발급 100건, 중복 4,900건 |
| 소진 중 다른 캠페인 준비 · 250 RPS · 20초 | 30.7 | 17.0 | 발급 1,000건, 품절 4,000건 및 다른 준비 2회 완료 |
| 발급 중 다른 캠페인 준비 · 400 RPS · 60초 | 27.7 | 27.5 | 발급 24,000건 및 다른 준비 2회 완료 |

위 다섯 시나리오는 양쪽 모두 요청 누락 없이 통과했다. 다른 캠페인마다 10,000개 재고를 준비했다.
준비 소요 시간은 RR에서 약 223~267ms, RC에서 약 231~289ms였고 모두 발급 측정 구간 안에
완료됐다. 두 준비 시나리오의 내부 관측 구간에서 행 잠금 대기와 교착 상태 증가가 없었다.
따라서 현재 삽입·발급 패턴에서 gap lock 경합을 이유로 RC로 전환할 근거도 확인되지 않았다.
이는 RR에서 gap lock 자체가 발생하지 않는다는 주장은 아니다.

중복 요청 구간에서는 RR 55건, RC 63건의 행 잠금 대기가 관측됐고 교착 상태는 없었다. 지속 발급
경로에서의 대기 제거를 모든 요청 유형에 대한 대기 0건으로 확대하지 않는다. 마지막 한 개의 성공
지연은 표본 한 개이므로 성공 백분위의 우열을 비교하지 않는다.

급증은 100 RPS 10초 → 1,000 RPS 5초 → 100 RPS 5초 → 100 RPS 20초로 구성했다.

| 급증 관측 | 대리 키 RR | 대리 키 RC |
|---|---:|---:|
| 전체 실제 발급 수 | 7,102 | 6,984 |
| 발생기가 보내지 못한 요청 | 1,398 | 1,517 |
| 급증 구간 응답 p95 | 2,124.8ms | 2,129.4ms |
| 초기 회복 구간 응답 p95 | 1,670.9ms | 1,584.3ms |
| 마지막 20초 회복 구간 응답 p95 | 14.3ms | 15.8ms |

두 급증 시험은 예정 부하를 모두 전달하지 못해 유효한 1,000 RPS 비교로 인정하지 않는다.
도달한 요청은 모두 발급됐지만, 요청 누락과 지연 기준 초과가 있으므로 1,000 RPS를 감당한다고
표현할 수 없다. 마지막 회복 구간은 양쪽 모두 기준을 통과했다. 예열 절차가 지속 부하 시험과
다르므로 지속 부하와 급증 결과의 차이를 부하 모양만으로 설명하지 않는다.

## 환경과 실행 범위

| 항목 | 조건 |
|---|---|
| 앱 | c6i.large 1대 · 2 vCPU · 4 GiB |
| 앱 컨테이너 | CPU 2개 · 메모리 3 GiB · JVM 힙 1,536 MiB |
| DB | RDS db.t3.small · MySQL 8.4.11 · 단일 AZ · gp3 100 GiB / 3,000 IOPS |
| 커밋 내구성 | innodb_flush_log_at_trx_commit=1 · sync_binlog=1 |
| Hikari | maximumPoolSize와 minimumIdle 모두 10 · 후보별 기본 격리 수준 일치 |
| 부하 발생기 | 별도 c6i.xlarge · k6 1.5.0 |
| 앱 소스 | 43edf992227af2ae628ac0d83815c56722cf34b8 |
| 앱 이미지 | sha256:bd5a786c730a8a86109d359df4928a68c56e7967c32811d566e55e8b681bea4d |

기존 DB를 V30으로 올렸고 기존 쿠폰과 회원 쿠폰을 보존했다. 새 JVM마다 실제 로그인과 준비를
측정 밖에서 수행한 뒤, 100 RPS 60초 → 목표 부하 120초 → 100 RPS 10초 예열 후 본 측정에
들어갔다. 각 단계는 별도 쿠폰을 썼다. 기준 구현은 15,001개, SKIP LOCKED 지속 측정은
60,001개 재고에서 시작했다. 후보 순서를 회차별로 회전했고 과거 fixture와 남은 unit은 보존했다.

초기 한계 탐색과 예열 변경 전 실패, 목표 부하 예열을 적용한 600 RPS 첫 회차도 원본에 남겼다.
600 RPS에서는 대리 키 RC가 p95 539ms로 기준을 넘었고, 최종 반복 부하는 500 RPS로 골랐다.
서로 다른 예열 절차와 목표 부하의 결과를 하나의 통계로 합치지 않는다.

원래 다섯 회 반복과 추가 시나리오 전체 비교를 계획했지만, 사용자가 소요 시간과 실험 목적을
고려해 **지속 부하 3회와 대리 키 RR·RC 추가 시나리오 각 1회**로 줄였다. 실행하지 않은
4·5회차를 실패나 통과로 처리하지 않으며, 원래의 5회 확인·5쌍 지연 개선 기준을 충족했다고
주장하지 않는다. 실제 관측된 3회 안정성과 요구사항에 근거해 현재 기본 구성을 유지한다.

앱 재시작과 예열, 이력 누적, 단일 DB 환경의 변동이 남아 있다. 쿠폰 전용 프로필의 보호된 비교
API를 측정했으므로 다른 업무가 함께 실행되는 전체 서비스 성능이나 최적 풀 크기를 확정한
결과는 아니다. Redis Lua 비교군도 없으므로 공용 카운터를 제거한 Lua 구현보다 빠르다고
주장할 수 없다.

실행 관리가 두 번 중단됐지만 완료된 원격 측정은 재실행하지 않았다. 첫 중단 원인은 확인되지
않았고, 두 번째에는 로컬에서 AWS SSM 관리 API로 연결하지 못한 오류를 확인했다. 두 번째 중단
중에도 AWS의 RR 추가 시나리오 여섯 개는 완료됐다. 결과를 회수하고 미실행 RC만 이어갔다.
인증 갱신은 측정용 로그인에 적용했고 부하의 세션과 앱 코드는 변경하지 않았다.

## 종료 상태

소유한 부하 프로세스가 없고 DB 관측기 1개를 종료했다. 부하 발생기의 임시 hosts 두 줄을 제거해
원본과 동일하게 복원했다. ASG의 HealthCheck·ReplaceUnhealthy를 복구했고 실행 잠금 191의
해제를 확인했다. 앱은 V30·풀 10개·기본 RR로 정상이며 ALB 대상도 healthy다. AWS 자원과
로컬 Grafana 연결은 유지했다. 정기 확인 자동화는 사용자 요청대로 일시 중지 상태다.

기존 캐시 실험용 ASG 실행 템플릿은 이번 측정에서 변경하지 않았다. 향후 인스턴스를 교체하거나
캐시 실험을 다시 시작할 때는 V30 호환 시작 계약을 적용해야 한다. 이번 복구는 현재 V30 앱을
유지한 것이며 이전 바이너리로 되돌리지 않았다.

공개 묶음의 27개 본 측정과 재고 검증을 다시 계산한 결과는
[publication-verification.json](https://github.com/eeoos/airbob/blob/a10b89a1bfdc173f3f327ed4657a1df2db14d2cd/docs/performance/results/coupon-aws-2026-10-11/publication-verification.json)에 보관했다.
