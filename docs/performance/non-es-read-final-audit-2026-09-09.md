## 추가 수정 우선: 정산 상세의 같은 시점 보장

[SettlementService](../../src/main/java/kr/kro/airbob/domain/settlement/service/SettlementService.java)의
`getSettlementDetail`은 저장된 settlement를 헤더로 사용하고,
[SettlementRepository](../../src/main/java/kr/kro/airbob/domain/settlement/repository/SettlementRepository.java)의
`findLineItems`는 조회 시점의 원장을 다시 집계한다. 취소는
`DATE(COALESCE(canceled_at, created_at))`로 월에 귀속된다. PG의 취소 시각과
복구 후 DB에 반영한 시각이 다르면 이미 생성한 월 정산에 뒤늦게 포함될 수 있다.

MySQL 8.4.11에서 기존 정산 통합 테스트의 fixture·실제 서비스·저장소를 사용한
진단 2개를 실행했다. 총액 130,000원의 5월 정산을 만든 후, 취소 시각은 5월 31일이고
DB 반영 시각은 6월 1일인 2,000원 부분취소를 추가했다.

| 상태 | 지연 원장 반영 후 헤더 net | 상세 lines net 합 | 재집계 후 헤더 net |
|---|---:|---:|---:|
| PENDING | 130,000 | 128,000 | 128,000 |
| PAID | 130,000 | 128,000 | 130,000 |

진단은 불일치의 재현 여부를 검증해 2개 모두 통과했다. 문제가 수정되어 회귀 테스트가
통과했다는 뜻은 아니다. 기존 테스트는 생성 직후 합계 일치만 확인했으므로 이 경우를
잡지 못했다. 재현 방법은 [정산 재현 기록](non-es-read-final-audit-2026-09-09/settlement-late-ledger-reproduction.md)에 남겼다.

추천 방향은 **정산 헤더와 숙소별 내역을 같은 집계에서 함께 저장하고, 지급 완료 후
둘 다 고정하는 것**이다. PENDING 재집계는 둘을 같은 트랜잭션에서 갱신한다.
지연 반영분은 고정된 지급 내역을 바꾸지 않고 별도 조정 대상으로 관리해야 한다.
기존 데이터에서 당시 내역을 복원할 수 없는 경우 현재 원장으로 과거 스냅샷을
만들었다고 간주해서는 안 된다. 스냅샷·조정 정책을 구현할 때 마이그레이션과
기존 정산 처리도 함께 설계한다. 이번 감사에서는 정산 금액이나 지급 상태를 수정하지 않았다.

## 선제 수정하지 않을 후보

- **후기 이미지:** 현재 `ReviewService.findReviews`는 페이지를 먼저 확정하고 이미지 엔티티를
  IN 조회한다. 3필드(후기 ID·이미지 ID·URL) projection으로 줄일 여지는 있지만 N+1은 아니다.
  프론트는 이미지 배열 순서대로 표시하고 저장소에는 명시적인 ORDER BY가 없다.
  이미지 순서를 제품 계약으로 고정할 때 ID 보조 정렬과 검증을 함께 추가한다.
  현재 조사에서 순서 뒤바뀜을 실제 결함으로 재현하지 않았으며 전체 측정의 차단 조건은 아니다.
- **후기 정렬:** 프론트는 서버 LATEST 페이지를 받고 모달에서 불러온 후기 안의 평점순을
  제공하며 그 범위를 화면에 명시한다. 전체 후기 평점순으로 바꾸는 것은 별도 기능 변경이다.
- **결제 단독 조회:** 소유권을 포함하는 projection으로 합칠 여지는 있다. 그러나 현재 프론트는
  예약 상세와 작업 polling을 사용한다. 기존 PaymentInfo·취소 DTO를 프론트 미사용만으로 줄이지 않는다.
- **공통코드:** 그룹 미존재 오류, 비활성 그룹의 빈 응답, 활성 코드가 없는 그룹을 구별한다.
  단순 INNER JOIN 통합은 이 차이를 잃는다. 1분 TTL 캐시의 실제 미스 비용부터 측정한다.
  BE 숙소 쓰기의 `isValidCode` 소비도 있으므로 프론트 미사용은 제거 근거가 아니다.
- **관리자 목록·매출:** 소비자와 요청 범위가 확인되지 않았다. 임의 limit·빈 날짜 0 채움·
  기간 목록과 누적 요약 통합은 성능 개선과 함께 의미를 바꾸므로 현재 계약을 유지한다.
- **원장 날짜 조건:** 정산과 매출 집계의 DATE/COALESCE 조건은 실행계획 점검 후보다.
  인덱스만 추가하기 전에 귀속 시간대·월 경계·null fallback을 보존하는 반개구간 조건을
  검토한다. 지금은 비용을 측정하지 않았으므로 무조건적인 재작성 대상으로 확정하지 않는다.

## 내부 조회의 처리

| 범주 | 판단 |
|---|---|
| 예약·결제의 소유권, 중복, 원장 멱등성 확인 | 쓰기 가드로 유지. 최종 응답에 없는 필드도 명령 검증 입력이다 |
| checkout 공유 잠금, 예약→날짜 행 잠금, 실행 fence | 조회 수를 줄이기 위해 합치거나 순서를 바꾸지 않음. 별도 잠금 대기·경합 측정 |
| 예약·견적 만료 청소, PaymentOperation 복구 | bounded batch와 SKIP LOCKED 유지. 복구의 OR/COALESCE 정렬은 대용량 실행계획 후보이며 잠금 범위까지 함께 검증 |
| 재고 seed·snapshot 검증 | 누락 날짜 확인 및 소유권 모델 유지. JDBC 읽기도 측정에 포함 |
| payment/outbox health | 결제 상태 집계·resolution 집계·outbox COUNT/MIN은 운영 지표 소비. 전역 행 수 증가 시 배경 DB 비용 측정. 프론트 미사용으로 제거하지 않음 |
| 정산·일 매출 배치 | API 읽기와 별도 비용 집계. 재집계의 원장 읽기·쓰기·지연 반영까지 확인 |
| 이력, checkout replay, 관리자 역할 재검증 | 감사·멱등성·인가 계약 유지 |
| before 비교용 조회 | 개선 전 비교 기준이므로 운영 경로와 구분해 보존 |
| ES 검색·문서 rebuild용 MySQL 읽기 | 원래 요청의 제외 범위. 공유 메서드가 있으면 비 ES 호출자까지 지우지 않음 |
| 정적 호출 미발견 Repository 메서드 | 이번 필수 작업에서 제외. 별도 정리 때 테스트·공유·내부 호출 확인 후 제거 |

`PaymentOperationRepository.findRecoverableForUpdate`와 health 집계는 성능 병목으로
확정한 것이 아니다. 요청당 Hibernate 지표에 잘 드러나지 않는 후보이므로 누락하지 않고
별도 관찰 대상으로 지정했다. outbox 행 수는 전송 backlog가 아닌 보관량이다.

## 측정으로 넘어가는 순서와 종료 기준

우선순위는 실제 호출량 자료가 없는 상태의 시작 순서다. DB 총 소요시간과 요청 빈도를
수집한 뒤 순위를 조정한다. 아직 p95 개선율이나 필요한 인덱스를 단정하지 않는다.

1. **공개 숙소 상세·날짜 가용성·결제 작업 polling:** 빈번한 화면/반복 요청부터 기준 수집.
   상세는 익명/로그인, cache hit/miss를 분리하고 재고 JDBC 비용도 기록한다.
2. **목록 페이지:** 호스트 숙소·게스트/호스트 예약·찜 목록/상세·후기.
   첫/후속 페이지, 데이터가 많은 소유자, 선택 필터 유무, 같은 시각 경계를 비교한다.
   위시리스트는 일반 목록과 `accommodationId` 선택 모드를 별도 표본으로 둔다.
3. **나머지 연결 조회:** 편집 상세·예약 상세·최근 본·쿠폰·회원정보.
   최근 본은 Redis 정리 여부, 쿠폰은 시각/상태를 고정한다. 단건·빈 응답도 별도 표본이다.
4. **관리·내부 경로:** 호출량 확인 후 독립 부하로 평가한다. 정산 상세는 정확성 수정 후 비교한다.

각 표본에 응답/권한/정렬/커서 동등성, DB 쿼리 수, rows examined/sent, DB 실행시간,
실제 실행계획, 요청 p50/p95와 처리량을 함께 남긴다. 엔티티 로딩 0이나 SQL 1회만으로
성능 완료를 판정하지 않는다. 한 번에 한 후보를 적용하고 효과가 없으면 추가하지 않는다.

[기존 요청당 쿼리 지표](../query-count-monitoring.md)는 요청 스레드의 Hibernate 범위이며
JdbcTemplate·native JDBC·배경 작업은 제외한다. 가용성과 운영 지표를 이것만 보고
SQL 0/1회라고 해석하면 안 된다. MySQL Performance Schema와 실제 계획으로 보완한다.
현재 MySQL 8.4.11에서 새 기준선을 수집하며 과거 8.0 실측과 지연시간을 직접 비교하지 않는다.

[기존 MySQL 증거 도구](../../load-test/mysql/README.md)는 실행계획과 DB 통계를 수집한다.
현재 read-model 전용 k6 도구는 후기 요약·위시리스트·매출의 비교 실험용이므로 17개
화면 조회를 모두 지원한다고 가정하지 않는다. 다음 구현은 재리팩터링이 아니라
선정 경로의 요청·데이터·계측을 연결하는 측정 시나리오다. 데이터·MySQL 패치·캐시 상태·
동시성·통계를 고정하고, EXPLAIN과 데이터 준비는 지연시간 측정 구간 밖에서 수행한다.
