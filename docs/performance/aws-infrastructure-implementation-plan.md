# AWS 인프라 구현 계획

상태: 사용자 승인 후 데이터셋과 독립적인 구성·승인·복원 흐름을 구현했다. 검증 결과와 남은 ETL 접점은 [작업 결과](aws-infra-workstream-2026-09-08.md)에 기록한다.

## 목표와 작업 분담

OCI는 면접관 시연을 계속 담당한다. AWS는 승인된 데이터로 성능 실험 환경을 반복 생성·삭제한다. 데이터셋 생성·ETL 리팩토링은 다른 채팅이 담당하고, 이 채팅은 AWS 구성·데이터 승인·스냅샷 재사용·운영 절차를 담당한다.

기본 흐름은 두 가지다.

```text
새 데이터 릴리스: ETL 산출물 → 최초 복원·전체 검증 → 기준 스냅샷 승인·보관
반복 성능 실험: 승인된 스냅샷 → 새 실험 환경 → 빠른 확인·워밍업 → 측정 → 삭제
```

데이터 승인과 앱 실험 준비의 완료 조건을 분리한다. DB 검증을 마친 후 앱·부하 생성기·모니터링 준비가 실패했다는 이유로 데이터를 다시 생성·검증하지 않도록 한다. ES도 데이터 릴리스에 대응하는 승인된 스냅샷으로 관리한다.

## 현재 출발점

- 최신 main `94477de9` 기반의 독립 브랜치 `codex/aws-lab-fresh-start`에 변경을 보관했다.
- S3 완료 기록 읽기 권한, private DNS 연결 관리, 앱 node-exporter 접근 규칙을 수정했다.
- RDS 모듈은 8.4 파라미터 그룹과 확장 지원 비활성화를 지원하도록 준비했다. 전체 실행 경로는 아직 8.4로 전환되지 않았다.
- foundation 모의 테스트 39개와 변경 후 lab 모의 테스트 52개가 통과했다.
- 새 데이터 생성·스냅샷 승격·AWS 적용은 수행하지 않았다. 기존 앱·ETL 작업과 별도로 진행한다.

## 1단계 — MySQL 8.4 실행 경로 정리

목적: RDS 모듈뿐 아니라 운영 입력·복원·CDC까지 같은 버전 계약을 사용한다.

- AWS lab 입력, 운영 스크립트, 준비 완료 기록, 스냅샷 승격의 MySQL 버전·파라미터 그룹 검사를 일치시킨다.
- 새 실행은 정확한 MySQL 8.4 패치를 지정하고 확장 지원을 비활성화한다. 지원하지 않는 버전은 비싼 작업을 시작하기 전에 거부한다.
- AWS용 Debezium을 8.4 지원 버전과 아티팩트 해시로 고정한다. OCI용 이미지·배포 경로와 구분해 OCI 배포를 동반 변경하지 않는다.
- 독립 Docker 네트워크와 작은 MySQL 데이터로 DB 접속, outbox 커밋 전달, 롤백 미전달, 재시작 후 전달을 확인한다. 기존 로컬 컨테이너·볼륨을 공유하지 않는다.

완료 기준: 설정·스크립트 테스트와 실제 작은 MySQL 8.4 → Debezium → Kafka 검증이 통과하고, OCI 경로의 이미지 선택이 유지된다. 사용자 데이터셋은 필요하지 않다.

## 2단계 — 최초 데이터 승인 절차 분리

목적: 데이터의 정확성을 검증하고 기준 스냅샷을 승인하는 작업을 실험 앱 기동과 분리한다.

- ETL 산출물의 출처·엔진·스키마·검증 명세를 확인한 후 최초 복원과 전체 데이터 검증을 수행하는 경로를 둔다.
- RDS와 ES 스냅샷 식별자, 정확한 엔진·스키마, 데이터 릴리스·manifest 해시, 검증 결과를 승인 기록에 묶는다.
- 승인 기록은 버전이 고정된 객체로 보관한다. 바꿀 수 있는 태그만으로 승인 여부를 판단하지 않는다.
- 앱 이미지·캐시 설정·ASG 수·부하 생성기·모니터링 준비 결과를 데이터 승인 조건에서 분리한다.
- 이미 승인된 릴리스는 새 실험 때문에 다시 승인하지 않는다. 데이터가 변경되거나 기존 승인의 신뢰 근거가 무효화되면 새 릴리스를 승인한다.

완료 기준: 작은 테스트 입력으로 승인 성공·중복 요청의 일관성·출처 불일치 거부를 검증한다. 실제 대량 데이터의 승인은 ETL 산출물 도착 후 수행한다.

## 3단계 — 반복 복원에서 전체 검증 제거

목적: 승인된 스냅샷을 재사용해 반복 준비 시간을 줄인다.

- 승인된 스냅샷의 실제 식별자와 승인 기록, 요청한 데이터 릴리스, 엔진·스키마 호환성을 대조한다.
- 스냅샷 복원 후 DB 연결, 마이그레이션 이력, 소수의 실험 대상, ES alias·복원 상태, 필요한 Redis·Kafka·CDC와 앱 상태만 확인한다.
- 전체 COUNT, 전체 행 지문, 전체 데이터 관계·집계 검사를 반복 기동 경로에서 실행하지 않는다.
- 데이터 지문이 최초 승인에서 승계된 값임을 기록해 이번 복원에서 재계산한 것처럼 표시하지 않는다.
- 앱 이미지·캐시·인스턴스 수 등 실험 변수는 실행 결과에 별도로 기록한다. 이 값이 바뀌어도 같은 승인 데이터를 재사용할 수 있게 한다.
- 워밍업은 별도 측정 준비 단계로 유지한다. 쿠폰·삭제·만료 등 쓰기 실험은 실행별 상태 준비와 변경 결과 검사를 수행한다.

완료 기준:

1. 승인 출처·내용·엔진이 다른 스냅샷은 거부한다.
2. 앱 이미지·캐시·ASG 수 변경만으로 데이터 재사용을 거부하지 않는다.
3. 반복 복원에서 전체 데이터 검사 함수가 호출되지 않는 것을 검증한다.
4. 잘못된 DB 연결·스키마·서비스 상태는 빠른 검사에서 실패한다.
5. 같은 승인 스냅샷에서 생성한 별도 실험이 각자의 실행 기록과 결과를 남긴다.

## 4단계 — 운영 절차와 관측 정리

목적: 실패 원인을 빠르게 알고 불필요한 실행 비용을 줄인다.

- 실행 전 메타데이터·권한·이미지·버전·입력을 확인해 장시간 복원 후 발견할 수 있는 오류를 앞당긴다.
- 준비 단계별 시작·종료·소요 시간과 실패 지점을 남긴다. 비밀 값이나 원본 데이터는 로그에 넣지 않는다.
- 실험 종료·실패·TTL 만료 시 정리 경로를 검사하고, 보관할 승인 스냅샷과 결과는 실험 자원 삭제 범위에서 분리한다.
- ALB·ASG·부하 생성기·지표 수집의 설정과 접근 경로를 검증한다. ASG가 새 앱을 띄울 때 데이터 제작이나 전체 검증을 실행하지 않도록 한다.

완료 기준: 모의 실패 주입과 구성 테스트에서 단계 진단·정리·보관 범위가 맞고, 기존 OCI로의 공용 접근이 기본 경로로 유지된다. 실제 AWS 통신·정리의 성공은 5단계에서 확인한다.

## 5단계 — 새 데이터와 실제 AWS 통합

이 단계는 실제 산출물이 필요하다.

- ETL 커밋, 산출물 디렉터리, MySQL·마이그레이션 버전, manifest·검증 결과를 받는다.
- 생산자 명세에 맞춰 AWS 소비자 어댑터와 실험별 준비 입력을 연결한다. 기존 v2의 고정 규모·필수 실험 목록을 새 데이터에 억지로 적용하지 않는다.
- 실제 데이터의 최초 복원·검증·스냅샷 승격을 수행한다.
- 승인된 스냅샷에서 실험 환경을 다시 만들고, 빠른 확인·워밍업·간단한 측정·삭제까지 완주한다.
- 준비 시간과 보관·실행 비용을 기록한다. 이후 동일 조건 A/A부터 시작해 사용자 지정 실험을 진행한다.

## ETL 채팅과 맞출 최소 접점

데이터 내용과 규모는 다른 채팅의 책임이다. 이 채팅에서 요구하는 것은 전달 형식과 확인 가능한 출처다.

- 정확한 MySQL 버전과 마이그레이션 이력.
- 데이터 릴리스 ID, manifest 및 파일 해시, 생성·검증 결과.
- 실제 산출물 경로와 ETL 커밋.
- 읽기 전용 데이터와 실행별 변경 데이터의 구분, 실험 계정·대상 목록.

작은 manifest 샘플이 정해지면 먼저 접점을 맞춘다. 데이터가 아직 없다는 이유로 1단계와 운영 구성 검증을 중단하지 않는다. 2–3단계의 데이터 형식에 의존하는 어댑터는 최종 명세를 받은 뒤 연결한다.

## 작업 묶음과 검토 순서

1. 기반 수정 + MySQL 8.4/CDC 호환성.
2. 최초 승인 + 반복 복원 분리.
3. 운영·관측·정리와 문서.
4. 실제 데이터 통합과 AWS 완주 증거.

각 묶음은 코드와 해당 검증 결과가 함께 검토 가능한 상태로 만든다. 실제 데이터와 AWS 통합은 새 ETL 산출물이 준비된 뒤 수행한다.
