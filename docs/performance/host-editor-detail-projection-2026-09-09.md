# 호스트 숙소 편집 상세의 기본 정보 조회 개선

## 판단과 범위

대상은 `GET /api/v1/profile/host/accommodations/{id}`다. 프론트
`codex/editable-booking-review`에서 원격 main을 가져왔고 `origin/main`의 `f80bc095`가
이미 작업트리에 포함되어 있음을 확인했다.

앞 단계에서 편집에 쓰이지 않는 후기·호스트 조회를 제거했고, 이미지·편의시설은
각각 두 컬럼으로 축소했다. 이번에는 숙소·주소·인원 정책의 전체 엔티티 조회를
`HostAccommodationDetailProjection`으로 바꿨다.

| 조회 필드 | 프론트 소비와 결정 |
| --- | --- |
| ID | 편집 대상과 저장·이미지 요청의 숙소 식별자로 유지 |
| 이름·설명·유형·가격·통화 | 모델·폼 초기화와 변경 요청에 사용하므로 유지 |
| 체크인·체크아웃 시각 | 폼 초기값, 표시 기본값 여부와 저장 변경 판단에 사용하므로 유지 |
| 시간대 | 현재 편집 mapper는 전달하지 않지만 기존 서버 메타데이터 계약으로 유지 |
| 주소 7필드 | 폼 초기값·변경 비교·주소 저장 입력에 사용하므로 유지 |
| 최대 인원·유아·반려동물 정책 | 초기값·기본값 보완·변경 저장에 사용하므로 유지 |
| 이미지 ID·URL, 편의시설 코드·수량 | 기존 별도 조회와 응답 유지 |

편집 DTO에서 사용하지 않는 좌표·대표 이미지·감사 컬럼과 연관 엔티티 식별자 등을
SELECT에서 제외했다. 프론트 제품 코드와 응답 JSON은 바꾸지 않았다.

## 유지한 조회 구조와 동작

- `accommodation.id = accommodationId AND accommodation.member_id = hostId`로 본인 숙소만 조회한다.
  호스트 엔티티를 읽지 않아도 소유권 검사는 동일하다.
- 첫 조회에서 미존재·타인 소유 숙소를 거부하고 이미지·편의시설은 읽지 않는다.
- 기존처럼 숙소 상태에 따른 추가 필터는 넣지 않는다. DRAFT·PUBLISHED·UNPUBLISHED·DELETED의
  기존 소유자 조회 결과를 모두 고정했다. 게시·수정·삭제 명령의 허용 정책을 바꾼 것은 아니다.
- 주소·정책은 LEFT JOIN을 유지한다. 없는 객체와 부분 누락 필드, 빈 문자열과 0 값을
  임의 기본값으로 치환하지 않고 기존 응답 그대로 전달한다.
- 이미지와 편의시설은 다건 관계이므로 분리한다. 이미지의 ID 오름차순과 숙소별 목록 범위를 유지한다.
- 호스트 편집 조회는 공통 공개 상세 캐시를 사용하지 않는다. 변경된 DB 값은 다음 조회에 반영한다.

## MySQL 측정

MySQL 8.4.11 Testcontainers에서 변경 전 `87b29da0` 기준 구현과 같은 데이터를 사용했다.
서비스 호출 전에 영속성 컨텍스트와 Hibernate 통계를 초기화했다.

| 항목 | 이전 | 이후 |
| --- | ---: | ---: |
| 정상 상세 SQL 횟수 | 3 | 3 |
| 기본 정보 SELECT 컬럼 | 39 | 19 |
| 편의시설 SELECT 컬럼 | 2 | 2 |
| 이미지 SELECT 컬럼 | 2 | 2 |
| 숙소·주소·정책이 있는 fixture의 엔티티 적재 | 3 | 0 |
| 주소·정책이 없는 초안의 엔티티 적재 | 1 | 0 |
| 미존재·타인 소유 조회 | 1 | 1 |

개선 후 편집 상세는 전체 경로에서 엔티티를 적재하지 않는다.
실제 운영 지연 시간이나 처리량 개선 비율은 측정하지 않았다.

## 검증

- 백엔드 44개 통과: 신규 호스트 상세 MySQL 10개, 공개 상세 MySQL 7개,
  기존 상세 조회 8개, 실제 정책 저장·수정·롤백 3개, DTO/정책 JSON 7개, 조회 서비스 9개.
- 기존 `host-accommodation-editor.json`을 변경 전부터 실제 DB 응답과 비교했고,
  변경 후에도 같은 필드와 값을 반환한다.
- 미완성 초안, 부분 정책, 0원·수량 0·빈 주소 문자열, 자정 체크인·별도 시간대,
  사진 순서, 타인·미존재 대상과 변경된 원본 재조회를 검증했다.
- 정책 저장 테스트에서 기존 정책 행 ID를 유지한 수정, 정책 생략 PATCH의 값 보존,
  롤백 후 이전 값 재조회를 확인했다. 정책 행 ID 확인용 테스트 보조 조회만 엔티티 조회로 구분했다.
- 프론트 127개 통과. 같은 공유 fixture로 폼을 초기화하면 불필요한 변경이 생성되지 않고,
  이름·상세 주소·최대 인원만 수정하면 해당 PATCH 필드만 생성되는 검증을 추가했다.
- 브라우저 4개 통과: 기존 숙소 초기화→저장→게시, 누락·부분 정책 기본값 저장,
  최대 인원 변경 시 기존 유아·반려동물 수 보존. 타입 검사와 변경 파일 lint·포맷도 통과했다.

브라우저는 합성 API 응답을 사용하며 실제 백엔드에 연결한 HTTP E2E는 아니다.
인덱스·스키마·ES 검색·예약/결제 쓰기 로직은 이번 변경 범위가 아니다.
