# 공개 숙소 상세 조회 개선

## 소비와 조회 설계 판단

대상은 `GET /api/v1/accommodations/{id}`다. 프론트 `codex/editable-booking-review`에서
원격 main을 다시 가져왔고 `origin/main`의 `f80bc095`는 이미 포함되어 있었다.

프론트의 `toAccommodationDetail`, `toAccommodationDetailViewModel`,
`toAccommodationBookingViewModel`과 예약 명령 입력을 대조했다.

| 응답 | 사용처와 결정 |
| --- | --- |
| 숙소 ID·이름·설명·유형 | 상세 제목·설명·유형 및 라우팅·요청 식별에 사용하므로 유지 |
| 가격·통화 | 예약 카드의 가격 표시와 예비 계산에 사용하므로 유지 |
| 체크인·체크아웃 시각·시간대 | 상세 시각 표시 및 숙소 모델의 시간대 계약으로 유지 |
| 주소 요약·좌표 | 위치 표시와 지도에 사용하므로 유지. 상세 도로명·상세 주소·우편번호는 기존 공개 DTO에 없음 |
| 호스트 ID·닉네임·이미지 | 호스트 표시 모델에 사용하므로 유지 |
| 인원·유아·반려동물 정책 | 표시, 인원 선택 제한과 예약 명령 입력에 사용하므로 유지 |
| 이미지 ID·URL | 사진 순서·갤러리의 식별과 표시에 사용하므로 유지 |
| 편의시설 코드·수량 | 편의시설 의미 해석과 표시에 사용하므로 유지 |
| 후기 수·평균 평점 | 후기 요약과 모달 진입에 사용하므로 유지 |
| 개인 찜 여부 | 사용자별 저장 상태이므로 공통 캐시와 분리 유지 |

프론트 제품 코드와 공개 응답 DTO는 변경하지 않았다.
주소 요약의 state·district 등 모델에 보존되는 메타데이터를 모두 직접 표시한다고 해석하지 않는다.
이번 목적은 기존 응답을 구성할 때 필요하지 않은 엔티티 컬럼을 읽지 않는 것이다.

기존 `AccommodationDetailProjection`은 숙소 엔티티 전체와 후기 요약 값을 담고 있었으며,
최근 본 숙소 조회도 사용하는 타입이다. 공개 상세용 `PublicAccommodationDetailProjection`을
추가하여 이 경로에서만 23개 컬럼을 조회하도록 바꿨다.

이미지와 편의시설은 각각 2개 컬럼의 projection으로 바꿨다.
서로 독립된 다건 관계이므로 세 조회를 유지하여 이미지 수 × 편의시설 수만큼의 중복 행이
발생하지 않도록 한다. 이미지의 `id ASC` 정렬을 유지하고 편의시설에 새로운 정렬 계약을 추가하지 않는다.
같은 목록 조립 함수를 사용하는 호스트 편집 상세도 이 두 컬럼 조회를 사용하며 응답과 소유권 검사는 유지한다.

## 캐시와 권한 보존

- 공통 `AccommodationDetailSnapshot`의 JSON 형식과 필드는 그대로다.
  캐시 키·버전·TTL·무효화·로드 조정 코드를 변경하지 않았다.
- 숙소 ID와 `PUBLISHED` 조건으로 첫 조회를 수행한다. 비공개·미존재 숙소는 기존 예외로 거부하며
  이미지·편의시설을 추가로 읽지 않는다.
- 주소·정책·후기 요약은 LEFT JOIN으로 조회한다. 데이터가 없으면 기존 null 필드 객체와
  후기 수·평점 0을 유지한다. 다른 숙소의 요약이나 자식 목록으로 대체하지 않는다.
- 후기 요약은 기존 `accommodation_review_summary` 값을 사용한다. 후기 원문을 읽거나
  실시간 COUNT/AVG로 다시 집계하지 않는다.
- 개인 찜은 로그인한 사용자의 ID로 매번 확인한다. 동일한 공통 캐시를 읽더라도
  저장한 사용자·다른 사용자·비로그인 사용자의 결과가 섞이지 않는다.
- 날짜 가용성은 별도 API와 재고 snapshot 조회를 계속 사용한다.

## 실제 측정

MySQL 8.4.11 Testcontainers에서 변경 전 `d695ebce` 기준 구현과 같은 데이터를 사용했다.
측정 전에 영속성 컨텍스트와 Hibernate 통계를 초기화했다.

| 공통 상세 읽기 | 이전 | 이후 |
| --- | ---: | ---: |
| SQL 횟수 | 3 | 3 |
| 기본 정보 SELECT 컬럼 | 52 | 23 |
| 편의시설 SELECT 컬럼 | 8 | 2 |
| 이미지 SELECT 컬럼 | 7 | 2 |
| 엔티티 적재 — 이미지 2개·편의시설 2개 fixture | 8 | 0 |

이전 8개는 숙소·주소·정책·회원 각 1개와 이미지·편의시설 각 2개다.
개선 후 공통 상세는 엔티티를 적재하지 않는다.

실제 Redis를 포함한 검증에서 비로그인 요청은 캐시 miss 3회 / hit 0회,
로그인 요청은 miss 4회 / hit 1회였다. 로그인 요청의 추가 1회는 개인 찜 확인이다.
이 수치는 인증 필터의 세션 Redis 접근을 포함하지 않으며 운영 지연 시간·처리량 개선 비율은 측정하지 않았다.

## 검증

- 변경 전부터 통과하는 공유 JSON fixture를 만들고 변경 후에도 같은 응답인지 비교했다.
- 실제 MySQL로 SELECT 컬럼 수·엔티티 적재 0, 이미지 ID 순서, 두 다건 목록의 값과 범위,
  빈 목록·누락된 주소/정책/후기 요약, 0원·좌표 0·수량 0, 변경된 원본 값 반영을 확인했다.
- 기존 공개 상세·호스트 편집·별도 가용성 조회와 상세 reader·query service 테스트를 통과했다.
- 실제 MySQL·Redis 캐시 테스트에서 이미지·편의시설을 포함한 miss/hit 응답 일치,
  사용자 간 찜 분리와 공통 캐시를 유지한 채 찜 삭제 후 결과 갱신을 확인했다.
- 기존 캐시 JSON·캐시 동작·공개 DTO 직렬화·벤치마크 서비스 테스트 41개도 통과했다.
- 프론트 상세·예약 표시 관련 223개와 제품/E2E 타입 검사, strict/E2E lint를 통과했다.
- 브라우저 3개에서 공유 DTO의 사진·편의시설·인원·후기·예약 금액,
  모바일 후기 모달·날짜 선택, 데스크톱 상세 진입을 확인했다.

프론트의 `public-accommodation-detail.json`은 백엔드의 같은 계약 fixture와 내용이 동일하다.
브라우저는 합성 응답을 사용하며 실행 중인 백엔드와 연결한 HTTP E2E는 아니다.
ES 검색·인덱스·스키마·예약 및 결제 쓰기 로직은 이번 변경 범위가 아니다.
