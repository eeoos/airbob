## 과거 공용 RR 풀 측정의 해석

격리 수준 비교 해석 보정(2026-10-10): 아래 과거 실행기는 Hikari 기본 격리 수준을 후보별로 맞추지

`SET SESSION TRANSACTION ISOLATION LEVEL` 명령을 확인했다. 아래 Hibernate SQL 수에는 이 명령이
포함되지 않는다. 따라서 아래 RC/RR 수치는 **공용 RR 기본 풀에서의 실행 결과**이며, 격리 수준
자체의 우열을 입증하지 않는다. 후보별 기본값을 맞춘 후속 실험과 합산하지 않는다.

| 풀 기본값 / 발급 격리 수준 | 요청 결과 | 격리 수준 변경·복구 SET 수 |
|---|---|---:|
| RR / RR | 100건 발급 | 0 |

전체 예정 요청 540,000건 중 보내지 못한 부하도 있다. `dropped_iterations` 합계는 64,309이며,
예정 수와 실제 HTTP 수의 차이 64,303과 6건 다른 것은 일부 실행 경계의 추가 예약 반복 때문이다.

전체 27회 중 **11회 유효, 10회 전체 기준 통과**다. 요청 누락은 9회, 호스트 CPU 기준 초과는 14회이며
7회가 겹친다. 관측 누락은 없었고 CPU 기준은 기존처럼 최대 표본 90% 미만을 유지했다.
유효한 풀 10·1,000 RPS 세 번째 회차도 지연·처리율 기준을 넘겨 실패했다.

### 통제 조건과 실행 순서

- 애플리케이션 발급 코드는 변경하지 않았다. 최신 main을 반영한 `a93b48ea89ef52460b2d5fe878b77d315e15a165`에서
  새로 빌드한 JAR SHA-256은 `e84067d904eecf5d9ab3af33cbf43f7d75ed1f25ac4e77b4eae876fed1eb1b72`다.
  한 사본을 고정해 모든 재시작에 사용했다. 이전 실험의 JAR와 다르므로 과거 812 RPS 자료와 통계를 합치지 않는다.
- 앱 1개, heap 512MiB, 같은 일회성 MySQL 8.4.11/Redis, 같은 호스트와 k6 1,000 VU를 사용했다.
  MySQL은 버퍼 풀 128MiB, `innodb_flush_log_at_trx_commit=1`, `sync_binlog=1`, binlog ON,
  `max_connections=151`을 유지했다. 프로필은 기존 로컬 실행기의 `test,coupon-benchmark`다.
- maximumPoolSize와 minimumIdle을 모두 10/20/30으로 맞췄고 실제 Hikari min/max 계측값도 검사했다.
  본 측정은 각 20초, 초기 재고 30,001개다. 30,001명의 실제 로그인 준비는 측정 밖에서 수행했다.
- 풀 순서는 10→20→30 / 20→30→10 / 30→10→20이다. RPS 순서는
  500→1,000→1,500 / 1,000→1,500→500 / 1,500→500→1,000으로 회전했다.
- 풀 차례마다 앱을 재시작하고, 매 본 측정 직전 별도 쿠폰으로 100 RPS·10초 워밍업 후 3초 기다렸다.
  로그인 준비에 사용한 첫 앱도 재시작했다. 이 짧은 워밍업이 JIT·캐시의 모든 영향을 제거한다고 보장하지 않는다.
- 같은 DB에 이전 쿠폰·발급 이력과 잔여 unit이 누적된다. 차례별 시작 행 수와 순서는 `metadata.poolCohorts`에 있다.
  실행 순서를 회전했지만 데이터 누적·실행 순서와 공유 호스트의 영향을 모두 제거한 실험은 아니다.

### 회차별 결과

값은 1/2/3라운드 순서다. `*`는 요청 누락 또는 호스트 CPU 기준 초과로 해당 실행 전체가 무효임을 뜻한다.
무효 회차의 지연 수치도 그대로 남겼으며 개선율 계산에 사용하지 않는다. 통과 횟수는 관측 유효성과
p95 ≤ 500ms, p99 ≤ 1,000ms, 처리율 ≥ 목표의 99%, 요청 누락·오류 없음의 전체 판정을 포함한다.

풀 20·30의 1,000 RPS는 각각 세 번 모두 요청 누락 없이 처리했고 응답 지연 기준도 만족했지만,
각각 두 회차가 호스트 CPU 기준을 넘었다. 따라서 전체 기준 3/3 통과로 표현하지 않는다.
풀 30·1,500 RPS의 첫 두 회차는 요청 3만 건을 모두 처리했으나 CPU 최대 표본이 95.86%/96.33%였다.
세 번째에는 요청 5,858건 누락과 p95 1,096.44ms가 발생했다. 1,500 RPS 지속 처리 능력을 확인한 결과가 아니다.

### 풀 대기와 DB 관측

아래는 1,000 RPS의 세 회차 전체에서 관측한 범위다. 무효 회차를 포함하는 진단 자료이며, 유효한
동일 요청량 비교의 성능 개선율로 해석하지 않는다. 획득·사용·COMMIT 값은 평균의 범위이고 p95/p99가 아니다.

| 풀 | 연결 획득 평균 ms | 연결 사용 평균 ms | COMMIT DB 평균 ms |
|---:|---:|---:|---:|
| 10 | 95.01~122.27 | 5.12~6.54 | 2.60~3.21 |
| 20 | 6.30~41.51 | 6.80~8.89 | 3.85~4.60 |
| 30 | 1.32~19.21 | 6.92~11.38 | 3.63~5.85 |

풀 10에서는 세 회차 모두 active 표본 평균 10개, pending 최대 189건이었다. 큰 풀에서는 획득 대기가
줄어드는 양상이 있었지만 연결 사용·COMMIT 시간까지 함께 줄지는 않았다. 이는 풀을 늘리는 것만으로
처리량이 비례 증가한다고 볼 수 없다는 진단 근거이며, COMMIT I/O가 유일한 병목이라는 증명은 아니다.
모든 본 측정에서 실제 요청당 연결 획득은 정확히 2회, Hibernate SQL은 7문장이었다.
발급 전략 조회·DB 시간 조회를 줄이는 코드 최적화는 이번 실험 변수에 포함하지 않았다.

### 판단과 후속 검증

풀 10을 고정한 과거 결과를 SKIP LOCKED 방식 자체의 처리 한계로 설명할 수 없다.
이번 결과에는 풀 증설에 따라 더 많은 요청을 처리하고 지연이 낮아지는 관측이 있지만,
이 로컬 실험만으로 20/30 중 운영 최적값이나 5,000 RPS 달성 가능성을 확정하지 않는다.
운영 설정은 그대로 두고, 후보 비교에는 독립 부하 발생기·충분한 워밍업과 더 긴 지속 측정이 필요하다.
최종 조건부 UPDATE/SKIP LOCKED before/after는 같은 풀 크기로 비교하며 풀 증설 효과와 구분한다.

실험 도구의 Python/k6 계약 테스트 62개와 변경 뒤 풀 검증 6개 재실행을 통과했고,
현재 애플리케이션 JAR 빌드 및 실제 풀 전환·재시작·정합성·정리를 확인했다. 6개는 앞의 62개에 포함된 테스트다.
임시 앱과 MySQL/Redis 2개는 종료·삭제했고 기존 개발용 컨테이너 11개는 유지했다.
[전체 원본·실행 소스·검증 기록](results/coupon-pool-sizing-2026-10-10/README.md)과

## 풀 10 고정 추가 측정 요약 · 2026-10-10

앱 1개·Hikari 10개를 고정하고 다섯 방식을 다시 비교했다. 충분한 재고의 부하 단계·경계 탐색 65회 자료와,
지속·급증·재고 경계 7개 시나리오의 본 측정 70회를 보존했다. 이 실행에서는 풀 크기를 고정했고 AWS 실행은 수행하지 않았다.

- 400 RPS·60초에서는 다섯 방식 모두 2/2회 통과했다. 650 RPS·60초의 기준선은 두 번 모두 요청 누락과
  높은 지연이 발생했고, SKIP LOCKED는 모두 39,000건을 발급했지만 호스트 압력 두 회차는 무효로 남겼다.
- 1,000 RPS 급증을 포함한 전체 판정은 0/10회 통과했다. 후반 회복 구간은 모두 기준을 만족했다.
- 재고 1,000개·마지막 1개·중복·다른 캠페인 준비의 40회는 모두 유효하고 통과했다.
- 7개 시나리오 70회 중 63회 유효·56회 통과, 실제 요청 861,356건이다. 발급 712,366건·품절 99,990건·
  중복 거절 49,000건이며, 초과·중복 발급·재고 불일치·CP012·예상 밖 응답·DB 교착 상태는 관측되지 않았다.

20초 탐색의 반복 통과 단계는 기준선 437 RPS, 대리 키 RR·복합 키 RR 812 RPS였지만
상위 단계의 무효·불안정 결과가 있어 최대 지속 처리량으로 확정하지 않는다.
최종 키·격리 수준·풀 크기와 이력서 개선율은 미확정이며 기본값은 대리 키 RR을 유지한다.
회차별 결과와 계측 제한은 아래 상세 및 [증거 묶음](results/coupon-scenarios-2026-10-10/README.md)에 있다.

## 고정 500 RPS 결과 · 2026-10-09

5개 방식으로 500 RPS·20초·5라운드씩 충분한 재고와 한정 재고를 측정했다.
총 50회, 실제 HTTP 495,128건에서 성공 270,796건과 품절 224,332건을 확인했다.
모든 회차의 실제 발급 수·고유 회원 수·잔여 재고가 일치했고 CP012·예상 밖 응답·DB 교착 상태는 0이었다.
50회 중 45회는 유효했고, 유효성·성능 기준을 모두 통과한 회차는 41회였다.

- 충분한 재고에서 대리 키 RR·RC와 복합 키 RR은 각각 5/5회 통과했다. 조건부 UPDATE는 1/5회 통과했다.
  RR의 회차별 성공 p95 중앙값은 대리 키 **22.50ms**, 복합 키 **22.10ms**로 비슷했다.
- 한정 재고에서 복합 키 RR은 **5/5회**, 대리 키 RR은 **3/5회** 통과했다. 복합 키 RR을 AWS에서 재확인할 근거가 생겼다.
  조건부 UPDATE도 이 조건에서는 5/5회 통과했다. SKIP LOCKED가 모든 응답에서 더 빠른 것은 아니다.
- 복합 키 RC는 두 시나리오 각각 1회씩 호스트 CPU 기준 미달과 요청 누락으로 무효였다.
  이 회차를 제외한 개선율은 계산하지 않았다. RC의 일관된 우위도 확인하지 못했다.
- 복합 키의 unit 레코드 잠금 항목은 줄었지만, 키 변경만으로 지연이 개선됐다는 인과 관계는 아직 확정하지 않는다.
  **현재 구현의 기본값은 대리 키 RR로 유지**한다. 최종 채택과 이력서 개선 수치는 다섯 방식의 AWS 반복 결과 후 결정한다.

## 범위와 구현 상태

`main`의 `97b021bf5132124b156f32b52d987897dbbd1ff3`에서 `refactor/coupon` 작업트리를 만들었다.
main에 없던 쿠폰 조건부 UPDATE 기준선·fixture·k6·AWS 준비의 선행 변경만 이식했다.
구현 커밋은 `706dd6f0a4c53e076ceda8b8637673299b3431fe`, 후속 잠금 관찰·실행기 보강 커밋은
`c04bd989dcf028b31436dd2f1fc92bbe8fd747e5`이다.

- 새 쿠폰은 유한한 양의 수량만 허용한다. 기존 nullable 스키마·과거 이력은 보존하며 새 CHECK를 추가하지 않았다.
- SKIP LOCKED에서는 unit 한 행을 삭제하고 `member_coupon`을 삽입하는 트랜잭션으로 발급한다.
  중복·FK 위반·실패 시 함께 롤백한다. 발급마다 `coupon.issued_quantity`를 갱신하지 않는다.
- 시작 전 증량·감량·폐기를 지원한다. 시작 후 수량 변경과 발급 회수에 의한 재입고는 지원하지 않는다.
- 쿠폰 정책을 `FOR SHARE NOWAIT`로 확인하고 unit을 `FOR UPDATE SKIP LOCKED`로 선택한다.
  빈 결과는 트랜잭션을 끝낸 뒤 새 스냅샷으로 확인한다. 확정 품절은 CP002, 재시도 후에도 남은 경합은 CP012이다.
- 대리 키 RR을 기본값으로 유지하고 대리 키 RC·복합 키 RR·복합 키 RC를 비교군으로 구현했다.
  비교군은 쿠폰 생성 시 고정된다. 조건부 UPDATE와 `issued_quantity`는 기준선으로 남겼다.
- 쿠폰 Redis Lua 구현은 제거했다. V29는 준비 컬럼을 `stock_prepared_at`으로 바꾸며,
  이전 Redis 준비 이력이 남아 있으면 적용을 중단한다. 기존 캠페인 전환을 자동으로 처리하지 않는다.

세부 계약은 [구현 계획](coupon-skip-locked-benchmark-plan.md), 실행법은
[실험 README](../../load-test/k6/coupon/README.md), AWS 절차는
[AWS 준비 문서](../../load-test/k6/coupon/AWS.md)에 있다.

## 잠금 구조와 격리 수준

실제 MySQL 트랜잭션을 유지한 상태로 `performance_schema.data_locks`를 관찰했다.

| unit 모델 | RR에서 선택한 unit의 레코드 잠금 | RC에서 선택한 unit의 레코드 잠금 |
|---|---|---|
| 대리 키 | 보조 인덱스 X + PK X,REC_NOT_GAP | 보조 인덱스와 PK 모두 X,REC_NOT_GAP |
| 복합 키 | PK X | PK X,REC_NOT_GAP |

이는 해당 단계에 보이는 **논리적인 unit 레코드 잠금 항목 2개 → 1개**의 차이다.
쿠폰·회원 FK 잠금과 테이블 intention lock은 별도로 존재한다.
`EXPLAIN FORMAT=JSON`에서는 대리 키가 `uk_coupon_issue_unit_coupon_unit`, 복합 키가 `PRIMARY`를 사용했고,
둘 다 `coupon_id`를 이용한 ref 접근으로 filesort 없이 조회했다. 이는 unit 두 행을 준비한 축소 SQL의 실행 계획이다.

`SHOW ENGINE INNODB STATUS`의 트랜잭션별 내부 수치도 별도로 확인했다. RR·RC 모두 아래와 같았다.

| 단계 | 대리 키 lock structs / row locks | 복합 키 lock structs / row locks | 표시된 heap size |
|---|---:|---:|---:|
| unit SELECT 직후 | 5 / 3 | 4 / 2 | 둘 다 1,128 bytes |
| unit DELETE 직후 | 5 / 3 | 4 / 2 | 둘 다 1,128 bytes |
| 회원 쿠폰 INSERT 직후 | 8 / 4 | 7 / 3 | 둘 다 1,128 bytes |

한 트랜잭션이 한 unit을 소비하는 이 재현에서 내부 잠금 구조는 하나 줄었지만 표시된 heap 할당은 같았다.
이는 모든 동시성·재고 크기에서 메모리가 동일하다는 결론은 아니며, 논리적 unit 잠금 항목 2개→1개를
전체 잠금 메모리 50% 절감으로 해석할 수 없다는 근거다. 처리량의 원인을 이 항목 수 하나로 설명하지 않는다.

빈 쿠폰 범위를 조회한 트랜잭션을 의도적으로 유지하고 바로 이웃 쿠폰에 unit을 삽입한 SQL 재현에서는,
두 키 모두 RR에서 삽입이 1초 lock wait timeout으로 끝났고 RC에서는 삽입이 성공했다.
따라서 쿠폰 하나를 조회하더라도 RR의 gap/next-key lock 영향이 구조적으로 사라지는 것은 아니다.
애플리케이션은 빈 조회 트랜잭션을 즉시 끝낸다. 이 축소 재현의 1초를 실제 발급 지연으로 해석하지 않는다.
회수·발급 시작 후 증감은 지원하지 않으므로 Shopify의 보충 작업과 같은 경쟁이 그대로 존재한다고 가정하지도 않는다.

이번 HTTP 반복 측정에서 InnoDB 교착 상태는 관측되지 않았다.
잠금 순서 변경으로 교착 상태를 해결했다는 이력서 사례는 만들지 않는다.

| 구현 | 반복 통과한 최고 설정 RPS | 바로 위의 관측 | 해석 |
|---|---:|---|---|
| 조건부 UPDATE | 437 | 500에서 두 회차 지연 실패, 한 회차 요청 누락 | 정확한 상한 미확정 |

| 복합 키 RC | 687 | 750에서 통과·실패 혼재 | 750 부근 불안정 |

이 수치는 이 환경의 **짧은 반복 탐색에서 확인한 단계**다. 운영 최대 처리량, DB 자체의 한계,
풀의 최적 크기나 AWS 성능으로 해석하지 않는다. 기본값은 대리 키 RR로 유지하고 최종 선택은 유보한다.
상위 단계의 실패·무효 회차도 보존했으며 통과한 회차만 고른 개선율은 계산하지 않는다.

500 RPS의 조건부 UPDATE 첫 회에서는 성공 p95 2,484.54ms, `dropped_iterations=338`, Hikari 대기 최대 189건이었다.
계획한 HTTP 요청은 10,000건이고 실제 요청은 9,663건이다. k6의 실행 경계에서 예약되는 추가 반복 때문에
`dropped_iterations`와 계획 HTTP 요청 수의 차이는 1건 다를 수 있다.
`coupon/PRIMARY/X,REC_NOT_GAP`에서 대기 트랜잭션 최대 8개가 관측됐고, 행 잠금 대기는 9,662회였다.
같은 설정의 대리 키 RR 첫 회는 요청 10,000건을 모두 처리했고 p95 15.91ms, 행 잠금 대기 0회였다.
기준선 첫 회는 실제 요청량이 달라 성능 개선율 비교에서 사용할 수 없다.
기준선 두 번째 회는 요청 누락 없이 10,000건을 처리했지만 p95 1,810.58ms, 완료 기준 처리량 462.34 RPS로 실패했다.
따라서 풀 대기와 실제 쿠폰 행 대기를 함께 관찰했다는 근거로 사용하며, 풀 증설 효과를 검증했다고 주장하지 않는다.

### 실행과 증거의 구분

- `local-20261010-004725-3294`: 큰 부하 단계 44회와 추가 300 RPS 1회를 완료했다.

  추가 300 RPS 1회와 중단된 부분 실행을 반복 통과 경계에 포함하지 않았다.
- `local-20261010-013103-3a96`: 같은 실행 파일·재고·시간·반복·VU·SLO를 검사하고 남은 경계 20회를 측정했다.

- 각 실행의 스크립트 사본, 설정·원본 해시, 측정·호스트·풀·DB 관측을 보존했다.
  인증 정보·세션 fixture·애플리케이션 로그는 저장소의 증거 묶음에 넣지 않았다.

무효였다. 후반 회복 구간의 응답은 모두 기준을 만족했지만 무효 회차의 후반 결과만 뽑아 성과로 쓰지 않는다.
이 구간 통계로 정확한 회복 완료 시점이나 모든 개별 요청의 지연을 단정하지 않는다.

급증을 포함한 전체 판정은 0/10회 통과했다. 복합 키 RR 두 번째 회차는 지연 기준은 만족했으나
급증 구간의 처리율 기준을 넘지 못했다. 나머지 회차는 급증 지연도 기준을 넘었다.
처리율은 해당 구간의 첫 요청부터 마지막 응답까지의 시간으로 나누므로 마지막 응답 지연을 포함한다.
특히 5초 구간에서는 이 기준이 민감하며, 1,000 RPS로 모든 요청을 보냈다는 사실과 구분한다.
SKIP LOCKED 급증 회차에서는 행 잠금 대기 없이도 풀 대기가 늘었다. 풀 크기·앱·DB의 후속 병목 실험 후보이며,
이 결과를 DB 자체의 최대 처리량으로 설명하지 않는다.

이 실행 사본에는 구간별 누락 계측의 제한이 있다. k6 전체 `dropped_iterations`와 실제 구간별 HTTP 요청 수는
수집됐지만, executor 누락을 사용자 정의 `segment` 태그로 나눈 값은 실제 누락이 있어도 0으로 표시됐다.
원본의 `segments` 내 `droppedIterations=0`을 구간별 누락 없음의 증거로 쓰지 않는다.
전체 누락 및 구간별 예정/실제 요청 수 검증이 별도로 있어 해당 실행의 무효·실패 판정은 유지된다.
원본을 고치지 않고 제한을 별도 기록했으며 이후 도구는 기본 `scenario` 태그와 전체/구간 합계 검증을 사용한다.
[k6의 시나리오 태그 문서](https://grafana.com/docs/k6/latest/using-k6/scenarios/advanced-examples/)를 참고했다.

### 재고 소진·중복·다른 캠페인 준비

재고 1,000개에 250 RPS·20초를 적용한 10회는 모두 유효하고 통과했다.
매 회차 정확히 1,000건 발급·4,000건 품절이었고, 요청 누락·CP012·재고 불일치가 없었다.
아래 지연은 두 라운드 순서다.

| 방식 | 성공 p95 ms | 품절 p95 ms |
|---|---|---|
| 조건부 UPDATE RR | 14.61 / 18.55 | 5.78 / 4.90 |
| 대리 키 RR | 5.54 / 5.78 | 9.71 / 12.93 |
| 대리 키 RC | 9.41 / 9.43 | 11.00 / 13.88 |
| 복합 키 RR | 20.94 / 6.76 | 9.46 / 9.24 |
| 복합 키 RC | 18.14 / 15.76 | 11.62 / 11.02 |

품절 응답에서는 기준선도 빠르며, SKIP LOCKED의 빈 조회 후 확정 품절 재확인 비용을 숨기지 않는다.

마지막 1개에 100 RPS·20초를 적용한 10회도 모두 유효하고 통과했다. 매번 1건 발급·1,999건 품절이며
CP012·초과 발급·잔여 unit 불일치는 없었다. 회차당 성공 표본은 하나이므로 성공 p95/p99를 성능 근거로
비교하지 않는다. 첫 요청의 잠금을 의도적으로 유지하는 실험은 아니며, 마지막 행을 잠근 동안의
빈 조회·제한적 재시도 분류는 앞선 실제 MySQL 정합성 테스트와 별도 SQL 관찰의 범위다.

중복은 회원 100명에게 10회씩 연속 요청한 뒤 순환하는 방식으로, 250 RPS·20초를 적용했다.
10회 모두 유효하고 통과했으며 매번 성공 100건·중복 4,900건이었다. SKIP LOCKED의 초기 1,001개 unit 중
901개가 남았고, 기준선의 최종 `issued_quantity`도 100이었다. 교착 상태는 관측되지 않았다.

중복 첫 대리 키 RR 회차에서는 `DELETE coupon_issue_unit`과 `INSERT member_coupon` 실행이 각각 111회
관측됐고, 최종 회원 쿠폰은 100개·잔여 unit은 901개였다. 응답은 성공 100건·중복 4,900건으로 일치했다.
정상 발급 수를 넘는 삭제 시도가 최종 재고 유실로 이어지지 않았음을 확인했다.
statement digest의 실행 횟수를 서로 다른 트랜잭션 수와 동일하게 취급하지 않는다.

현재 기준선은 카운터 UPDATE 후 중복 여부를 확인하며 첫 회차의 UPDATE 실행은 5,000회였다.
SKIP LOCKED는 unit을 가져오기 전에 기존 발급을 조회한다. 따라서 이 중복 경로의 성능·SQL 수 차이에는
확인 순서 차이도 포함된다. 공용 카운터 경합 제거 효과는 고유 회원의 충분한 재고 시나리오를 중심으로 해석한다.

다른 캠페인 준비는 재고 1,000개에 250 RPS·20초를 보내면서 같은 방식의 새 캠페인 두 개를 각각
10,000개 재고로 만들었다. 첫 발급 응답을 관측한 뒤 6초를 기다리고, 첫 준비 완료 후 다시 6초를 기다렸다.
예상 재고 소진 시점인 약 4초 이후를 겨냥했으며 실제 품절 전환 시각으로 준비를 동기화한 실험은 아니다.
20건의 준비 모두 발급 HTTP 측정 구간 안에서 시작·완료됐고, 새 캠페인의 발급 수는 0·재고는 10,000개로 맞았다.
기준선은 unit을 만들지 않으므로 준비 지연을 SKIP LOCKED와 같은 작업의 속도로 비교하지 않는다.

| 방식 | 준비 4건의 HTTP 소요 ms (회차·실행 순) | 전체 구간의 행 잠금 대기 횟수 (회차 순) |
|---|---|---|
| 조건부 UPDATE RR | 5.82 / 6.37 / 10.92 / 6.45 | 102 / 213 |
| 대리 키 RR | 56.31 / 61.93 / 60.81 / 59.81 | 0 / 0 |
| 대리 키 RC | 63.76 / 54.54 / 89.70 / 54.98 | 0 / 0 |
| 복합 키 RR | 50.57 / 45.86 / 185.41 / 52.98 | 0 / 0 |
| 복합 키 RC | 48.26 / 49.88 / 51.38 / 48.56 | 0 / 0 |

10회 모두 유효하고 통과했으며 매번 1,000건 발급·4,000건 품절이었다. 이 자연 발생 부하에서
SKIP LOCKED의 행 잠금 대기는 관측되지 않았다. 이는 앞서 의도적으로 빈 범위 잠금을 유지한 SQL 실험을
반증하거나 RR에서 gap lock이 불가능함을 뜻하지 않는다. DB 전체 대기 카운터에는 발급·품절·준비 작업이
함께 들어 있으므로 기준선의 대기를 모두 다른 캠페인 준비 탓으로 해석하지 않는다.

시작 전에 실행 중이던 개발 컨테이너 11개는 모두 계속 실행 중이었다.

### 격리 수준 비교와 검증 범위

격리 수준 비교의 범위도 구분한다. 연결의 기본 격리 수준은 RR이고, RC 비교군은 발급 트랜잭션에서만
RC로 바꾼다. 실행 파일에 포함된 Spring JDBC 6.2.14의 `DataSourceUtils`는 요청된 격리 수준이 다르면
변경하고 트랜잭션 후 이전 수준을 복원하며, Connector/J 9.5.0은 이를 `SET SESSION TRANSACTION ISOLATION LEVEL`
명령으로 전달한다. 실행 중 MySQL의 누적 statement digest에서도 RC 설정·RR 복원 명령을 확인했다.
따라서 HTTP 결과에는 이 구현 비용도 포함된다. 이 관측은 준비·워밍업·여러 비교군이 섞인 누적 자료이므로,
회차별 추가 비용이나 RC 결과의 원인을 정량적으로 설명하는 자료로 쓰지 않는다.

구현 중 두 문제를 실제로 재현하고 수정했다. 전략 조회가 연결을 점유한 채 새 트랜잭션이 두 번째 연결을
요구하던 풀 고갈은 조회 트랜잭션을 먼저 끝내도록 수정했다. OSIV의 기존 관리 객체 때문에 새 잠금 조회가
오래된 쿠폰 정책을 반환하던 문제는 각 시도·재확인 전에 영속성 컨텍스트를 비우고 회귀 테스트로 확인했다.
둘을 InnoDB 교착 상태 해결 사례로 설명하지 않는다.

이번 변경은 측정 도구와 문서에 한정되며 앱 JAR은 바꾸지 않았다. 최종 쿠폰 Python/k6 도구 테스트
56개가 통과했다. 부족한 VU·느린 응답으로 실제 누락을 만든 회귀 사례에서 수정된 구간별 누락 합계를 확인했다.
첫 검증은 세션 갱신 중에 수행했다. 짧은 측정에서도 워밍업 세션 수를 확보하는 가드를 보완한 뒤
실험 종료·리소스 정리 후 같은 56개를 다시 통과했다. 두 검증 모두 완료된 140개 HTTP 회차의 시간 구간과
겹치지 않음을 확인했다. 서로 다른 테스트 112개를 수행한 것으로 합산하지 않는다.
앞선 Java 검증을 이번에 다시 수행한 것으로 표현하지 않는다.

## 재현과 증거

JDK 21과 Docker, k6 및 관측용 Python 의존성을 준비하고 [실험 README](../../load-test/k6/coupon/README.md)의
환경 조건을 따른다. `COUPON_JAVA_HOME`에는 같은 JDK 경로를 지정한다.

```bash
python load-test/k6/coupon/run_local_e2e.py \
  --rate 500 --duration 20 --rounds 5 --observe \
  --variants db skip_surrogate_rr skip_surrogate_rc skip_composite_rr skip_composite_rc \
  --client-vus 500 --cooldown 3 --java-home "$COUPON_JAVA_HOME"
```

원본은 `build/k6/coupon-local/{runId}/`에 있다. 저장소에는 요청·지연·정합성·SQL·잠금·풀·자원·판정의
요약 자료와 해당 `result.json`의 SHA-256을 보존한다. 이메일·세션·비밀번호·토큰과 앱 로그는 포함하지 않는다.
모든 실험은 전용 앱을 종료하고 자신이 만든 MySQL/Redis 컨테이너만 정리했다.

AWS용 다섯 비교군·5라운드 오프라인 묶음은 `build/k6/coupon-aws/prepared-skip-locked-all-five-final/`에 준비했다.
파일 해시를 검증했고 AWS·네트워크 호출은 0회이며 `readyToExecute=false`다. 실제 환경 입력은 아직 채우지 않았다.
AWS는 오프라인 준비까지 수행했다. 실제 이미지 발행·클라우드 자원 변경·AWS 부하 측정은 아직 수행하지 않았다.
AWS에서는 부하 발생기를 분리하고 더 긴 측정 구간과 단계별 부하 탐색으로 이 결과를 검증해야 한다.
최종 키·격리 수준 선택, 지속 가능한 처리량과 이력서 개선율은 그 결과를 확인한 뒤 결정한다.
