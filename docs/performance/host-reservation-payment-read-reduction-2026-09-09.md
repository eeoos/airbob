# 호스트 예약 상세 조회 통합

## 판단과 적용 범위

대상은 `GET /api/v1/profile/host/reservations/{reservationUid}`다.
호스트 예약 본문과 최초 결제 금액을 **필요한 응답 컬럼만 읽는 단일 조회**로 통합했다.
쿼리 수만을 기준으로 합친 것이 아니라 다음 조건을 확인했다.

| 검토 항목 | 근거와 판단 |
| --- | --- |
| 실제 화면 소비 | 호스트 화면은 결제 존재 여부와 최초 결제 금액만 사용한다. |
| 결제 조인의 행 수 | V1 스키마의 `payment.reservation_id` UNIQUE가 예약당 최대 한 건을 보장한다. 행이 늘어나지 않는다. |
| 다른 조인의 행 수 | 숙소·게스트는 PK 한 건, 주소는 선택적 PK 한 건이다. 목록이나 컬렉션을 조인하지 않는다. |
| 결제 없는 예약 | LEFT JOIN으로 예약을 유지하고, NOT NULL인 `payment.amount`가 조인 결과에서 null이면 결제 없음으로 매핑한다. 0원은 별도로 유지한다. |
| 소유권 | 기존 `reservation_uid`와 `accommodation.member_id` 조건을 동일하게 적용한다. 별도 엔티티 조회를 권한 검사 용도로 남길 필요가 없다. |
| 취소 이력 | 여러 건인 거래 원장은 조인하지 않는다. 게스트의 내역 조회는 기존 구조와 내용을 유지한다. |

이번 조회는 위 조건 때문에 통합이 적절하다. 여러 건인 컬렉션이나 페이지 조회에도 같은 결론을
일괄 적용하지 않는다. 별도 캐시나 외부 조회가 필요한 관계도 이 사례의 판단 범위가 아니다.

## 현재 구현과 응답 계약

`HostReservationDetailProjection`은 예약·숙소·주소·게스트의 응답 생성용 컬럼과
`payment.amount` 총 23개를 읽는다. `Reservation`, `Accommodation`, `Member`, `Address`,
`Payment` 엔티티를 적재하지 않는다. 사용처가 사라진 별도 결제 금액 조회 메서드는 제거했다.

호스트의 `payment`는 `{ "total_amount": 100001 }` 또는 `null`이다.
이전 단계에서 호스트 전용 `PaymentResponse.HostPaymentInfo`와 프론트 타입을 분리했으며,
이번 통합에서는 기존 JSON 응답과 화면 동작을 유지했다.

- 부분·전액 취소 후에도 최초 결제 금액을 표시한다. 잔액이나 예약 금액으로 대체하지 않는다.
- 결제가 없으면 `null`, 기록된 0원 결제이면 `{ "total_amount": 0 }`으로 구분한다.
- 주소가 없어도 예약을 반환하며, 주소 하위 필드를 null로 채우는 기존 계약을 유지한다.
- 체크인·체크아웃은 현재 숙소 시간대가 아닌 **예약 당시 시간대**로 복원한다.
- 요청 메시지와 우편번호 등 기존 응답 필드도 보존한다. 이 단계는 데이터 조회 구조의 변경이다.
- 타인의 예약과 존재하지 않는 예약은 기존 `ReservationNotFoundException`으로 처리한다.
- 소유권 조건과 결제가 한 문장으로 조회되므로 예약·결제 결과가 같은 조회 시점에 속한다.

프론트 작업트리 `codex/editable-booking-review`에서 원격 main을 다시 가져왔다.
`origin/main`의 `f80bc095`는 이미 포함되어 있었고, 추가 프론트 수정은 필요하지 않았다.
`hostReservationDetailViewModel.ts`와 `HostReservationDetailScreen.tsx`의 소비 경로를 확인했다.

## 전후 측정

MySQL 8.4.11 Testcontainers에서 영속성 컨텍스트와 Hibernate 통계를 초기화한 뒤,
`ReservationTransactionService`의 실제 SQL과 엔티티 적재를 측정했다.
직전 구현 `8d4e5ee3`에 동일한 결제 완료·부분 취소·전액 취소 fixture를 적용해 기준값을 확인했다.
이 fixture에는 주소 행이 없으며, 주소가 있는 전체 응답은 별도 통합 테스트로 검증했다.

| 항목 | 직전 구현 | 현재 구현 |
| --- | ---: | ---: |
| 호스트 상세 SQL 수 | 2 | 1 |
| 두 조회에서 읽던 SELECT 컬럼 합계 | 69 (본문 68 + 금액 1) | 23 |
| 적재한 엔티티 수 — 위 측정 fixture | 3 | 0 |
| 결제 없는 호스트 상세 SQL 수 | 2 | 1 |
| 소유권 거부·예약 없음 SQL 수 | 1 | 1 |

앞선 결제 응답 축소 단계에서는 취소 원장 조회를 없애 SQL 3회에서 2회로 줄였고,
이번 단계에서 본문과 금액 조회를 합쳐 1회로 줄였다.
조회 SQL 수와 읽는 컬럼·엔티티 수의 감소를 확인한 것이며,
운영 응답 시간이나 처리량의 개선 비율을 측정한 것은 아니다. HTTP 인증 조회는 집계에서 제외했다.

## 검증

- 백엔드 60개 통과: `ReservationPaymentReadQueryIntegrationTest` 14개,
  `ReservationResponseTest` 7개, 예약 저장소·트랜잭션 테스트 39개.
- 결제 완료·부분 취소·전액 취소·0원 결제, 주소 및 결제 없음, 다른 예약의 결제 혼입 방지,
  예약 게스트 및 타인의 호스트 상세 접근 거부, 존재하지 않는 예약을 확인했다.
- 서울 시간대로 바뀐 숙소와 뉴욕 시간대 예약의 조합, 서머타임 종료를 걸친 날짜,
  주소·이미지·요청 메시지를 포함한 전체 JSON 응답을 실제 DB 조회와 계약 fixture로 검증했다.
- 호스트 조회 SQL 1회, SELECT 23개 컬럼, 엔티티 적재 0건, 취소 원장 조회 없음도 검증했다.
- 게스트의 최초 금액·잔액·취소 내역 순서와 과거 원장 보존 회귀 검사를 통과했다.
- 프론트 API adapter·mapper·호스트 화면 모델 관련 45개 테스트 통과.
  백엔드와 프론트의 `host-reservation-stay-payment.json` 내용은 동일하다.

결제 쓰기·취소 처리, DB 스키마·인덱스, ES 검색은 이번 변경 대상이 아니다.
호스트 예약 목록의 후속 개선은 [목록 조회 개선 기록](host-reservation-list-projection-2026-09-09.md)에 정리했다.
다른 조회 경로의 개선, 운영 데이터 실행계획·지연 시간 측정은 별도로 판단해야 한다.
이번 상세 조회의 통합 결과로 전체 조회 개선이 끝났다고 보지 않는다.
