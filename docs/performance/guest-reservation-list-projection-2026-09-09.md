# 게스트 예약 목록 조회 개선

## 판단과 소비 근거

대상은 `GET /api/v1/profile/guest/reservations`다. 프론트 작업트리
`codex/editable-booking-review`에서 원격 main을 다시 가져왔고,
`origin/main`의 `f80bc095`는 이미 포함되어 있었다.

`reservationListViewModel.ts`, `guestTripGroups.ts`와 wire mapper를 확인했다.
여행 카드는 예약 UID, 숙소 이름·이미지, 체크인·체크아웃 날짜를 사용하고,
연도별 그룹은 체크인 날짜를 사용한다. 기존 API의 ID·상태·시간대·생성 시각 계약도 보존한다.

예약과 숙소는 한 건씩 연결되므로 단일 조인을 유지하는 것이 적절하다.
주소·호스트·결제·취소 이력을 추가 조회할 이유는 없다.
예약·숙소 엔티티 전체 대신 응답 생성, 커서, 만료 계산에 필요한 11개 컬럼만 읽도록 바꿨다.

| 조회 데이터 | 필요한 이유 |
| --- | --- |
| 예약 ID·생성 시각 | 기존 응답과 생성 시각 동률을 처리하는 커서 |
| 예약 UID | 상세 이동과 목록 식별 |
| 체크인·체크아웃 날짜·예약 시간대 | 기존 날짜·시간대 계약과 카드·연도 그룹 표시 |
| 저장 상태·만료 시각 | 정리 작업을 기다리지 않고 실제 만료 상태 계산 |
| 숙소 ID·이름·대표 이미지 | 기존 숙소 기본 정보 계약과 카드 표시 |

만료 시각은 화면에서 직접 표시하지 않지만 상태 계산에 필요하다.
`GuestReservationListProjection`에 남기고 응답에는 추가 노출하지 않았다.

## 보존한 로직

- `Reservation.effectiveStatus(status, expiresAt, now)`를 재사용한다.
  필터와 응답 계산에는 서비스가 한 번 읽은 동일한 `now`를 전달한다.
- `PAYMENT_PENDING`은 만료 시각 직전까지 예정 목록에 남고, 정확한 만료 시각부터
  `EXPIRED`로 응답하며 취소·만료 목록에서 조회된다.
- `PAYMENT_PROCESSING`은 만료 시각이 지났다는 이유로 만료 처리하지 않는다.
- 조회가 DB 상태를 변경하지 않는다. 만료 대기 행의 저장 상태가 `PAYMENT_PENDING`이어도
  응답은 `EXPIRED`일 수 있으며, 실제 정리는 기존 쓰기 경로가 담당한다.
- 기존 확정·취소 처리 중·취소 실패 예약의 체크아웃 시각 필터를 유지한다.
  정확한 체크아웃 시각은 과거 목록에 속한다.
- 소유권은 `reservation.guest.id = memberId`다. 숙소 소유자는 다른 게스트의 예약을
  자신의 여행으로 조회할 수 없다. 예약한 숙소의 호스트가 서로 달라도 본인의 여행은 포함한다.
- 현재 비공개인 숙소, 주소·대표 이미지가 없는 숙소의 기존 예약도 유지한다.
- 정렬은 `createdAt DESC, id DESC`이며, 한 건 더 읽어 다음 페이지 여부를 결정한다.
  커서는 실제 반환한 마지막 행에서 생성하고 마이크로초 정밀도를 유지한다.

## 선택 필터 오류 수정

API는 `filterType`을 선택 파라미터로 선언했지만 기존 저장소는 null switch로
`NullPointerException`을 발생시켰다. 통합 테스트에서 이 오류를 재현한 뒤 수정했다.
필터 생략 시 본인의 모든 상태를 조회하고 응답의 만료 계산도 적용한다.
호스트 목록과 달리 게스트에게 필요한 결제 대기·진행 상태도 포함한다.
프론트가 지정하는 세 필터의 기존 결과는 보존한다.

## 측정

MySQL 8.4.11 Testcontainers에서 직전 구현 `3d757b49`와 동일한 데이터를 사용했다.
서비스 호출 전에 영속성 컨텍스트와 Hibernate 통계를 초기화했다.

| 항목 | 이전 | 이후 |
| --- | ---: | ---: |
| 페이지당 SQL 수 | 1 | 1 |
| SELECT 컬럼 수 | 44 | 11 |
| 엔티티 적재 — 두 건 반환하는 첫 페이지 fixture | 5 | 0 |
| 주소·회원·결제 추가 조회 | 0 | 0 |

첫 페이지 fixture는 다음 페이지 확인용 예약까지 3건과 숙소 2건을 읽던 경우다.
기존 엔티티 수는 데이터에 따라 달라지며, 개선 후에는 projection만 생성한다.
HTTP 인증 조회는 포함하지 않았다. 운영 지연 시간과 처리량 개선 비율은 아직 측정하지 않았다.

## 검증

- 백엔드 75개 통과: 게스트 목록 통합 8개, 호스트 목록 7개, 예약 상세 결제 조회 14개,
  예약 DTO 7개, 예약 저장소·트랜잭션 39개.
- 만료 직전·정각·직후, 결제 진행 유지, DB 저장 상태 불변, 세 필터와 필터 생략을 검증했다.
- 생성 시각 동률의 페이지 연결, 소유권, 마지막·빈 페이지, 커서 기준 행 삭제와
  더 최신 예약 삽입 이후의 누락·중복 방지를 확인했다.
- 실제 DB 응답을 `contracts/guest-reservation-list-expired.json`과 비교한다.
  같은 fixture를 프론트 mapper·카드 표시 및 브라우저 테스트에서 사용한다.
- 프론트 예약·프로필 관련 293개, 브라우저 2개, 타입 검사와 strict/E2E lint 통과.
  만료된 예약의 취소된 여행 표시·상세 이동 링크와 기존 데스크톱·모바일 화면을 확인했다.
  브라우저는 응답 fixture를 사용하며 실행 중인 백엔드와 연결한 E2E는 아니다.

프론트 제품 코드 수정은 필요하지 않았고 계약 검증을 추가했다.
인덱스·DB 스키마·재고 및 결제 쓰기 경로·ES 검색은 이번 변경 범위가 아니다.
다른 조회의 DTO·조인 판단과 운영 실행계획·지연 시간 측정은 별도로 진행해야 한다.
