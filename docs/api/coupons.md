# 쿠폰 조회와 발급

캠페인 조회·내 쿠폰 조회·발급은 모두 로그인 후 호출한다. 사용자용 발급 경로는 `POST /api/v1/coupons/{couponId}/issue` 하나다. 관리자 생성·수정·준비·삭제에는 활성 ADMIN 권한이 필요하다.

## 캠페인 목록

`GET /api/v1/coupons?size=20`

활성이고 재고 준비를 완료했으며 발급 종료 시각 전인 캠페인만 나온다. 발급 시작 전, 품절, 이미 본인이 발급받은 캠페인도 포함한다. 전체 캠페인이나 관리 중인 미준비 캠페인을 조회하는 API가 아니다.

발급 시작 시각·캠페인 ID 내림차순이며 `cursor`, `size`를 사용한다. size는 기본 20, 1~50이다. 첫 요청에는 cursor를 생략하고 `data.page_info.has_next=true`이면 `next_cursor`를 그대로 전달한다. 마지막 페이지에는 `next_cursor=null`, 빈 결과에는 `infos=[]`, `current_size=0`이 나온다.

| issuance_status | 의미 |
|---|---|
| UPCOMING | 현재 시각이 발급 시작 전이다. 재고 유무보다 우선한다. |
| SOLD_OUT | 발급 시작 후 `total_quantity`가 null이 아니며 잔여 재고가 없다. |
| OPEN | 그 외의 조회 상태다. 과거 `total_quantity=null`도 시작 후 이 상태로 읽힌다. |

`total_quantity`는 전체 수량이며 남은 수량이 아니다. OPEN은 발급 성공을 보장하지 않는다. 조회 후 다른 회원이 재고를 소진하거나 발급 기간이 끝날 수 있고, 본인은 이미 발급받았을 수 있다. 과거 null 수량을 읽는 호환 규칙은 신규 무제한 쿠폰 생성·발급을 허용한다는 뜻이 아니다.

## 내 쿠폰 목록과 사용 상태

`GET /api/v1/members/me/coupons?size=20`

현재 회원의 모든 보유 쿠폰을 발급 내역 생성 시각·보유 내역 ID 내림차순으로 조회한다. 사용 완료·만료·비활성 쿠폰도 포함한다. 응답의 `coupon_id`는 **캠페인 ID**이며 예약 견적의 `coupon_id`에 그대로 사용한다. 정렬에 사용하는 보유 내역 ID는 응답에 노출하지 않으므로 커서를 직접 만들지 않는다.

캠페인 목록과 같은 크기 범위를 사용하지만 두 API의 커서를 서로 바꾸어 쓰면 안 된다. 두 목록 모두 요청 시점의 현재 데이터를 읽으므로 페이지 사이에 포함 여부·순서가 바뀔 수 있다. 최신 목록은 커서 없이 다시 조회한다. 잘못된 커서는 400/C010, size의 범위·정수 형식 오류는 400/C006이다.

아래 조건을 위에서부터 적용한다.

| status | 조건 |
|---|---|
| USED | 예약에 사용 처리된 쿠폰 |
| EXPIRED | 사용 종료 시각에 도달했거나 지난 미사용 쿠폰 |
| UNAVAILABLE | 만료 전이지만 비활성인 미사용 쿠폰 |
| UPCOMING | 활성·미사용 상태이며 사용 시작 전 |
| AVAILABLE | 활성·미사용 상태이며 사용 기간 안 |

발급 기간 종료나 캠페인 품절은 이미 보유한 쿠폰의 사용을 막지 않는다. AVAILABLE이어도 예약 금액이 최소 금액에 미달하거나 계산한 할인액이 0이면 적용할 수 없다. [예약 견적](reservation-payment.md)에서 현재 조건을 검증한다.

견적은 쿠폰을 소비하지 않고, 체크아웃에 적용되면 결제 완료 전부터 USED가 된다. 보유 해제·예약 취소 등으로 복원되면 현재 기간과 활성 여부에 따라 상태를 다시 계산한다. 보유 쿠폰 복원으로 발급용 재고가 늘거나 같은 캠페인을 다시 발급받을 수 있는 것은 아니다.

## 발급 요청

`POST /api/v1/coupons/{couponId}/issue`

본문과 회원 ID 입력은 없다. 현재 로그인한 회원에게 발급하며 성공은 **201**과 `{"success":true}`다. 캠페인별로 한 번만 발급받는다.

| HTTP / 코드 | 의미와 대응 |
|---|---|
| 404 / CP001 | 캠페인이 존재하지 않는다. |
| 409 / CP002 | 잔여 재고가 소진되었다. 품절로 표시한다. |
| 409 / CP003 | 이미 발급받았다. 내 쿠폰 목록을 확인한다. |
| 409 / CP005 | 활성·발급 기간·양수 유한 수량 조건을 충족하지 않는다. |
| 503 / CP011 | 발급 기간 안이지만 재고 준비가 완료되지 않았다. 운영 상태를 확인한다. |
| 503 / CP012 | 다른 발급과 경합했다. 지연을 두고 제한된 횟수로 재시도한다. |
| 400 / C004 | couponId를 숫자로 해석할 수 없다. |

CP012에는 `Retry-After` 헤더가 없으며 품절로 표시하면 안 된다. 네트워크 단절 후 재요청에서 CP003을 받으면 첫 요청이 성공했을 수 있으므로 보유 목록에서 확인한다. 발급 기간이 끝나는 등 조건을 벗어나면 이미 발급받았더라도 CP005가 먼저 반환될 수 있다.

## 관리자 생성과 재고 준비

1. `POST /api/v1/admin/coupons`로 미래에 발급을 시작하는 캠페인을 생성한다.
2. **201 응답의 `data.id`를 보관한다.** 생성만으로는 재고가 준비되지 않으며 사용자 목록에도 나오지 않는다.
3. 활성 상태에서 발급 시작 전에 `POST /api/v1/admin/coupons/{couponId}/stock/prepare`를 본문 없이 호출한다.

생성 요청 예시:

```json
{
  "name":"겨울 여행 할인",
  "description":"숙박 예약 할인 쿠폰",
  "discount_type":"FIXED_AMOUNT",
  "discount_value":1000,
  "min_payment_price":10000,
  "issue_start_at":"2027-01-01T00:00:00Z",
  "issue_end_at":"2027-01-31T00:00:00Z",
  "usable_from":"2027-01-01T00:00:00Z",
  "usable_until":"2027-02-28T00:00:00Z",
  "is_active":true,
  "total_quantity":100
}
```

생성 응답 예시:

```json
{"success":true,"data":{"id":101}}
```

이름·할인 종류·할인 값·발급 및 사용 시각 4개·활성 여부·전체 수량은 필수다. 이름은 빈 값·공백만으로 지정할 수 없으며 이름과 설명은 최대 255자다. 설명·최소 금액·최대 할인액은 생략하거나 null로 보낼 수 있다.

전체 수량은 양수다. `FIXED_AMOUNT`의 할인 값은 원 단위 양수, `PERCENTAGE`는 1~100이다. `min_payment_price`는 할인 전 숙박 금액의 하한으로 null 또는 0이면 하한이 없다. `max_discount_amount`는 정률 할인에만 적용하며 null이면 상한이 없고 0이면 할인액도 0이 된다. 할인액은 원래 숙박 금액을 초과하지 않는다.

시각은 `Z` 또는 `+09:00` 등 오프셋이 있는 ISO 8601 문자열로 보낸다. 서버는 UTC로 변환하고 마이크로초 단위로 반올림한 값으로 검증·저장한다. UTC 1000~9999년 범위이며 반올림으로 범위를 넘는 값도 거부한다. 발급·사용 기간은 시작 포함, 종료 제외다. 다음 조건을 모두 만족해야 한다.

- 발급 시작은 현재보다 미래이고 발급 종료보다 이르다.
- 사용 시작은 사용 종료보다 이르다.
- 사용 종료는 발급 종료와 같거나 이후다.

응답은 항상 UTC `Z` 형식이며 한국 화면은 `Asia/Seoul`로 표시한다. 예시 날짜는 실제 실행 시 미래 일정으로 바꾼다. 형식 해석 실패는 400/C001, 누락·길이·할인·수량·기간 등 설정 검증 실패는 400/CP013이다.

재고 준비는 활성·시작 전·발급 내역 없음 조건이 필요하다. 이미 준비했으면 409/CP009, 미준비 상태에서 준비 조건을 충족하지 않으면 409/CP010이다. 재호출로 재고를 중복 생성하거나 소비된 재고를 복원하지 않는다.

## 관리자 수정과 삭제

`PATCH /api/v1/admin/coupons/{couponId}`는 부분 수정이다. 모든 필드는 **생략·null이면 유지**하므로 null로 기존 값을 제거할 수 없다. 설명을 비우려면 `{"description":""}`을 보낸다. 병합한 최종 설정을 생성과 같은 규칙으로 검증한다.

| 수정 항목 | 허용 범위 |
|---|---|
| 이름·설명·할인 종류 및 금액 조건·사용 기간 | 발급 시작 후에도 수정 가능. 보유 쿠폰에도 현재 조건이 적용됨 |
| 발급 시작·종료·활성 여부·전체 수량의 실제 값 변경 | 발급 시작 전이며 발급 내역이 없어야 함. 아니면 409/CP014 |

`issue_start_at`은 명시하면 동일한 값이라도 현재보다 미래여야 한다. 시작 후 일반 정보만 수정할 때는 이 필드를 생략한다. 이미 상한 금액이 설정된 경우 null로 상한을 제거할 수 없으며 0은 ‘상한 없음’이 아니다.

수량 전용 경로는 `PATCH /api/v1/admin/coupons/{couponId}/quantity`, 본문은 `{"total_quantity":200}`이다. 증가분이 아닌 **목표 전체 수량**이다. 미준비 상태는 전체 수량만 변경하며, 준비 상태는 재고도 함께 조정한다. 같은 수량을 다시 보내도 시작 전·발급 내역 없음 조건을 검사한다. 이 경로의 누락·null·0·음수는 400/C001이다.

`DELETE /api/v1/admin/coupons/{couponId}`는 시작 전이며 발급 내역이 없는 캠페인과 미발급 재고를 삭제한다. 본문은 없고 조건 위반은 409/CP014, 삭제 후 재요청은 404/CP001이다. 수정·수량 변경·준비·삭제 성공은 모두 **200**과 `{"success":true}`다.

로그인하지 않으면 401/M004, 활성 ADMIN이 아니면 403/M006이다. 운영 점검은 [쿠폰 운영 안내](../operations/coupon-issuance-operations.md), 시간 계약은 [쿠폰 UTC 계약](../operations/coupon-time-contract.md)을 따른다.
