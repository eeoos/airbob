# 정산 API 사용 안내

정산 API는 결제 원장을 월별·호스트별로 집계하고 **지급 완료 상태를 기록**한다. 지급 처리 API는 은행·PG 송금 기능을 호출하지 않는다. 외부 지급 절차와 상태 기록을 구분해서 사용한다.

호스트 조회는 [client.yaml](openapi/client.yaml), 관리자 집계·조회·지급 처리는 [admin.yaml](openapi/admin.yaml)의 `정산` 태그에서 확인한다. 모든 API는 로그인이 필요하며, 로그인 응답의 HttpOnly `SESSION_ID` 쿠키를 브라우저가 자동 전송한다. 회원 ID나 쿠키 값을 요청 폼에 직접 입력하지 않는다.

## 경로와 입력

| 작업 | 메서드와 경로 | 입력 |
|---|---|---|
| 내 정산 목록 | `GET /api/v1/profile/host/settlements` | 필수 쿼리 `from`, `to`: `YYYY-MM-DD` |
| 내 정산 요약 | `GET /api/v1/profile/host/settlements/summary` | 없음 |
| 내 정산 상세 | `GET /api/v1/profile/host/settlements/{settlementId}` | 정산 ID |
| 관리자 월별 조회 | `GET /api/v1/admin/settlements` | 필수 쿼리 `month`: `YYYY-MM`, 선택 `status` |
| 관리자 월 생성·재집계 | `POST /api/v1/admin/settlements/generate` | 필수 쿼리 `month`: `YYYY-MM` |
| 관리자 기간 생성·재집계 | `POST /api/v1/admin/settlements/backfill` | 필수 쿼리 `from`, `to`: `YYYY-MM` |
| 관리자 지급 완료 기록 | `POST /api/v1/admin/settlements/{settlementId}/pay` | 정산 ID |

POST에도 요청 본문이 없다. 월·기간은 JSON 본문이 아닌 **쿼리**로 전달한다. 목록에는 페이지·커서·크기 입력이 없으며 해당 범위의 저장된 정산 전체를 반환한다.

관리자 경로는 현재 활성 ADMIN만 호출할 수 있다. 호스트 경로는 로그인한 회원 본인의 정산만 조회한다. 자신의 정산이 없는 회원은 빈 목록·0으로 된 요약을 받는다. 상세 조회는 다른 회원의 정산에 대해 403/S004를 반환한다.

입력 연도는 **1000~9999**이며, 월은 `2027-01`처럼 월 두 자리를 포함한 정확한 형식을 사용한다. `2027-1`, `2027-13`, 앞뒤 공백을 넣은 월은 400이다. 기간은 `from ≤ to`여야 하며 같은 날짜·같은 월도 허용한다.

## 조회 범위와 응답

호스트 목록은 정산 월의 1일인 `settlement_month`가 `[from, to]`에 포함되는지 확인하고 월 오름차순으로 반환한다. 예를 들어 `from=2027-01-15&to=2027-03-31`이면 1월 정산은 제외되고 2·3월 정산이 대상이다. 한 달을 조회하려면 월의 1일을 범위에 포함한다.

```http
GET /api/v1/profile/host/settlements?from=2027-01-01&to=2027-03-31
```

관리자 목록은 `month=2027-01`처럼 월 하나를 지정하고 호스트 ID 오름차순으로 반환한다. `status`는 대문자 `PENDING`, `PAID`이며 생략하거나 빈 값이면 전체 상태다. 조회만으로 원장을 새로 집계하지 않는다. 두 목록 모두 결과가 없으면 `{"success":true,"data":[]}`다.

정산 요약은 기간 제한 없이 **저장된 정산 전체**의 `payout_amount`를 상태별로 합산한다. `pending_count`·`paid_count`는 예약 건수가 아닌 정산 레코드 수다. PENDING에는 현재 월 등 아직 마감되지 않은 달도 포함될 수 있다. 정산이 없으면 다음과 같다.

```json
{
  "success": true,
  "data": {
    "pending_payout_total": 0,
    "pending_count": 0,
    "paid_payout_total": 0,
    "paid_count": 0
  }
}
```

## 금액과 집계 날짜

집계 월과 지급 가능 여부는 **UTC** 기준이다. 숙소 현지의 체크인·체크아웃 월이나 한국 시간으로 환산한 월을 사용하지 않는다.

| 응답 필드 | 의미 |
|---|---|
| `settlement_id` | 정산 상세·지급 처리 경로에 사용할 ID |
| `settlement_month` | 집계 월의 1일(`YYYY-MM-01`) |
| `gross_amount` | 해당 월에 생성된 `CONFIRM` 원장의 `amount` 합계 |
| `refund_amount` | `CANCEL`·`PARTIAL_CANCEL` 원장의 `cancel_amount` 합계. `canceled_at`의 날짜를 사용하고 없으면 원장 생성 날짜 사용 |
| `net_amount` | 매출 합계 − 환불 합계 |
| `commission_rate` | 정산에 저장된 수수료율. 기본 설정 `0.03`은 3% |
| `commission_amount` | 순금액 × 수수료율을 정수로 HALF_UP 반올림 |
| `payout_amount` | 순금액 − 수수료 |
| `status` | `PENDING`: 지급 처리 전, `PAID`: 지급 완료 상태 기록 |
| `settled_at` | 지급 완료 상태를 기록한 서버 UTC 시각(`Z`). 지급 전에는 `null` |

예를 들어 매출 150,000, 환불 20,000, 수수료율 0.03이면 순금액 130,000, 수수료 3,900, 지급액 126,100이다.

다른 달 매출에 대한 환불이 이번 달에 발생하면 순금액·수수료·지급액이 음수일 수 있다. 환불만 50이고 수수료율이 0.03이면 순금액 −50, 수수료 −2, 지급액 −48이다. 현재 구현은 이를 0으로 보정하거나 지급 완료 기록을 거절하지 않는다.

집계는 원장 금액을 그대로 더하며 통화별 분리·환산을 수행하지 않는다. 정산 응답에도 통화 필드가 없다.

## 생성·재집계와 기간 처리

월 생성·재집계는 동기식이다. 원장 집계 결과가 있는 호스트마다 월 정산을 만들고 상태를 PENDING으로 설정한다. 기존 PENDING은 현재 원장 금액과 수수료율로 갱신하며 이력을 남긴다. **PAID의 저장된 금액·상태·처리 시각은 재집계로 변경하지 않는다.**

현재·미래 월도 요청할 수 있다. 해당 월 원장이 없으면 새 정산이 만들어지지 않는다. 매월 1일 04:00 UTC의 자동 배치는 전월을 대상으로 같은 생성 처리를 호출한다.

```http
POST /api/v1/admin/settlements/generate?month=2027-01
POST /api/v1/admin/settlements/backfill?from=2027-01&to=2027-03
```

기간 처리는 양 끝 월을 포함해 순서대로 실행한다. **월마다 독립된 트랜잭션**이므로 뒤쪽 월에서 실패해도 앞서 완료한 월은 되돌리지 않는다. 지급된 정산은 각 월의 재집계에서도 유지한다.

같은 월의 동시 생성을 조정하는 잠금을 5초 안에 얻지 못하거나 잠금 대기가 중단되면 그 월을 건너뛴다. 이 경우에도 API는 200일 수 있다. 생성·기간 처리 응답은 `{"success":true}`이며 실행·건너뜀 건수나 작업 ID를 제공하지 않는다. **200만으로 해당 요청이 모든 월을 실제 집계했다고 판단하지 말고 관리자 월별 조회로 결과를 확인한다.**

## 지급 완료 기록

```http
POST /api/v1/admin/settlements/101/pay
```

UTC 기준 현재 월보다 이전 월의 PENDING 정산만 PAID로 변경한다. 당시 저장된 정산 금액을 사용하며 지급 처리 안에서 원장을 재집계하지 않는다. 월별 조회로 금액을 확인한 뒤 호출한다. 성공하면 `settled_at`과 상태 변경 이력이 기록되고 `{"success":true}`를 반환한다.

이미 PAID이면 409/S002, 아직 마감되지 않은 달이면 409/S003이다. 동시 지급 요청에서는 한 요청만 전환에 성공하며 나머지는 409/S002가 된다. 지급과 재집계는 같은 정산 행을 잠근 뒤 최신 상태를 확인해 지급 결과를 덮어쓰지 않는다.

이 API는 송금이나 입금 확인을 실행하지 않으며 PAID 응답만으로 외부 이체 완료를 증명하지 않는다.

## 상세 내역의 최신성

상세의 요약 금액은 저장된 정산 값이다. `items`는 **조회 시점의 결제 원장과 숙소의 현재 소유자**를 기준으로 숙소별 집계를 다시 계산하며 숙소 ID 오름차순이다. 숙소 이름도 현재 값이고 과거 데이터는 `null`일 수 있다. 내역이 없으면 빈 배열이다.

따라서 늦게 반영된 원장이나 숙소 소유권 변경이 있으면 `items`의 합계가 저장된 요약과 다를 수 있다. PAID 요약은 고정되지만 상세 내역을 당시 상태로 보관한 스냅샷은 아니다. 숙소별 내역에는 매출·환불·순금액만 있으며 수수료·지급액은 호스트 단위 요약에만 있다.

## 주요 오류

| 상태·코드 | 상황 |
|---|---|
| 400/C001 | 필수 쿼리 누락, 월 형식·연도 범위 오류, 시작이 종료보다 늦은 기간 |
| 400/C004 | 호스트 조회 날짜 해석 실패, 정산 ID의 64비트 정수 해석 실패, 잘못된 status 값 |
| 401/M004 | 세션 없음·만료 |
| 403/M006 | 관리자 API 호출 회원이 현재 활성 ADMIN이 아님 |
| 403/S004 | 다른 회원의 정산 상세 조회 |
| 404/S001 | 상세 조회·지급 처리 대상 정산 없음 |
| 409/S002 | 이미 지급 완료로 기록된 정산 |
| 409/S003 | UTC 기준 아직 마감되지 않은 달의 지급 처리 |
| 500/C003 | 그 밖의 서버 처리 오류 |
