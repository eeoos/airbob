# 쿠폰 발급·조회 운영과 스키마 전환

쿠폰 발급은 대리 키 재고 행과 `REPEATABLE_READ`로 확정한다. 공개 발급 API는
`POST /api/v1/coupons/{couponId}/issue` 하나이며, 기존 세션 인증을 유지한다.
조건부 UPDATE, RC, 복합 키 발급과 발급 비교용 API·fixture는 현재 앱에서 제거했다.

## 재고와 트랜잭션

- 발급 시작 전 쿠폰 수량만큼 `coupon_issue_unit`을 준비한다. PK는 `id`,
  `(coupon_id, unit_no)`는 유니크 키다. `stock_prepared_at`은 준비 완료 근거다.
- 쿠폰을 `FOR SHARE NOWAIT`로 읽고 준비·활성·발급 기간을 확인한다.
- `FOR UPDATE SKIP LOCKED`로 재고 하나를 확보하고, 해당 재고 삭제와 `member_coupon` 저장을
  한 트랜잭션에서 커밋한다. `UNIQUE(member_id, coupon_id)`와 전체 롤백으로 중복 발급과 재고 유실을 막는다.
  공유 발급 카운터는 갱신하지 않으며, 저장 실패·중복 발급이면 삭제도 롤백한다.
- 빈 조회나 재시도 가능한 DB 경합 이후에는 새 읽기 트랜잭션에서 중복·기간·잔여 재고를 확인한다.
  잔여 재고가 없으면 `409/CP002`, 남아 있으면 새 발급 트랜잭션으로 제한적으로 재시도한다.
  기본값은 최초 포함 최대 3회, 대기 1~5ms, 재시도 시간 예산 250ms다.
  시간 예산은 추가 시도의 중단 기준이며, 진행 중인 SQL을 250ms에 취소하는 타임아웃은 아니다.
  한도 소진 후에는 `503/CP012`를 반환하고 호출자가 다시 요청해야 한다.
- 발급 시작 후 증감·재준비는 허용하지 않는다. 사용 취소로 보유 쿠폰을 복원하는 것은
  발급용 재고를 다시 만드는 작업과 다르다.
- 캠페인 V1 조회는 목록 쿼리 안에서 `coupon_issue_unit`의 잔여 행을 `EXISTS`로 확인한다.
  시작 전에는 `UPCOMING`, 시작 후 유한 수량 쿠폰은 재고가 있으면 `OPEN`, 없으면 `SOLD_OUT`이다.
  과거 `total_quantity IS NULL` 데이터는 시작 후 `OPEN`으로 표시하는 기존 조회 계약을 유지한다.
  발급 건수를 집계하거나 재고 존재 여부를 API 필드로 노출하지 않는다. 일반 조회로 상태만 표시하며,
  실제 발급 가능 여부는 발급 트랜잭션에서 다시 확인한다. 캠페인·보유 쿠폰 목록은 아래 커서 계약을 사용한다.

## 쿠폰 목록 페이지네이션

두 목록 API는 `@CursorParam`으로 `size`와 `cursor`를 받는다. `size` 기본값은 20, 허용 범위는
1~50이다. 첫 요청에서는 `cursor`를 생략한다. 파라미터 없는 요청도 전체 목록이 아닌 첫 20개만
반환하므로, 프론트는 `data.page_info.has_next`가 참이면 `next_cursor`를 다음 요청의 `cursor`로
전달해야 한다. URL 파라미터 인코딩은 적용하되 커서 내용을 해석하거나 직접 생성하지 않는다.

| API | 정렬 | 서버 내부 커서 경계 |
| --- | --- | --- |
| `GET /api/v1/coupons` | `coupon.issue_start_at DESC, coupon.id DESC` | `lastIssueStartAt` + 쿠폰 ID |
| `GET /api/v1/members/me/coupons` | `member_coupon.created_at DESC, member_coupon.id DESC` | `lastCreatedAt` + 회원 쿠폰 ID |

내 쿠폰의 정렬 경계는 `member_coupon.id`다. 기존 응답 항목의 `coupon_id`는 쿠폰 자체의 ID이므로
커서 경계로 사용하지 않는다. 두 API의 커서를 서로 바꾸어 쓰지 않는다.

응답 `data`에는 기존 `infos`와 `page_info`가 함께 들어간다. `current_size`는 실제 반환 항목 수다.
마지막 페이지는 `has_next=false`, `next_cursor=null`이며 빈 결과는 다음과 같다.

```json
{
  "infos": [],
  "page_info": {
    "has_next": false,
    "next_cursor": null,
    "current_size": 0
  }
}
```

페이지는 요청 시점의 현재 데이터를 읽는다. 캠페인 종료·활성 상태 변경으로 목록에서 빠지거나,
발급 시작 전 기간 수정으로 정렬 위치가 바뀔 수 있으므로 여러 요청에 걸친 스냅샷을 보장하지 않는다.
새 발급 내역 등 최신 목록은 커서 없이 다시 조회한다. 기존 발급·사용 상태 판정과 UTC `Instant`
응답은 유지하며, 날짜 표시와 커서의 시간 정밀도는 [쿠폰 시간 계약](coupon-time-contract.md)을 따른다.

## 준비·수량 변경

새 쿠폰은 양의 유한 수량만 허용한다. 과거 nullable 수량은 마이그레이션 호환용으로 읽는다.

관리 작업은 쿠폰 행을 먼저 `FOR UPDATE`로 잠근다. 시작 전이며 발급 내역이 없을 때만 허용한다.
최초 준비는 unit 생성과 `stock_prepared_at` 기록을 함께 커밋한다.
시작 후 증감·재입고를 허용하지 않고, 준비 재호출로 소비된 재고를 복원하지 않는다.

| 상태 | 목표 수량 M으로 변경 |
|---|---|
| 미준비 | 총수량만 변경 |
| 준비 완료·증량 | N+1~M번 unit 추가와 총수량 변경을 함께 커밋 |
| 준비 완료·감량 | `unit_no > M` 삭제와 총수량 변경을 함께 커밋 |
| 폐기 | 시작 전·발급 내역 없음을 확인하고 미발급 unit 정리 |

변경 건수가 기대와 다르거나 작업이 실패하면 전체를 롤백한다.

## V29·V30 전환 이력

V29는 MySQL unit과 불변 발급 전략을 도입하고 준비 시각 컬럼을 변경한다.
구 Lua writer를 중단하고 기존 Redis 준비값·회원 쿠폰·캠페인 상태를 확인한 뒤 전환한다.
기존 Redis 준비 시각만으로 MySQL 재고 준비를 판정하거나 발급 중인 캠페인을 자동 재준비하지 않는다.
V29 이후 Lua 바이너리로 되돌리지 않는다.

V30은 쿠폰 업무 시각을 UTC로 변환한다. 이전 reader/writer를 중단하고 함께 전환하는 절차는
[쿠폰 시간 계약](coupon-time-contract.md)에 정리했다. 기존 마이그레이션은 수정하지 않는다.

## V31 적용

1. DB를 백업하고 구버전 앱을 정지한다. 쿠폰 발급·관리뿐 아니라 쿠폰 엔티티를 읽는 예약·결제
   경로도 이전 컬럼을 참조하므로 구버전과 혼합 배포하지 않는다.
2. `issue_strategy='DB'`인 활성·미종료 캠페인을 정리한다. V31은 해당 캠페인이 있으면
   어떤 재고도 옮기기 전에 실패한다. 카운터에서 재고 행을 자동 생성하지 않는다.
3. V31은 복합 키 테이블에 실제로 남아 있는 `(coupon_id, unit_no)`만 대리 키 테이블로 복사한다.
   기존 대리 키의 ID와 재고, 발급된 회원 쿠폰, 쿠폰 설정·준비 시각을 보존한다.
   이전 복사가 끝난 동일한 재고 행은 중복 생성하지 않는다.
4. 복사 후 `coupon_issue_unit_composite`와 `coupon.issue_strategy`, `coupon.issued_quantity`를
   제거한다. V29·V30 파일과 적용 이력은 수정하지 않는다. 과거 nullable 총수량은 보존하되
   신규 생성과 발급에는 계속 양수 유한 수량을 요구한다.
5. V31 호환 앱으로 시작하고 발급·품절·중복·경합 응답과 재고 보존을 확인한다.
   이전 바이너리로 롤백하지 않는다. 현재 앱에는 `coupon-performance`를 포함한 실험 전용 프로필이 없다.

전략과 재고 테이블의 소유가 어긋나거나, 발급 이력이 없는 미래 캠페인에 레거시 발급 카운터가
남아 있으면 V31 사전 검사가 실패한다. 상태를 조사한 뒤 정리하며 무조건 카운터를 0으로 바꾸지 않는다.
MySQL DDL은 전체 마이그레이션을 하나의 트랜잭션으로 롤백하지 않는다. 복사 또는 DDL 이후 오류가
발생하면 앱을 정지한 상태에서 실제 스키마와 재고를 확인하고 남은 단계를 복구한다. 확인 없이
Flyway 성공 이력을 추가하거나 이전 앱을 재시작하지 않는다.

## V32 적용

V32는 보유 쿠폰 정렬의 필수 값인 `member_coupon.created_at`을 `DATETIME(6) NOT NULL`로 바꾸고,
`member_coupon(member_id, created_at DESC, id DESC)`와
`coupon(is_active, issue_start_at DESC, id DESC)` 인덱스를 추가한다. 기존 쿠폰·회원 쿠폰·재고와
UTC 감사 시각의 값은 변경하지 않는다.

1. 배포 전에 `member_coupon.created_at IS NULL`인 행을 확인한다. 누락된 시각은 신뢰할 수 있는
   실제 발급 이력에 근거해 복구하고 근거를 남긴다. 현재 시각, `updated_at`, 캠페인 시작 시각을
   일괄 대입하거나 알 수 없는 시각을 추측하지 않는다. 근거가 없으면 전환을 보류한다.
2. 백업 후 쿠폰 writer를 중지하고 누락 여부를 다시 확인한다. 원시 SQL로 발급 행을 넣는 도구도
   실제 발급 시각을 UTC로 기록해야 한다. V32 사전 검사는 writer를 차단하는 DB fence가 아니다.
3. V32를 적용한다. NULL이 하나라도 있으면 테이블 변경 전에
   `Reconcile member_coupon.created_at from trusted issuance evidence before V32`로 실패한다.
   자동 보정은 수행하지 않는다. 실패했으면 실제 데이터·스키마·Flyway 이력을 확인하고 원인을
   해결한 뒤 실패 이력을 복구하고 다시 적용한다. MySQL DDL의 부분 성공 여부를 확인하지 않고
   마이그레이션 완료를 기록하지 않는다.
4. 페이지네이션 대응 프론트와 백엔드를 함께 반영하고 첫 페이지·다음 페이지·마지막 페이지,
   기존 UTC 날짜와 발급 동작을 확인한다. 파라미터 없는 목록이 첫 20개로 바뀌는 점을 검증한다.

실제 MySQL 마이그레이션 테스트는 누락된 시각에 대한 사전 실패, 기존 행과 마이크로초 보존,
인덱스 컬럼 순서·방향, 이후 NULL 입력 거부를 검증한다. V1~V31과 과거 실험 데이터셋은 수정하지 않는다.

## 관측과 실험 이력

Grafana의 `Airbob - Coupon Issuance`는 성공·전체 결과, 발급 시도, 재시도 사유, 커넥션 풀을
구분해 보여준다. 과거 시계열과의 연속성을 위해 메트릭의 `strategy=skip_surrogate_rr` 라벨은
상수로 유지하며, 호출 코드의 전략 인자와 대시보드의 전략 선택기는 제거했다.

[AWS 결과 요약](../performance/coupon.md)을 유지하며,
원본 자료와 당시 실행 기록은 결과 문서의 보관본 링크에서 확인한다.
당시 앱 소스는 `43edf992227af2ae628ac0d83815c56722cf34b8`, 스키마는 V30이다.
[과거 실행기](../../load-test/k6/coupon/MEASUREMENT.md)는 해당 소스와 별도 V30 DB에서 사용한다.
이번 정리 후 앱을 당시 이미지와 동일한 측정 대상이라고 표현하지 않는다.

실제 MySQL 테스트에서 동시 발급·마지막 재고 경합·중복 요청·관리 작업 롤백을 검증한다.
과거 전략별 API와 비교 기준은 [쿠폰 실험 이력](../performance/history/coupon-local-results.md#당시-발급-비교-계약)에 보존한다.
