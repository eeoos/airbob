# AI 리뷰 기록

AI가 작성한 변경을 다른 AI가 리뷰한 결과와 판정을 남긴다.
- 리뷰어가 따르는 기준: [AI 코드 리뷰 기준](code-review.md)
- 검증 장치 전체: [AI 변경 검증](ai-change-verification.md)

## 방식

| 단계 | 리뷰어 | 시점 | 실행 |
|---|---|---|---|
| PR 전 | Codex(다른 계열 모델) | 커밋과 로컬 테스트를 마친 뒤 push 전 | 로컬 `codex exec`, `.claude/skills/pr-ai-review` |
| PR 후 | Claude | 초안이 아닌 PR을 열거나 다시 열 때, 초안을 준비 완료로 바꿀 때. 다시 볼 때는 `claude-review` 라벨 | PR의 `.github/workflows/claude-review-request.yml`(권한 없음)이 끝나면, main의 `.github/workflows/claude-review.yml`이 main의 `scripts/ci/claude_review.py`와 기준으로 리뷰한다(Messages API 1회, 도구 없음) |

- Codex를 먼저 둔다. 작성자와 계열이 다른 모델이 작성자의 사각지대를 가장 많이 찾기 때문이다.
- 리뷰어는 고치지 않는다. 작성자(Claude Code)가 지적마다 코드를 읽거나 재현해 확인한 뒤 판정하고 고친다.
  - 의도와 맥락을 가진 쪽이 고치고, 그 수정을 다시 다른 모델이 확인하는 구조다.
- 다른 모델이 다시 확인하는 경우는 두 가지다.
  - 고친 내용이 로직을 건드리면 그 수정분만 Codex로 다시 리뷰한다.
  - 넘김·오탐으로 판정한 지적은 그 근거를 Codex에게 보여 주고 동의하는지 묻는다. 작성자가 자기 코드를 방어하는 쪽으로 판정하는 편향을 막기 위해서다. 의견이 갈리면 사용자가 정한다.
- 수정분 재리뷰는 최대 2회다. 재리뷰 1은 첫 리뷰의 심각도와 관계없이 로직을 고쳤으면 하고, 재리뷰 2는 재리뷰 1에 필수가 있을 때만 한다. 2회째에도 필수가 나오면 멈추고 사용자에게 묻는다. 고칠 때마다 새 경계 조건이 생겨 끝없이 이어질 수 있기 때문이다.
- Claude 리뷰는 PR당 1회다. Claude 지적을 고친 부분은 Codex가 다시 본다. 라벨로 다시 돌리는 것은 실행 실패, 리뷰 뒤의 큰 설계 변경, 리뷰 과정 자체를 다듬는 PR에서 사용자가 원할 때뿐이다.
  - 근거: 이 도입 PR에서 Claude 리뷰를 세 번 돌렸더니 필수는 매번 0건이었는데, 실제 결함이 1~2건씩 계속 나왔다. 그 결함은 주로 직전 수정 근처에서 나왔다.

| 판정 | 기준 |
|---|---|
| 고침 | 사실로 확인했고 이 PR에서 고쳤다 |
| 보류 | 사실이지만 이 PR 범위 밖이다. 후속 작업으로 남긴다 |
| 넘김 | 사실이지만 이 저장소에서는 일어나지 않거나 영향이 없다. 비현실적인 전제(API 계약 위반, 러너·플랫폼의 비정상 동작, 강제 종료 타이밍, 극단적인 입력)가 필요한 지적도 넘긴다. 사유를 적는다 |
| 오탐 | 확인해 보니 사실이 아니다. 근거를 적는다 |
| 사용자 결정 | 계약(API·DB·잠금 순서)을 바꾸거나 기존 규칙과 충돌한다. 작성자가 멈추고 묻는다 |

## 지표

- **정확도:** (지적 − 오탐) ÷ 지적
- **실제 결함:** 맞는 지적 중 작성자가 놓친 결함(버그·보안·실패 경로)의 수
  - 이 저장소에서 실제로 일어날 수 있는 것만 센다.
  - API 계약 위반(예: 정수 필드에 `null`)이나 러너 파일 쓰기 실패처럼 비현실적인 전제가 필요한 경로는 고쳤더라도 세지 않는다.
- **2단계 추가 발견:** Claude가 찾은 맞는 지적 중 Codex가 찾지 못한 것의 수
- **비용과 시간:** Claude 단계는 리뷰당 비용을 적는다. Codex는 구독이라 시간만 적는다.

PR 10개가 쌓이면 2단계 추가 발견과 비용을 보고 Claude 단계를 유지할지 다시 판단한다.
넘김과 오탐의 사유가 반복되면 그 사유를 리뷰 기준의 "지적하지 않는 것"에 더한다.
