# AI가 만든 변경을 검증하는 장치

airbob의 코드 변경과 PR 상당수는 AI 코딩 에이전트(Claude Code)가 작성한다. 이 문서는 그 결과물을 무엇으로
검증하는지 정리한다. 원칙은 하나다.

**AI의 설명("통과했다", "안전하다")을 믿지 않고, 테스트·계약 검사·측정이 만든 사실로 확인한다.**

다른 AI의 리뷰도 같은 원칙을 따른다. 지적은 코드를 읽거나 재현해 사실로 확인한 뒤에만 고친다.

## 검증 흐름

```
편집 ─ 컴파일 훅 ─ 응답 종료 전 테스트 훅 ─ Codex 리뷰 ─ PR CI ─ PR 점검 보고서·Claude 리뷰 ─ CI result(필수) ─ main CD
       (로컬)       (로컬, 변경 영역)       (로컬, push 전) (계약 검사, 빌드·테스트, ArchUnit, OpenAPI 스냅샷)
```

- 로컬 훅은 에이전트가 편집할 때마다 바로 실패를 돌려준다. 그래서 컴파일 오류나 깨진 테스트가 PR까지 가지 않는다.
- 기계로 확인할 수 없는 결함은 두 단계 AI 리뷰가 찾는다. 먼저 작성자와 계열이 다른 Codex가 push 전에 보고, PR을 연 뒤 Claude가 다시 본다. 방식과 판정은 [AI 리뷰 기록](ai-review-log.md)에 있다.
- PR CI는 사람과 AI의 변경을 구분하지 않고 같은 검사를 한다.
- main CD는 같은 CI 정의를 다시 실행한 뒤에만 배포한다.

## 장치 목록

| 단계 | 장치 | 종류 | 실패하면 |
|---|---|---|---|
| 편집 직후 | `.claude/hooks/compile-on-edit.sh`: 편집한 Java 파일을 Spotless로 포매팅하고, 그 파일이 속한 모듈의 소스셋을 컴파일한다 | 테스트 | 에이전트에 컴파일 오류를 돌려준다 |
| 응답 종료 전 | `.claude/hooks/test-before-stop.sh`: 커밋하지 않은 변경이 있는 영역의 테스트와 ArchUnit, 바뀐 모듈의 `spotlessCheck`(포매팅 설정이 바뀌면 모든 모듈)를 실행한다 | 테스트 | 에이전트가 작업을 끝내지 못한다 |
| push 전 | Codex 리뷰(`.claude/skills/pr-ai-review`): 작성자와 계열이 다른 모델이 브랜치 diff를 [리뷰 기준](code-review.md)에 따라 리뷰한다 | 리뷰 | 작성자가 지적을 검증해 고치거나 사유를 남긴다 |
| PR CI | `scripts/ci/contracts.py`: 보관 부하 테스트 파일의 해시·모드, 적용된 Flyway 마이그레이션의 수정·삭제 | 계약 검사 | CI 실패 |
| PR CI | `scripts/ci/scope.py`와 `check_result.py`: 변경에 맞는 검사를 고르고, 선택한 검사가 실패·취소·누락되면 필수 검사 `CI result`를 실패시킨다 | 계약 검사 | CI 실패 |
| PR CI | 테스트 1,968개: core-api 1,865, API 문서 85, client 모듈 18 (2026-11-24 기준) | 테스트 | CI 실패 |
| PR CI | ArchUnit: 엄격 계층 규칙 10개, 동결 규칙 3개(기록된 위반 외에 새 위반이 생기면 실패), 코드 규칙 6개(main 5, 테스트 1, [코딩 컨벤션](coding-convention.md#코드-규칙)) | 계약 검사 | CI 실패 |
| PR CI | Spotless `spotlessCheck`: 네이버 컨벤션 포매팅, import 순서, static이 아닌 와일드카드 import 금지([코딩 컨벤션](coding-convention.md)) | 계약 검사 | CI 실패 |
| PR CI | OpenAPI 스냅샷(`verifyOpenApi`, operation 75개): 코드에서 만든 명세와 커밋된 스냅샷이 다르면 실패 | 계약 검사 | CI 실패 |
| PR CI | 쿼리 수 고정 테스트: 예약 상세 SQL 1개(`ReservationPaymentReadQueryIntegrationTest`), 숙소 상세 쿼리 수 등 | 측정 | CI 실패 |
| PR CI | 배포 계약 테스트: `OciDeploymentContractTest`, `MessagingDeploymentContractTest`, 모든 GitHub Action의 SHA 고정(`infra/aws/tests/image-publication-test.sh`) | 계약 검사 | CI 실패 |
| PR 댓글 | PR 점검 보고서(`scripts/ci/pr_report.py`, `pr_baseline.py`, `pr_comment.py`): CI 잡 결과, 모듈별 테스트, main 대비 테스트 증감, 계약 신호(API·마이그레이션·오류 코드·ArchUnit·보관 해시·설정·빌드), 바뀐 영역 | 측정 | 표시만 한다(⚠️) |
| PR 댓글 | Claude 리뷰(`.github/workflows/claude-review-request.yml` → `claude-review.yml`, `scripts/ci/claude_review.py`, main의 코드와 기준으로): 초안이 아닌 PR을 열거나 다시 열 때, 초안을 준비 완료로 바꿀 때, `claude-review` 라벨을 붙일 때 같은 기준으로 리뷰하고 요약 댓글을 단다 | 리뷰 | 표시만 한다. 작성자가 검증해 [AI 리뷰 기록](ai-review-log.md)에 판정을 남긴다 |

에이전트가 따를 영역 불변식은 `CLAUDE.md`와 `.claude/rules/*.md`에 둔다. 위 장치들은 그 불변식 중 기계로 확인할 수 있는 부분을 강제한다.
PR 보고서의 구조는 [실행 도구 안내](../../scripts/README.md#ci-검사-선택과-결과)를 본다.

## 비어 있는 곳

- **오류 코드:** 98개 중 49개는 어떤 테스트에서도 단언하지 않는다. 엔드포인트별 `@ApiErrors` 선언과 실제로 던지는 예외를 잇는 검사가 없다.
- **컨트롤러 테스트:** 컨트롤러 테스트가 없는 컨트롤러가 6개다. HTTP 계약 검사가 `ApiDocumentationTest` 한 파일에 몰려 있다. Spring REST Docs로 전환할 때 컨트롤러 테스트로 옮긴다.
- **문서의 코드 경로:** 문서 속 코드 경로와 클래스 이름이 실제와 맞는지 확인하는 검사가 없다. 패키지 이동 뒤 끊긴 링크를 사람이 읽다가 발견했다.
- **부하 테스트 결과:** 결과를 문서 표로 옮기는 일을 사람이 한다. 표의 숫자가 원본 측정값과 맞는지 확인하는 장치도 없다.

## 작업 원칙

- PR에는 실행 결과를 남긴다: 테스트 수, 실패 0, 스냅샷 불변, 측정값. "확인했다"는 말만 남기지 않는다.
- 추정은 추정이라고 쓴다. 확인한 뒤 틀렸으면 바로잡는다(위 사례).
- 계약을 바꾸는 결정(API, DB, 잠금 순서)은 사람이 한다.
- 검증 장치도 코드다. 테스트하고, 과거 이력으로 재현해 본 뒤 도입한다.
