# 회원 권한 승격·회수 기능 설계

## 목적

관리자가 활성 회원의 역할을 `MEMBER`와 `ADMIN` 사이에서 변경할 수 있게 한다. 역할 변경은 현재 세션에 즉시 반영되고, 변경 주체와 사유를 회원 이력에 남긴다. 관리자가 자기 관리자 권한을 회수해 관리 기능에 접근할 수 없게 되는 상황은 금지한다.

## 범위

- 관리자 전용 역할 변경 API 추가
- `MEMBER → ADMIN` 승격 및 `ADMIN → MEMBER` 회수
- 서비스 트랜잭션 안에서 호출 관리자 재검증
- 호출 관리자와 대상 회원에 대한 비관적 잠금
- 회원 역할 변경 도메인 메서드 추가
- SCD Type-2 회원 이력에 역할 변경 기록
- 요청 검증, 도메인 예외 및 API·서비스·통합 테스트 추가

다음 항목은 이번 범위에서 제외한다.

- 관리자/회원 목록 조회 화면용 API
- 비활성 회원의 역할 변경
- 역할 종류 추가 또는 세분화된 권한 체계
- 역할 변경 시 강제 로그아웃
- 관리자 비밀번호 재확인이나 별도 2차 인증
- Flyway 스키마 변경

## API 계약

### 역할 변경

```http
PATCH /api/v1/admin/members/{memberId}/role
Content-Type: application/json

{
  "role": "ADMIN",
  "reason": "운영 관리자 지정"
}
```

요청 필드:

- `role`: 필수. `ADMIN` 또는 `MEMBER`
- `reason`: 필수. 공백을 제외한 1~255자

호출 관리자 식별자는 요청 본문에서 받지 않고 `@CurrentMemberId`로 인증 컨텍스트에서 주입한다.

성공 응답은 HTTP 200과 변경 결과를 반환한다.

```json
{
  "success": true,
  "data": {
    "member_id": 10,
    "role": "ADMIN"
  }
}
```

동일한 역할을 다시 요청하면 멱등 성공으로 처리하며 새 이력은 생성하지 않는다.

## 구성 요소

### `MemberAdminController`

- `/api/v1/admin/members` 하위 관리자 API를 담당한다.
- `AdminAuthInterceptor`의 기존 `/api/v1/admin/**` 보호를 그대로 사용한다.
- 대상 회원 ID, 검증된 요청 DTO, `@CurrentMemberId` 호출 관리자 ID를 서비스로 전달한다.

### `MemberAdminService`

- 역할 변경 트랜잭션의 경계를 담당한다.
- 호출 관리자와 대상 회원을 ID 오름차순으로 비관적 잠금해 교차 권한 회수 요청의 교착 및 관리자 0명 상태를 방지한다.
- 잠금 이후 호출 관리자가 여전히 `ACTIVE + ADMIN`인지 다시 검증한다. 인터셉터 통과 직후 호출자 권한이 회수되는 TOCTOU 상황에서는 변경을 거부한다.
- 대상 회원은 `ACTIVE` 상태만 허용한다.
- 자기 자신에 대한 `ADMIN → MEMBER` 요청은 거부한다.
- 실제 역할이 바뀌는 경우에만 회원 엔티티와 이력을 변경한다.

### `Member`

- 외부에서 필드를 직접 수정하지 않고 `changeRole(MemberRole role)` 도메인 메서드로 역할을 변경한다.

### `MemberHistory`

- `ChangeType.ROLE_CHANGE`를 추가한다.
- 기존 현재 이력의 `validTo`를 닫고 변경된 역할을 가진 새 현재 스냅샷을 연다.
- 요청의 `reason`, JPA Auditing의 `historyCreatedBy`, 요청 컨텍스트의 출처와 IP를 기록한다.

## 잠금과 동시성

호출 관리자와 대상 회원이 다르면 두 회원 행을 항상 ID 오름차순으로 잠근다. 예를 들어 관리자 A가 B를 회수하는 요청과 B가 A를 회수하는 요청이 동시에 들어와도 동일한 잠금 순서를 사용한다. 먼저 완료된 요청이 한 관리자의 역할을 변경하면, 뒤 요청은 잠금 획득 후 호출자의 `ADMIN` 역할 재검증에서 실패한다.

자기 자신의 역할을 `ADMIN`으로 지정하는 멱등 요청은 한 행만 잠근다. 자기 자신의 역할을 `MEMBER`로 지정하는 요청은 정책상 거부한다.

## 세션 정책

세션에는 `memberId`만 저장하고 역할은 저장하지 않는다. `AdminAuthInterceptor`가 관리자 요청마다 DB에서 `ACTIVE + ADMIN`을 확인하므로 다음과 같이 동작한다.

- 승격: 기존 로그인 세션으로 다음 관리자 요청부터 접근 가능
- 회수: 기존 로그인 세션은 일반 회원 세션으로 유지되지만 다음 관리자 요청부터 403

역할 변경만으로 Redis 세션을 삭제하지 않는다.

## 예외 계약

- 인증되지 않은 호출: 기존 `M004`, HTTP 401
- 호출자가 활성 관리자가 아님: 기존 `M006`, HTTP 403
- 대상이 없거나 비활성: 기존 `M001`, HTTP 404
- `role` 누락·잘못된 enum·`reason` 검증 실패: 기존 `C001`, HTTP 400
- 자기 관리자 권한 회수: 신규 `M007 MEMBER_ROLE_CHANGE_NOT_ALLOWED`, HTTP 409

## 테스트 전략

### 컨트롤러 테스트

- 정상 승격·회수 요청과 응답 계약
- 누락되거나 잘못된 역할
- 공백 또는 255자 초과 사유
- 자기 권한 회수 예외 응답

### 서비스 테스트

- 활성 회원 승격 및 회수
- 동일 역할 요청의 멱등 처리와 이력 미생성
- 자기 관리자 권한 회수 거부
- 대상 회원 없음·비활성 거부
- 잠금 이후 호출자가 관리자가 아니면 거부
- 역할 변경 시 이전 이력 종료 및 `ROLE_CHANGE` 스냅샷 생성

### 통합 테스트

- 기존 세션으로 승격 직후 관리자 API 접근 가능
- 회수 직후 기존 세션으로 관리자 API 접근 불가
- 두 관리자가 서로의 권한을 동시에 회수해도 최소 한 명의 활성 관리자가 남음

## 완료 조건

- 승인된 API 계약과 예외 코드가 자동 테스트로 검증된다.
- 호출자·대상 상태와 자기 권한 회수 정책이 서비스 트랜잭션 안에서 보장된다.
- 역할 변경과 SCD Type-2 회원 이력이 함께 커밋된다.
- 역할 변경 직후 기존 세션의 관리자 접근 결과가 DB 역할과 일치한다.
- 관련 단위·통합 테스트와 `git diff --check`가 통과한다.
