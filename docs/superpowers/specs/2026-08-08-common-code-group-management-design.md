# 공통 코드 그룹 관리 설계

## 목표

관리자가 공통 코드 그룹을 조회·생성·수정할 수 있게 한다. 새 그룹은 DB 카탈로그에 등록되어 기존 공통 코드 관리 API와 공개 조회 API에서 사용할 수 있지만, 특정 화면이나 비즈니스 필드에 자동으로 연결되지는 않는다.

삭제 API와 별도의 소프트 삭제 상태는 이번 범위에 포함하지 않는다. 그룹의 `is_active`를 `false`로 바꾸면 신규 조회·검증에서 그룹 전체를 사용 중지할 수 있다.

## 접근 방식 비교

### 정적 그룹만 유지

`CommonCodeGroups`에 선언된 `AMENITY_TYPE`, `ACCOMMODATION_TYPE`만 허용하고 그룹 생성 API를 제공하지 않는다. 구현은 단순하지만 관리자가 그룹을 생성한다는 요구를 충족하지 못한다.

### DB 기반 동적 그룹 관리 — 채택

`common_code_group`을 그룹 존재 여부의 기준으로 사용한다. `CommonCodeGroups`는 백엔드 도메인 코드가 사용하는 상수만 제공하고, 공개 조회 허용 여부를 제한하는 목록으로 사용하지 않는다.

이 방식은 새 그룹을 배포 없이 등록하고 기존 `GET /api/v1/common-codes/{group}` 및 관리자 코드 API에서 사용할 수 있게 한다. 다만 프론트 선택 항목이나 백엔드 저장 필드가 새 그룹을 사용하려면 해당 소비자 작업은 별도로 필요하다.

### 화면까지 자동 연결하는 메타데이터 시스템

그룹에 화면 위치, 입력 타입, 대상 필드 같은 메타데이터를 추가해 프론트가 동적으로 폼을 구성할 수 있다. 현재 요구보다 범위와 결합도가 크므로 제외한다.

## 관리자 API

모든 API는 기존 `AdminAuthInterceptor`가 보호하는 `/api/v1/admin/**` 아래에 둔다.

### 그룹 목록 조회

```http
GET /api/v1/admin/common-code-groups
```

활성·비활성 그룹을 모두 `groupCode` 오름차순으로 반환한다.

### 그룹 생성

```http
POST /api/v1/admin/common-code-groups
```

요청 예시:

```json
{
  "groupCode": "PAYMENT_METHOD",
  "groupName": "결제 수단",
  "description": "결제 화면에서 사용하는 결제 수단",
  "isActive": true
}
```

- `groupCode`와 `groupName`은 필수다.
- `groupCode`는 앞뒤 공백을 제거하고 `Locale.ROOT` 기준 대문자로 정규화한다. 영문자로 시작하고 영문자·숫자·밑줄만 허용하며 최대 길이는 50자다.
- `groupName`은 최대 100자, `description`은 최대 255자다.
- `isActive`를 생략하면 `true`를 사용한다.
- 이미 존재하는 `groupCode`이면 `409 Conflict`를 반환한다.
- 성공 응답은 `201 Created`다.

### 그룹 수정

```http
PATCH /api/v1/admin/common-code-groups/{groupCode}
```

요청 예시:

```json
{
  "groupName": "결제 방식",
  "description": "변경된 설명",
  "isActive": false
}
```

- `groupName`, `description`, `isActive`는 부분 수정한다.
- null인 필드는 기존 값을 유지한다.
- 전달된 `groupName`은 공백만으로 구성할 수 없고 최대 100자이며, `description`은 최대 255자다. 빈 문자열의 `description`은 설명을 비우는 값으로 허용한다.
- 식별자인 `groupCode`는 수정할 수 없다. 코드 변경이 필요하면 새 그룹을 만들고 기존 그룹을 비활성화한다.
- 존재하지 않는 그룹이면 기존 `CC001`, `404 Not Found`를 반환한다.

### 응답

목록·생성·수정은 다음 필드를 공통으로 사용한다.

```json
{
  "groupCode": "PAYMENT_METHOD",
  "groupName": "결제 수단",
  "description": "결제 화면에서 사용하는 결제 수단",
  "active": true
}
```

## 애플리케이션 구조

- `CommonCodeAdminController`에 그룹 목록·생성·수정 엔드포인트를 추가한다.
- 그룹 요청과 응답은 코드 요청·응답과 구분되는 DTO로 둔다.
- `CommonCodeAdminService`가 정규화, 중복 검사, 조회, 생성 및 트랜잭션 내 부분 수정을 담당한다.
- `CommonCodeGroup`에 이름·설명·활성 상태를 변경하는 메서드를 추가한다.
- `CommonCodeGroupRepository`는 그룹 코드 순서의 목록 조회를 제공한다.
- 그룹 생성에 새 테이블이나 컬럼이 필요하지 않으므로 Flyway 마이그레이션은 추가하지 않는다.

## 공개 조회와 캐시

현재 `CommonCodeGroups.isSupported()`의 고정 목록 검증은 동적 그룹 생성과 충돌하므로 제거한다. `AMENITY_TYPE`, `ACCOMMODATION_TYPE` 상수는 숙소 도메인의 매직 스트링 방지 용도로 유지한다.

Caffeine 캐시 로더는 DB에서 그룹을 조회해 다음 상태를 캐시한다.

- 그룹 없음: 다음 공개 조회에서 `CC001`, 404 반환
- 비활성 그룹: 빈 코드 목록 반환
- 활성 그룹: 활성 공통 코드 목록 반환

존재하지 않는 그룹도 짧게 상태를 캐시해 같은 잘못된 키가 반복될 때마다 DB를 조회하지 않게 한다. 캐시는 기존 정책인 `maximumSize(100)`과 쓰기 후 TTL 1분을 유지한다. 그룹 생성·활성 상태 변경도 다른 공통 코드 변경과 동일하게 인스턴스별로 최대 1분 후 반영될 수 있다.

임의의 서로 다른 그룹 키를 계속 요청하는 공격은 캐시 크기로 메모리 사용을 제한하지만 DB 조회 자체를 완전히 막지는 않는다. 이는 공통 코드 모듈이 아닌 API rate limit 영역으로 보고 이번 범위에서 다루지 않는다.

## 삭제와 비활성화

그룹 삭제 API는 제공하지 않는다. 그룹을 물리적으로 삭제하려면 하위 공통 코드와 기존 비즈니스 데이터의 사용 여부를 함께 판단해야 한다. 현재 숙소 유형과 편의시설은 공통 코드 값을 FK 없이 문자열로 저장하므로 일반적인 그룹 삭제는 안전하지 않다.

`is_active=false`는 삭제가 아니라 신규 사용을 막는 운영 상태다. 그룹과 하위 코드는 DB에 남아 관리자 화면과 감사 정보에서 확인할 수 있고 필요하면 다시 활성화할 수 있다.

## 오류 처리

- 존재하지 않는 그룹 조회·수정: 기존 `CC001`, 404
- 중복 그룹 생성: 새 그룹 중복 오류 코드, 409
- 필수 생성 값 누락 또는 형식 오류: 기존 검증 오류 응답, 400
- 예상하지 못한 DB 오류: 기존 전역 예외 처리 계약 유지

## 테스트

TDD로 다음 동작을 먼저 고정한다.

1. 관리자 그룹 목록이 활성·비활성 그룹을 그룹 코드 순으로 반환한다.
2. 그룹 생성이 코드를 대문자로 정규화하고 기본 활성값을 적용한다.
3. 중복 그룹 생성이 409 예외를 발생시킨다.
4. 그룹 수정이 전달된 필드만 변경하며 그룹 코드는 유지한다.
5. 존재하지 않는 그룹 수정이 `CC001`을 발생시킨다.
6. DB에 새로 등록한 그룹의 공통 코드를 공개 API 서비스에서 조회할 수 있다.
7. 존재하지 않는 동적 그룹은 404이며 동일 키의 반복 조회가 캐시 정책을 따른다.
8. 비활성 그룹은 공개 조회와 저장 전 검증에서 사용할 수 없다.

관련 단위 테스트와 MySQL Testcontainers 통합 테스트를 모두 실행해 Flyway 스키마, JPA 매핑 및 Caffeine 로딩을 함께 검증한다.

## 범위 제외

- 그룹 또는 공통 코드의 하드 삭제·소프트 삭제
- `groupCode` 변경
- 새 그룹을 특정 프론트 화면이나 도메인 필드에 자동 연결
- 그룹별 권한, 다국어 라벨, 버전 관리
- Redis 분산 캐시 또는 인스턴스 간 즉시 무효화
