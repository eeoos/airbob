# AI 코드 리뷰 절차

리뷰어는 [리뷰 기준](../../../docs/development/code-review.md)을 따른다. 판정과 지표의 뜻은 [AI 리뷰 기록](../../../docs/development/ai-review-log.md)에 있고, 결과도 그 파일에 남긴다.

**역할:** 리뷰어(Codex, Claude 리뷰)는 읽기 전용으로 지적만 한다. 아래의 검증, 판정, 수정, 기록은 모두 작성자, 곧 이 스킬을 실행하는 Claude Code 세션이 한다. 단 판정은 고치기 전에 사용자에게 보여 확인받는다(A.3).

## A. PR 전: Codex 리뷰

1. **범위를 정한다.**
   - base는 PR이 향할 브랜치다. 보통 `origin/main`이다. 이전 PR 브랜치 위에 쌓았으면 그 브랜치다.
   - `git diff --stat <base>...HEAD`로 확인한다.
   - 문서(`docs/`, `*.md`)만 바뀌었으면 건너뛰고, PR 본문에 "문서만 바뀌어 생략"이라고 쓴다. 단 에이전트 규칙(`CLAUDE.md`, `AGENTS.md`, `.claude/`)과 리뷰 기준(`docs/development/code-review.md`)은 문서로 보지 않는다.
2. **Codex를 실행한다.**
   - Claude 샌드박스 밖에서 실행한다(`dangerouslyDisableSandbox`). 네트워크와 `~/.codex`가 필요하다.
   - 몇 분 걸리므로 백그라운드로 돌리고, 시작과 끝 시각을 적는다.

   ```
   mkdir -p build/review
   codex exec -s read-only --ephemeral -o build/review/codex-<head 8자리>.md "<지시문>" < /dev/null
   ```

   지시문:
   > 이 저장소의 `<base>...HEAD` 변경을 리뷰하라. `git log`와 `git diff <base>...HEAD`로 변경을 보고, 필요하면 저장소 파일을 읽어라. 파일은 수정하지 마라. 기준은 docs/development/code-review.md다. 변경 의도: <PR 요약 한두 줄>.

   - `codex exec review --commit`은 지시문과 함께 쓸 수 없다. 그래서 일반 `exec`를 쓴다.
   - `< /dev/null`로 입력을 닫는다. 백그라운드에서 입력이 열려 있으면 `Reading additional input from stdin...`에서 멈춘다.
   - 모델과 추론 수준은 `~/.codex/config.toml`을 따른다. 기록할 때 실제 값을 적는다.
3. **작성자가 지적마다 검증하고 판정한다.**
   - 코드를 읽고, 가능하면 테스트나 메모리 입력으로 재현한다.
   - 판정: 고침, 보류, 넘김, 오탐, 사용자 결정
   - 계약(API, DB, 잠금 순서)을 바꾸거나 기존 규칙과 충돌하는 지적은 작성자가 판정하지 않고 "사용자 결정"으로 둔다.
   - **사실이어도 고칠 가치가 있는지 따진다.**
     - 비현실적인 전제가 있어야 일어나는 지적은 넘긴다. 예: API 계약 위반, 러너·플랫폼의 비정상 동작, 강제 종료 타이밍, 극단적인 입력. 리뷰 기준의 "지적하지 않는 것"과 같다.
     - 권장·참고를 고치는 데 코드가 늘어나면 넘김이나 보류도 함께 따진다. 고친 코드는 다음 리뷰의 새 표면이 되기 때문이다.
   - **고치기 전에 판정을 사용자에게 보여 주고 멈춘다.** 작성자가 자기 코드를 판정하는 편향은 Codex 교차 확인만으로 다 막지 못하고, 어디까지 고칠지는 저장소 주인이 정할 가치 판단이기 때문이다.
     - 리뷰 회차(첫 리뷰, 재리뷰, Claude 리뷰)마다 한 번 멈춘다. 지적이 0건이면 멈추지 않고 결과만 알린다.
     - 아래 표를 보여 준다. 고칠 방법·규모에는 바꿀 파일과 늘어날 코드의 대략을 적는다.

       | # | 심각도 | 지적(한 줄) | 판정 | 근거 | 고칠 방법·규모 |
       |---|---|---|---|---|---|

     - 사용자의 답("진행", 또는 지적별로 판정을 바꿈)으로 판정을 확정한 뒤 A.4로 간다. 사용자가 바꾸거나 정한 판정은 기록의 근거에 "사용자 결정"이라고 적는다.
4. **작성자가 고친다.**
   - 확정한 판정이 고침인 것은 작성자가 테스트와 함께 고쳐 커밋한다.
   - 수정이 로직(main 코드, 스크립트, 워크플로)을 건드리면 수정 커밋만 Codex로 다시 리뷰한다. 같은 명령에서 base를 수정 직전 커밋으로 둔다.
   - 넘김이나 오탐으로 판정한 지적이 있으면, 같은 재리뷰 지시문에 판정 근거를 붙여 Codex가 동의하는지 묻는다. 작성자가 자기 코드를 방어하는 쪽으로 판정하는 편향을 막기 위해서다.
     - Codex가 반례를 들면 다시 검증한다.
     - 그래도 의견이 갈리면 사용자에게 묻는다.
   - 문서나 테스트만 고쳤고 넘김·오탐도 없으면 다시 리뷰하지 않는다.
   - 다시 리뷰한 결과는 기록에 따로 한 줄로 남긴다.
   - **재리뷰를 멈추는 기준.** 고칠 때마다 새 경계 조건이 생겨 끝없이 이어질 수 있으므로 상한을 둔다.
     - 재리뷰는 직전 수정분만 본다.
     - 재리뷰 1은 첫 리뷰(Codex든 Claude든)의 심각도와 관계없이, 고친 내용이 로직을 건드리면 한다.
     - 재리뷰 2는 재리뷰 1에 필수가 있을 때만 한다. 직전 재리뷰가 권장·참고만 냈으면, 재리뷰 없이 고치거나 넘기거나 보류하고 멈춘다.
     - 재리뷰는 최대 2회다. 2회째에도 필수가 나오면 더 돌지 않고 사용자에게 묻는다. 계속 새 결함이 나온다는 것은 땜질보다 설계를 다시 볼 신호일 수 있다.
5. **기록한다.**
   - `docs/development/ai-review-log.md`에 한 줄을 추가하고 브랜치에 커밋한다.
   - PR 본문에 아래 절을 넣는다. 재리뷰도 한 행과 접은 표 하나를 더한다. 기록 파일은 리뷰마다 한 줄 요약이라, 지적별 판정은 이 표에만 남는다.

   ```
   ## AI 리뷰
   | 단계 | 리뷰어 | 범위 | 지적 | 고침 | 보류 | 넘김 | 오탐 | 실제 결함 |
   |---|---|---|---:|---:|---:|---:|---:|---:|
   | PR 전 | Codex <모델>, <수준> | `<base>...<head>` | … | … | … | … | … | … |

   <details><summary>지적별 판정: PR 전</summary>

   | # | 심각도 | 지적 | 판정 | 실제 결함 | 근거 |
   |---|---|---|---|:-:|---|
   </details>
   ```

## B. PR 후: Claude 리뷰

1. **실행을 기다린다.**
   - 초안이 아닌 PR을 열거나 다시 열 때, 초안을 준비 완료로 바꿀 때 `claude-review-request.yml`이 PR에서 돈다. 그 실행이 끝나면 main의 `claude-review.yml`이 `workflow_run`으로 `scripts/ci/claude_review.py`를 돌린다. Messages API 1회, 도구 없음이다. 초안 PR은 준비 완료로 바꿔야 돈다.
   - 리뷰는 main에 있는 워크플로, 스크립트, 리뷰 기준으로 돈다. 이것들을 바꾼 PR도 바꾸기 전 버전으로 리뷰되고, 바뀐 것은 머지 뒤 다음 PR부터 적용된다.
   - PR을 만들 때 `claude-review` 라벨을 함께 붙이지 않는다. `opened`와 `labeled`로 같은 커밋을 두 번 리뷰한다.
   - 리뷰를 받은 PR은 고치는 동안 초안으로 돌리거나 닫지 않는다. 초안을 준비 완료로 되돌리거나 다시 열면 라벨 없이 리뷰가 다시 돈다.
   - 먼저 요청 실행을 찾고, 그 ID로 리뷰 실행을 찾아 끝날 때까지 기다린다. 리뷰 실행은 브랜치가 main으로 찍히고, 이름 끝에 `(request <요청 실행 ID>)`가 붙는다.
     ```
     gh run list --workflow claude-review-request.yml --branch <브랜치> --json databaseId,headSha,conclusion
     gh run list --workflow claude-review.yml --event workflow_run --branch main \
       --json databaseId,displayTitle,status,conclusion \
       --jq '.[] | select(.displayTitle | endswith("(request <요청 실행 ID>)"))'
     ```
     - `--event workflow_run --branch main`은 빼지 않는다. 그래야 main의 워크플로가 만든 실행만 남는다. PR 브랜치에서 같은 파일명으로 돈 실행은 PR이 바꾼 워크플로일 수 있다.
     - 요청이 건너뛰어졌으면(초안, 다른 라벨) 리뷰도 돌지 않는다.
   - 요청은 성공했는데 리뷰 잡이 건너뛰어졌으면, 이벤트에 연결된 PR이 없거나 여럿인 경우다. 미완료로 기록하고 라벨로 다시 돌린다.
   - 실행이 취소(cancelled)되면 미완료로 보고 라벨로 다시 돌린다. 같은 PR의 리뷰 요청이 겹치면(예: 리뷰가 도는 동안 라벨을 다시 붙임) 대기 중이던 리뷰가 새 요청으로 바뀌며 취소될 수 있다.
2. **결과를 읽는다.** 판정에 쓰는 리뷰 본문은 PR 댓글이 아니라 **기다린 리뷰 실행의 로그**에서 읽는다.
   - 이유: 로그는 main의 워크플로가 남겨 PR이 손댈 수 없다. 반면 PR의 워크플로는 같은 마커와 실행 ID를 넣은 댓글을 `github-actions[bot]` 이름으로 달 수 있다. 댓글(`<!-- airbob-claude-review -->`로 시작, 인라인 댓글 없음)은 사람이 보는 사본이다.
   - 스크립트는 응답을 받으면 토큰 수를 출력하고, 리뷰 본문을 마커부터 `::***::` 줄(워크플로 명령을 다시 켠 줄)까지 출력한 뒤 게시한다.

     ```
     gh run view <실행 ID> --log \
       | awk -F'\t' '$2 == "Review with Claude" { sub(/^[^\t]*\t[^\t]*\t[^ ]+ ?/, ""); print }' \
       | sed -n '/^<!-- airbob-claude-review -->$/,$p'
     ```

     잡 이름, 단계 이름, 시각만 떼고 줄의 나머지는 그대로 둔다. 본문 안의 탭도 보존된다. 본문은 마커부터 **마지막** `::***::` 줄 앞까지다. 리뷰가 이 표식을 인용할 수 있으니 처음 나온 표식에서 자르지 않는다. 그 뒤에 남은 줄은 게시 오류 같은 스크립트 출력이다.
     - 같은 실행 ID의 PR 댓글은 꼬리말(`<sub>리뷰한 커밋`…)을 빼면, 로그 본문에서 마지막 `::***::` 줄을 뺀 것과 같아야 한다. 댓글이 길어 잘렸으면 잘림 안내 앞까지만 같다. 그 밖에 다르면 댓글은 쓰지 않고 사용자에게 알린다.
     - 본문이 있는데 댓글이 없으면, 로그의 본문으로 검증을 이어가고 "댓글 게시 실패"를 따로 기록한다.
   - 본문이 "Claude 리뷰를 하지 않았습니다"로 시작하면 크기 한도로 건너뛴 것이다. "생략(크기 한도)"으로 기록하고 지표(정확도, 2단계 추가 발견, 비용)에서 뺀다.
   - 로그에 "Unusable response"(`max_tokens`, JSON 오류)나 거절 오류("Claude declined")가 있으면 응답 처리 실패다. 이번 리뷰를 "미완료"로 기록한다.
     - 비용은 로그의 토큰 수로 적는다. 단 거절은 과금되지 않았을 수 있으므로 Console에서 확인해 적는다.
   - 본문도 처리 실패 기록도 없으면 이번 리뷰를 "미완료"로 기록하고 로그에서 원인을 본다.
   - 토큰 수와 추정 비용은 댓글 꼬리말에 있다.
3. **검증하고 고친다.** A의 3·4와 같다. 고치기 전에 판정을 사용자에게 보여 주고 멈추는 것도 같다.
   - 사용자에게 보여 주는 표에 `Codex도 냄` 열을 더한다.
   - 넘김·오탐 판정의 근거도 Codex에게 묻는다. Claude 리뷰어는 작성자와 같은 계열이라, 다른 계열의 확인이 더 필요하다.
   - 지적마다 Codex가 이미 낸 것인지 표시한다. 이 표시가 "2단계 추가 발견"의 근거가 된다.
4. **기록한다.**
   - PR 본문의 "AI 리뷰" 표에 PR 후 행과 지적별 접은 표를 추가한다. 접은 표에는 `Codex도 냄` 열을 더한다.
     - 본문은 `gh api -X PATCH repos/<저장소>/pulls/<번호> -F body=@<파일>`로 바꾼다. `gh pr edit`은 classic Projects 조회 오류로 실패할 수 있다.
   - 기록 파일에 한 줄을 추가해 커밋하고 push한다.
5. **Claude 리뷰는 PR당 1회다.** 다시 돌릴 때마다 지적과 수정, Codex 재리뷰가 새로 시작돼 끝나지 않기 때문이다.
   - Claude 지적을 고친 부분은 다시 Claude가 아니라 A.4의 Codex 재리뷰로 확인한다. 재리뷰를 할지, 언제 멈출지는 A.4의 기준을 따른다.
   - A.4의 기준으로 재리뷰가 멈추면 그 PR의 리뷰를 끝낸다. Claude를 다시 돌리지 않는다.
   - `claude-review` 라벨로 다시 돌리는 것은 다음 경우뿐이다. 이미 붙어 있으면 뗐다가 다시 붙인다.
     - 실행이 실패해 리뷰를 받지 못했을 때(미완료)
     - 리뷰 뒤에 설계가 크게 바뀌었을 때(예: 구현 방식 교체)
     - 리뷰 과정 자체(이 스킬, 리뷰 기준, 리뷰 워크플로·스크립트)를 다듬는 PR에서 사용자가 원할 때
